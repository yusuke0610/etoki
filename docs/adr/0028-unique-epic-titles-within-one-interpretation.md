# 0028: 同じ解釈の中で epic のタイトルを一意にする（弾いて直させる）

ステータス: 採用

## 文脈

draft issue は native な親子関係を持てないので、親は **epic のタイトル文字列**で
指している。Text フィールドによる手作りの外部キーであり、GitHub 側は整合性を
一切保証しない（ADR 0006）。

にもかかわらず、外部キーであるタイトルの一意性をどこも検証していなかった。
`Interpretation.Validate` は `localId` の重複・親の不在・階層の逸脱を弾くが、
タイトルの重複は素通りする。

同じ解釈に「認証」という epic が 2 つあると、その配下の issue はすべて
`Parent = "認証"` になる。**GitHub 側では区別が付かない。**

- エラーにならない。作成は最後まで成功する
- Project でグルーピングして初めて「なぜか 1 つにまとまっている」として現れる
- **draft issue は削除できない。** 気づいた時点で取り返せない

出力するのは LLM なので、似た話題を 2 箇所囲めば同じタイトルは普通に出る。
珍しいケースではない。

## 決定

**`Interpretation.Validate` で、同じ解釈の中の epic のタイトル重複を弾く。**

### 範囲は「同じ解釈の中」だけにする

衝突しうる相手は 3 段階ある。**下に行くほど etoki から見えなくなる。**

| | 何と衝突するか | 見えるか |
| --- | --- | --- |
| **1. 同じ解釈の中** | 同時に作る epic 同士 | `Interpretation` を見るだけ |
| 2. 同じ注釈の再作成 | 前回 run のタイトル | `sync_items` にある |
| 3. 同じ Project の他のボード / 他の注釈 | 別経路で作った epic | 全部は見えない |

**1 だけを入れる。** いちばん安く、いちばん頻度が高く、`Validate` の中で閉じる。

2 は「前回のどれの更新か」の対応づけと同じ土俵にある。更新なら同名は正しく、
新規なら誤りなので、`previousItemId` が解決した後でなければ判定できない。
対応づけは LLM に解釈させて開発者が決める形になっている（ADR 0026）ので、
そこに機械的な一意性検査を差し込むと、開発者が選んだ対応づけを検査が
覆すことになる。**別に判断する。**

3 は 1 つの Project に複数のボードがぶら下がる（ADR 0019）以上、必ず取りこぼす。
他のボードの epic を見にいけば「見えている範囲では一意」を保証できるが、
GitHub 側で直接作られた項目までは見えない。**中途半端に保証すると、保証されて
いると誤解される。** 文脈をどこまで持つかの話（#68）と重なるので、そちらと
まとめて判断する。

### タイトルを etoki が付け替えない

サフィックスを足して一意にする、といったことはしない。作るものの中身を黙って
変えることになり、「システムは自動で判断せず、状態を見せて開発者に選ばせる」
に反する。

**弾いて直させる。** 解釈結果は作成前に手直しできる（ADR 0024）ので、開発者に
出口がある。スキーマ違反と同じく LLM への再送ループにも載り、`ValidationError`
の文がそのまま修正指示になる。

### 比較は「見分けが付かないものを同じとみなす」

正規形は `normalizeTitle` = 前後の空白を落として NFC。

- **前後の空白は落とす。** Parent に入るのは生のタイトルなので `"認証"` と
  `" 認証"` は GitHub 上では別の文字列になる。しかし人には見分けが付かないので、
  「なぜか 2 つある」という形で同じように壊れる。
- **Unicode は NFC で揃える。** 合成済みと結合文字の違いは入力方式の差でしかない。
  「見た目が同じものは同じ」という判断は `ComputeContentHash` の `normalizeText`
  に既にあるので、それを再利用する。**別の正規化を 2 つ持たない。** どちらが
  正しい「同じ」なのかが決まらなくなる。
- **大文字小文字と全角半角は畳まない。** `API` と `api`、`API` と `ＡＰＩ` は
  どちらも見分けが付くうえ、GitHub 側でも別の文字列なので親子は壊れない。
  畳むと、壊れないものを弾くことになる。NFKC まで掛けないのはこのため。

### issue のタイトルは重複してよい

issue は親として指されないので、同名でも構造は壊れない。弾くと、壊れないものを
弾くことになる。

### フロントエンドに同じ判定を持たせない

注釈の判定規則（`isAnnotation`）を Go と TypeScript の両方に持っているのは、
フロントが往復なしで判定する必要があるからである。今回はそれに当たらない。

`Validate` は **GitHub への書き込みより前**に通る（`CreationService.Create` は
`applyItems` の手前で呼ぶ）ので、重複したまま作成を押しても draft issue は
1 件も作られない。失うのは 1 往復だけで、`ValidationError` の文がそのまま理由に
なる。取り返しの付かない状態には入らないので、判定を 2 箇所に増やす理由が無い。

## 結果

同じ解釈の中で親子が黙って壊れることは無くなった。範囲 2 と 3 は開いたままで、
**同じ注釈を作り直したとき、および同じ Project の別のボードとの衝突は防げない。**

タイトルが空の epic が 2 件あるときは「title を空にはできません」だけを報告し、
重複としては報告しない。元を 1 箇所直せば消える指摘を重ねると、修正指示が
実際より多く見える。

`interpretationSystemPrompt` の制約一覧にも同じことを書いてある。片方だけ変えると、
守れない指示を出すか、指示していない制約で弾くことになる。
