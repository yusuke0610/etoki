# 0044. 図の種別は注釈のメタデータに持ち、読み方の規則は実装に書かない

- 状態: 採用
- 日付: 2026-09-03

## 背景

新しいボードを白紙から始めるのではなく、開発で実際に使う図のひな形から始め
られるようにしたい（#52）。用意するのは todo / マインドマップ / シーケンス図 /
ER 図 / システム構成図の 5 種で、これは図のドラフト生成（#58、ADR 0041）が
既に持っている語彙（`domain.DiagramKind`）と同じものである。

ひな形は見た目の便宜ではない。**テンプレートを選んだ時点で「この範囲は何の
図か」が決まる**ので、解釈する LLM はそれを前提に読める。いまは白紙の
キャンバスに書かれたテキストの一覧しか渡していないため、シーケンス図として
描かれたものも ER 図として描かれたものも、同じ形で渡っている。

一方でここは中核思想を踏み外しやすい。ひな形は「構造」を配るものなので、
配る構造を間違えると、ブレストフェーズに etoki の概念を持ち込むことになる。

## 決定

### 種別は注釈のメタデータ（`customData.etoki.kind`）に持つ

粒度（`granularity`）と同じ場所に置く。フロントだけがシーンを組み立てて種別を
持つと、**サーバーからは見えず解釈のプロンプトに載せられない。** それでは
ひな形が「ただの絵」で終わる。

規則は Go（`internal/domain/scene.go`）と TypeScript
（`web/src/excalidraw/annotation.ts`）の両方に要る。注釈の判定規則が 2 箇所に
あるのと同じ形で、**片方だけ足すと壊れる。**

契約（`api/openapi.yaml`）では `AnnotationStatus.kind` を**省略可能**にした。
`Granularity` のように空文字を enum に足さないのは、`DiagramKind` の語彙を
1 つに保つため。プロンプトからのドラフト生成は「何の図か」が入力そのもので
指定なしを受け付けないので、enum に空文字を足すとそちらの契約まで緩む。

### 種別は `content_hash` の入力に含める

粒度と同じ理由。**種別を変えれば LLM が読む前提が変わるので、`changed` に
ならなければおかしい。** 含めないと、種別を差し替えたボードが `created` の
まま残り、前の種別で作った draft issue が最新であるかのように見える。

`TestComputeContentHash_IgnoresNonTextChanges`（図形・座標の変更を無視する
仕様）とは矛盾しない。種別は図形ではなくメタデータで、粒度がすでに同じ扱いに
なっている。

**指定なしでも入力に書く。** 書かない形にすれば種別を持つ前の値と一致させられ、
既存の記録済み `content_hash` をそのまま使えるが、**算出の入力が種別の有無で
分岐する**ことになる。分岐は「なぜここだけ特別なのか」を知らないと消せない形で
恒久的に残るので、一度きりの移行のために抱えない。

代償は移行時に一度だけ払う。**既存の `created` な注釈は一斉に `changed` に
見える。** 中身は変わっていないので、開発者はそれを見て更新するか放置するかを
選べる（中核思想 3、ADR 0026 の更新は取り消せないので押すかどうかは人が決める）。

### 種別から図の読み方を導く実装を書かない

これが中核思想 2 との境目である。

- **渡してよい理由**: 種別は開発者が明示的に選んだメタデータであって、座標や
  近接から推測したものではない。だから LLM に渡しても「構造は座標から推測
  しない」に反しない。
- **反する側**: 種別を使って etoki のコードが図を読み始めたとき。
  「シーケンス図だからこの矢印は呼び出しだ」「ER 図だからこの線は 1 対多だ」
  といった規則を実装に書いた時点で、決めているのは etoki になる。

解釈のプロンプトに載せる指示（`usecase.diagramReadings`）も「何の図として
読むか」までに留める。**プロンプトに書いてもコードに書いても、決めているのが
etoki である点は変わらない。**

守れていることの印は、`domain.Element` が読むフィールドが増えていないこと。
いま読んでいるのは `frameId` / `containerId` / `name` / `text` / `customData`
だけで、矢印の始点・終点を読む口を足したくなったら、そこが設計を見直す合図。

### ひな形は etoki の構造語を置かない

**epic / issue の枠をひな形に置かない**（中核思想 1）。置いた時点で、ブレスト
フェーズに issue / epic の概念を持ち込むことになる。ひな形が与えるのは設計の
構造（登場人物、実体、構成要素）までで、構造化は解釈と開発者フェーズの仕事の
まま。`web/src/excalidraw/template.test.ts` がこれを検査する。

粒度もひな形が決めない（`granularity` は「指定なし」から始める）。決めると、
選んだ覚えのない制約が解釈に効く。

### ひな形は frame を作らない。種別は注釈パネルで選ばせる

「etoki は frame を自前生成しない」という線は、**境界にまたがる要素の帰属
判定を自分で持たないために**引いてある（ルートの `CLAUDE.md`、ADR 0040 で
mermaid の変換結果から frame を拒む理由も同じ）。

ひな形なら frame と中身を同時に作るので帰属を推測する場面は無く、線を曲げても
壊れないという理屈は立つ。**それでも曲げない。** 「この条件なら安全だから」で
1 つ例外を作ると、次に frame を配りたくなったときに参照される前例がここに残る。
線は条件つきになった時点で線でなくなる。

**ひな形が配るのは絵だけ**にする。どこを issue 化の対象にするかは、これまで
どおり人がフレームツールで囲んで決める。

その帰結として、**種別はひな形には載らない。** 種別は注釈のメタデータなので、
載る先は人が引いた frame になる。だから**選ぶ場所は注釈パネル**（粒度の隣）に
なる。ひな形を選ぶことと種別を選ぶことは別の操作で、ひな形を使わずに自分で
描いた図にも種別を付けられる。

**ひな形の選択と種別の選択を自動で結ばない**（中核思想 3）。「シーケンス図の
ひな形で作ったのだから、囲んだらシーケンス図だろう」は etoki が勝手に決める
ことで、ひな形をなぞらずに別の図を描く自由をその場で奪う。

### 境界は frame ではなく矩形で描く

システム構成図のひな形だけは、境界（外部サービスとの境目など）という囲みが
要る。これを frame で描くと、人がこの絵を囲んで注釈にしたとき、注釈の frame の
中に frame が入る。

`Scene.AnnotationTexts` は **1 段だけを見る。入れ子の frame は辿らない。**
内側の frame に入れた要素は `frameId` が内側を指すので、外側の注釈の子には
出てこない。つまり境界を frame で描くと、**境界の中に書いた文字がまるごと
ハッシュと解釈から抜ける。**

矩形なら中身は注釈の直接の子のままで、ラベルも `containerId` 経由で拾える。
`TestAnnotationTexts_DoesNotFollowNestedFrames` が抽出側の仕様を、
`template.test.ts` の「frame を作らず、注釈も作らない」と「囲めば 1 段で拾える
形になっている」がひな形側を固定する。

なお、内側の frame が注釈と誤認されないこと自体は既存の判定規則
（`customData.etoki` を持つ frame だけが注釈）がすでに守っている。ここで
避けているのは誤認ではなく、テキストの取りこぼしのほう。

## 検討したが採らなかった案

### `AnnotationTexts` が入れ子の frame を辿るようにする

境界を frame で描けるようになるが、**仕様変更としての影響が広い。** ユーザーが
自分の用途で注釈の中に置いた frame の中身まで、黙って解釈の入力に混ざる。
ひな形 1 つのために抽出の意味を変えるのは順序が逆で、境界を矩形にすれば
済む話だった。辿るように変えたくなったら、そのときにここを書き換える。

### 種別ごとに専用のスキーマを持たせる

「シーケンス図の登場人物」「ER の実体」を etoki の型として持てば、解釈に
渡す情報は増える。**採らない。** 図を読む仕事を etoki が引き受けることに
なり、中核思想 2 に正面から反する。渡すのは種別という一語だけでよい。

### ひな形に仮置きの言葉を置かない（枠だけにする）

解釈の入力に余計な文字が一切入らない。**採らない。** 何を書く場所なのかが図から
読めなくなり、ひな形の値打ちが「線を引く手間を省く」だけに縮む。

置く言葉は**役割名**にする（「利用者」「注文」「フロントエンド」）。番号だけの
仮置き（「実体 1」）では何を書く場所か伝わらず、逆に特定の製品名まで踏み込むと、
書き換え忘れたときに解釈がその言葉を拾って描いていないものが候補に出てくる。

### ひな形を選ぶ画面を 1 枚増やす

分かりやすいが、**空白で始めたい人にも通り抜けるだけの手順が増える。**
ボード名の入力と同じフォームに並べれば、選ばないという選択がそのまま既定に
なる。

### 既存のボードにひな形を差し込めるようにする

差し込みは既存シーンの上書きになるので、未保存の扱いと衝突検知（ADR 0020）に
揃える必要がある。**今回は入れない。** 新しいボードで始められれば、ひな形が
解釈に効くかどうかは確かめられる。

## 影響

- **移行時に、既存の `created` な注釈が一度だけ `changed` に見える。**
  `ComputeContentHash` の入力が種別のぶん伸びるため。中身は変わっていないので、
  更新するかどうかは開発者が選ぶ（作成も更新も押したときにしか起きない）。
- **ひな形から作ったボードには注釈が無い。** 囲むのは人なので、開いた直後の
  注釈パネルは「保存済みの注釈はありません。」のまま。
- 注釈パネルに「種別」が増える。粒度と同じ `<select>` で、**選び直すと未保存に
  なる**（シーンに書くため）。保存すれば `content_hash` が変わるので `changed`
  になる。
- 知らない種別は「指定なし」に丸めず 400 で弾く（粒度と同じ）。
