# 0041: 図のドラフト生成はサーバーの状態を変えない（会話も持たない）

ステータス: 採用

## 文脈

白紙のキャンバスから描き始めるのはコストが高い。一文のプロンプトから図の骨格を
生成し、そこから人が手で直せるようにしたい（#58）。

似た形の機能がすでにある。解釈（`InterpretationService`）は LLM を叩き、
スキーマ検証と修正指示つき再送を持つ。**同じ形に見えるが、入力の出どころが
違う。** そこから先の制約がすべて分かれる。

|                    | 解釈                    | 生成           |
| ------------------ | ----------------------- | -------------- |
| 入力               | 保存済みシーン + 画像   | プロンプトだけ |
| 出力               | `domain.Interpretation` | mermaid        |
| 保存               | しない                  | しない         |
| 未保存でも使えるか | 使えない（ADR 0018）    | **使える**     |
| 会話               | 無い（1 回で完結）      | **続けられる** |

## 決定

### サーバーの状態を一切変えない

DB にも GitHub にも触れない。**確定させるのは常に人間の保存操作**（中核思想 3）。

```text
生成:  プロンプト → LLM → 画面   （サーバーは素通り）
保存:  キャンバス → DB           （人間だけがトリガー）
```

`usecase.BoardLocks` を使わないのはこの帰結。直列化は「作成先の固定を判定する
側と、その前提を崩す側」を揃える仕組みで、何も書かないなら揃える対象が無い。

副産物として、**同時編集の後勝ち（#31）の危険が bot 由来では消える。** bot は
保存しないので、他人の作業をサーバー側で潰しようがない。

### 未保存でも使える。解釈との非対称は副作用の有無から出る

解釈は保存済みシーンからテキストを取り、画像は画面から取るので、揃っていないと
1 回の解釈の入力が食い違う（ADR 0018）。生成はどちらも読まないので、その理由が
無い。

**手抜きではなく説明のつく非対称。** 解釈は `contentHash` を返し、それが取り
消せない作成の前提になる（ADR 0010）。生成が返すのは絵の下書きだけで、置くか
どうかも保存するかどうかも、このあと人が決める。

### 会話は永続化せず、毎回まるごと組み立て直す

会話履歴はフロントのメモリだけに置き、リクエストのたびに全部送ってもらう。

- **保存すると「誰の会話か」「他のメンバーに見えるか」が立ち上がる**（ADR 0017）。
  テーブルとマイグレーションが要る問いで、後から足せる。**会話は成果物では
  なく、成果物はキャンバス。**
- **`port.LLMClient` は拡張しない**（ADR 0005）。1 往復ぶんしか運べないままに
  して、会話はユースケース層が 1 通の自己完結したメッセージへ書き下ろす。
  既存の `buildRetryMessage` と同じ形。**自前実装を差し込む外部リポジトリの
  負担を増やさない**（ADR 0001 / 0008）。

代償として、会話が伸びるとトークンがそのまま積み上がる。上限は 2 つ持つ
（`usecase.MaxDiagramTurns` と `MaxDiagramChatBytes`）。**回数だけでは足りない。**
1 通に長文を貼れば往復 1 回で同じだけ積み上がる。

**上限に当たったら黙って古いやりとりを捨てない。** 捨てると、積み上げた指示の
どれが効いているのかが分からなくなる。413 で返し、やり直すかどうかは開発者が
決める（中核思想 3）。400 に畳まないのは、送られた内容は正しく、打ち手が
「送った内容を直す」ではなく「会話をやり直す」になるため（ADR 0038 と同じ
切り方）。

### どの mermaid 記法で書かせるかはサーバーが決める

開発者が選ぶ語彙は #52 と同じ 5 種（todo / mindmap / sequence / er /
architecture）。**語彙を 2 箇所に持たない**ので、`domain.DiagramKind` 1 つに
まとめた。

その中でどの mermaid 記法を使うかは etoki が決める。**選ぶ基準は「mermaid で
書けるか」ではなく「Excalidraw の要素として置けるか」。** mermaid には
`mindmap` と `architecture-beta` があるが、変換器はそれを図形に分解せず画像
1 枚にして返し、置く側はそれを拒む（ADR 0040）。頼めば**必ず置けないものが
返る**ので、どちらも flowchart で書かせる（木、および subgraph で境界を作った
図）。

**開発者に見せる語彙は変えていない。** 変えたのは、その中でどう書かせるかだけ。

### mermaid の構文はサーバーで検証しない

解釈がスキーマ違反を修正指示つきで再送するのと同じ扱いにはしない。

- Go で mermaid を検証するにはパーサを持ち込むことになる。**コアに JS の
  ランタイムを抱えるのは、依存の方向として引き合わない。**
- そもそも要るのは「mermaid として読めるか」ではなく**「Excalidraw の要素と
  して置けるか」**で、それを知っているのは変換器だけ。半端にサーバーで検べると、
  置けないものを通す判定が置ける判定より手前に立つ（ADR 0018 の「判定を 2 箇所に
  持たない」と同じ）。

サーバーが見るのは、**指摘すれば直る 2 つだけ**。何も返さなかったことと、
頼んだのと違う記法で書いたこと。どちらかなら 1 度だけ投げ直す。構文エラーで
変換が落ちたときの投げ直しは、**変換を試したフロントが会話の次の 1 往復として
行う**（#61）。

## 結果

- `Capabilities` に `diagramDraft` が増えた。**`interpretation` と畳まない。**
  未設定の理由も設定するものも同じ LLM だが、答えている問いが違う。畳むと
  画面がどちらのボタンを止めればよいのかをこの値から決められなくなる
  （ADR 0030）。
- エンドポイントは**ボードの直下**（`POST /api/boards/{id}/diagram-draft`）。
  囲みとは無関係で、キャンバスに何も無くても呼べるので、注釈の下に置かない。
- **viewer には許さない。** LLM を叩く外部呼び出しで課金も伴う。閲覧者に外部
  呼び出しを許すのは「閲覧」ではない（ADR 0017、解釈と同じ理由）。
- 生成 1 回ぶんの実績はログに残す（ADR 0031）。**失敗しても残す。** 投げ直して
  直らなかったぶんも課金されている。
- **レート制限（#45）は入っていない。** チャットは解釈より桁違いに呼び出しが
  多いので、共有ボードに人を招く構成では先に要る。上限が効いているのは
  「1 回の生成」の中まで（往復と長さ）で、**何回生成できるかは抑えていない。**
