# 0042: ボードの削除は、GitHub 側に残るものを見せてから通す

ステータス: 採用

## 文脈

ボードを作ったあとに消す手段が無い（#40）。作成時に名前と作成先を決めさせる作り
（ADR 0017）なので、**打ち間違えたボードも、試しに作ってやめたボードも、そのまま
一生残る。** 一覧は作成先でまとめて見せる（ADR 0019）ため、要らないボードは木の
中に混ざり続け、共有した相手にも見え続ける。

問題は削除そのものではなく、削除が何を捨てるかにある。**etoki は GitHub 側の
draft issue を消さない**（消せない、が正しい。逆方向同期はスコープ外）。ボードを
消すと `sync_runs` が `ON DELETE CASCADE` で消えるので、**GitHub に残った draft
issue の出どころが辿れなくなる。** これは ADR 0007 が「履歴を残す」と決めた理由と
正面からぶつかる。

## 決定

**削除を通す。ただし、何が残るのかを見せてから確認させる。**

- **`DELETE /api/boards/{id}`。owner だけ**（ADR 0017）。ボードごと畳む操作は、
  招待もロールの変更も作成先の変更もできる相手に限る。editor はシーンを書き換え
  られるが、それは中身を直す操作であって、他のメンバーからボードを取り上げる
  操作ではない。
- **削除で失われるものを先に返す口を分ける。** `GET /api/boards/{id}/deletion` が
  「etoki が作成を記録している draft issue の件数」を返し、画面は押される前に
  それを出す。**押されたときだけ引く**（中核思想 3、ADR 0037 の取り直しと同じ形）。
- **文言は「残る」と「辿れなくなる」を分けて言う。** GitHub 側の draft issue は
  残る。消えるのは etoki 側の記録のほうで、失われるのは「どのボードのどの注釈から
  作ったか」という対応づけである。
- **件数は `ListItemsByBoard` の畳み込みから採る**（ADR 0026）。注釈のカードに
  出している「いま GitHub に在る N 件」と同じ数え方にする。別に数えると、同じ
  ボードについて画面が 2 つの数を出す。**届いたか分からない書き込み（ADR 0056）は
  別に数えて言う**（末尾の追記）。
- **削除はボード単位のロック（`usecase.BoardLocks`）の中で行う。** 作成の途中で
  ボードが消えると、GitHub には draft issue ができたのに run を書けず、**取り
  消せない作成が記録の無いまま残る**（ADR 0009 が避けたかった状態そのもの）。
  作成先の固定判定と同じ鍵で直列化する。
- **アーカイブは持たない。** 一覧から外すだけの状態を足すと、「消したつもりだが
  消えていない」ものが増える。単一利用者のローカルツールで、消したいのはたいてい
  打ち間違えたボードである。

## 結果

- 打ち間違えたボードも、作成先を間違えたボードも畳める。`board_members` も
  `sync_runs` も `sync_items` も CASCADE で消えるため、マイグレーションは要らない。
- **GitHub 側に残った draft issue の出どころは、削除した時点で辿れなくなる。**
  ADR 0007 が避けたかった状態に、開発者が選んで入ることになる。etoki が自動で
  そこへ落とすことはない（中核思想 3）。
- 「最後の owner は外せない」（ADR 0017）と削除は矛盾しない。あの規則は**誰も
  管理できないボードを残さない**ためのもので、畳む手段を塞ぐものではない。owner は
  抜けられないが、ボードごと消すことはできる。
- `UpdateScene` は「ボードを消す経路が無い」ことを前提にしていた（照合に失敗した
  あと、触れるかどうかを引き直す 2 文）。削除が入っても答えは変わらない。隙間で
  消えたなら「触れなくなった」（`ErrNotFound`）が正しい返り値になる。

## 採らなかった案

- **run のあるボードは削除させない（`targetLocked` と同じ考え方）。** 追跡表は
  守れるが、いちばん畳みたいボード——作成先を間違えたまま 1 回作ってしまった
  ボード——が永久に残る。しかも「システムが自動で判断せず、状態を見せて開発者に
  選ばせる」（中核思想 3）に反する。判断できる材料を見せずに、こちら側で決めて
  いることになる。
- **アーカイブ（一覧から外すが消さない）にする。** 追跡表は残るが、削除したい
  という要求には答えていない。状態が 1 つ増え、一覧・共有・作成先の判定すべてに
  「アーカイブ済みをどう扱うか」が生える。**残すこと自体が目的なら、いま何も
  しないのと同じ。**
- **削除時に GitHub 側の draft issue も消す。** 逆方向の書き込みはスコープ外で、
  しかも draft issue は取り消せない作成物である（ADR 0009）。etoki が消せる／
  消すべきだと決めてよいものではない。
- **件数を `BoardDetail` に足す。** ボードを開くたびに畳み込みを引くことになる。
  削除を押すまで要らない数なので、押されたときに引く。

## 追記（ADR 0056 との隙間）

**届いたか分からない書き込みも、削除の確認で別に数えて言う**
（`BoardDeletion.unconfirmedWriteCount`）。

ADR 0056 で、応答を失った書き込みを `confirmed = 0` で記録するようになった。
上の件数（`ListItemsByBoard`）は確定したものしか畳まないので、未確定の作成しか
無いボードでは「このボードから作成した draft issue の記録はありません」と出て
いた。実際には GitHub に draft issue が作られているかもしれず、削除すると、それを
確かめにいく手掛かり（注釈の詳細の記録）も消える。この ADR の目的（何が失われる
のかを見せてから確認させる）が、未確定の書き込みについて果たされていなかった。

- **確定の件数に混ぜない。** 混ぜると「N 件記録されています」が嘘になる。数えるのは
  draft issue ではなく書き込みの回数で、未確定の更新は確定した item への書き込み
  でもありうる（混ぜると同じ draft issue を 2 度数える）。注釈の詳細の
  `unconfirmedItems` と同じ口（`ListUnconfirmedItemsByBoard`）から採り、あとで確定の
  記録が付いたものは数えない。
- **「失敗しました」と書かない**（ADR 0056）。言うのは、届いたか分からないこと、
  draft issue が作られているかもしれないこと、削除すると確かめる手掛かりも消える
  こと。
- **削除は止めない。** 決めるのは開発者（中核思想 3）。
