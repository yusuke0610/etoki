# 0086: 作成先を選んだときに、作成に要るフィールドが揃っているかを見せる

ステータス: 採用

## 文脈

draft issue の種別と親は、作成先の Project のカスタムフィールドで表す
（ADR 0006）。種別を表す単一選択のフィールド（選択肢 epic / issue）と、親を
表すテキストのフィールドが要る。足りなければ作成は 422
（`project_field_missing`）で止まる。黙って作ると、種別も親子も無い draft issue
が並ぶだけになるため。

**足りないと分かるのは「GitHub に作成する」を押したとき**だった（#292）。
ボードを作り、ブレストし、絵解いた後で止まる。初めて使う人と導入する人が、
いちばん手間をかけた後で止まる。

押した後の文は #292 の 1 つ目の PR で「何を作ればよいか」まで言うようにした。
この ADR は、それを**選んだ時点でも見せる**かどうかを決める。

## 決定

**作成先の Project を選んだときに 1 度だけ GitHub に問い合わせ、足りないものを
見せる。** 口は `GET /api/github/projects/{projectId}/fields`。

### 返すのは役割と状態だけ

- 結果は `status: ok | missing | unknown` と、`missing` のときの
  `missingFields`（`kind_epic` / `kind_issue` / `parent` の enum）。
- **フィールドの名前は返さない。** 名前は設定で変わり、知っているのは起動の
  配線だけ。画面に名前を写すと、名前を変えた構成で既定の名前を案内し続ける。
  ADR 0083 は環境変数の名前についての判断で、フィールドの名前はその値にあたる
  ので直接の対象ではない。**同じ理由で同じ線を引いた。** 名前は作成時の
  エラー本文として「詳細」に出る（ADR 0034 の畳み方のまま）。
- **選択肢の epic / issue は画面に出す。** これは設定で変わらない etoki の語彙
  （ADR 0006）。

### 判定ではなく状態

**確かめた結果を判定に使わない。** 実際に作れるかは作成時に GitHub が返した
ものが正しい（ADR 0017 の `projectAccess` と同じ）。確かめたあとで GitHub 側の
フィールドは消せるし、足せる。

- 選択の画面は結果を見せるだけで、**`missing` でも選ばせる**（中核思想 3）。
  ブレストを先に始め、フィールドは後で足す、という順番を潰さない。
- **作成時の判定はそのまま。** 足りなければ作らずに止める。
- **判定は 1 つの関数を共有する**（`usecase.matchProjectFields`）。作成の
  `resolveFields` と確認が同じものを呼ぶ。2 箇所に書くと、確認が「揃っている」
  と言った Project で作成が止まる。名前も同じ値を `etoki.New` から両方に渡す。

### 問い合わせられなければ unknown

GitHub への問い合わせが失敗したら、**エラーにせず 200 で `unknown` を返す。**
`ok` にも `missing` にも倒さない。確かめていないことを確かめたように見せない
（`projectAccess` と同じ扱い、ADR 0017）。

同じ並びのカタログの口（リポジトリと Project の一覧）は GitHub の失敗を
502 / 403 で返す。**扱いを分けたのは、答えの性質が違うため。** 一覧が取れない
と選ぶものが無いが、確認が取れなくても選ぶことはできる。表示のための材料が
取れないだけで、選択の画面に失敗を出す理由が無い。

GitHub を設定していない構成は、ほかのカタログの口と同じく 503
（`github_not_configured`）。`unknown` に混ぜると、capabilities が材料にしている
nil と案内が食い違う（ADR 0030）。

### 置き場所

- **問い合わせは `GitHubCatalogService` に置く。** `BoardService` に GitHub への
  依存を生やさない（#25 で却下済み）。
- **ボードではなく Project に紐づける。** 新しいボードを作る流れでは、作成先を
  選ぶ時点でまだボードが無い（ADR 0017）。フィールドの有無は Project の性質で、
  ボードの口に載せるとボードによって違いうるように読める（ADR 0030 が
  `capabilities` をボードの口に載せなかったのと同じ理屈）。

### 画面

- **作成先の選択を 2 段にした。** これまでは Project を押した瞬間に確定して
  画面が切り替わり、結果を見せる場所が無かった。押すと「選んだ」状態になって
  確認が走り、「この Project にする」で確定する。**確定のボタンは結果で止め
  ない。**
- **問い合わせるのは選んだときだけ。** 一覧を出しただけでは引かない（Project の
  数だけ問い合わせが増える）。ボードを開いたときにも引かない（ADR 0037 が
  自動で取りにいかないと決めたのと同じ）。
- **文言は `ERROR_MESSAGES.project_field_missing` と同じ部品から組む**
  （`web/src/api/errorMessage.ts`）。足りないものの言い方を役割ごとの表に置き、
  押した後の文はそれを全部並べて、押す前の文は足りないものだけを並べて作る。
  **同じ原因には同じ文**（ADR 0030）。役割の表は `ErrorCode` ではなく契約の
  `ProjectFieldRequirement` を鍵にした `Record` なので、契約に役割を足して
  文言を書き忘れると `tsc` が落ちる。`project_field_missing` を言うための
  部品なので、失敗の文言を持つこのモジュールに置く。

## 採らなかった案

- **作成時の 422 に、足りないものを構造化して載せる。** 押した後の文を足りない
  ものだけに絞れるが、分かるのは押した後のままで、#292 の困りごと（いちばん
  手間をかけた後で止まる）は残る。`ErrorResponse` に code ごとの付帯情報を持た
  せる形も、今は他に使い手がいない。押した後は全部の要件を並べ、何が足りないかは
  詳細の本文で読める。
- **`capabilities` に載せる。** あれはプロセスの設定を返す口で、Project ごとに
  違うものを載せると ADR 0030 の「プロセスの設定と利用者の権限を分ける」に反する。
  フィールドの有無は `projectAccess` と同じく、作成先ごとの状態。
- **名前まで前に出す。** 名前を契約に載せることになり、画面が設定の値を写す。
  名前を変えた構成で、画面と設定がずれる経路が増える。名前は作成時の本文で
  読めるので、今回は入れない。

## 結果

- 作成先を選んだ時点で、足りないフィールドが分かる。GitHub 側で作ってから
  選び直しても、そのまま選んで後で作ってもよい。
- 選ぶたびに GitHub への問い合わせが 1 往復増える。
- 作成先の選択に 1 クリック増えた。取り返しのつかない選択（最初の作成で固定、
  ADR 0014）の手前に、確かめる場所ができたとも言える。
- 判定を共有していることは `TestCheckProjectFields_AgreesWithCreate` が見ている。
  片方の判定だけを変えると、同じ入力で確認と作成の答えが割れて落ちる。
