# 0045: 保存できる上限を超えたボードは、開いた時点で真偽値だけを返して知らせる

ステータス: 採用

## 文脈

`usecase.MaxSceneBytes`（8 MiB、ADR 0038）は保存の入口にしか無く、読み出しには
上限が無い。上限を導入する前に保存された大きいボードや、上限を引き下げた後の
ボードは、これまでどおり開けるが、開いた先で保存を押すと必ず 413 になる
（issue #103）。画面には「貼った画像が大きすぎて保存できません」と出るので理由は
分かるし、拒まれるのは保存だけでキャンバスの内容は失われない。それでも、
「画像を減らす」以外に出口が無いことが、押すまで分からない。

ADR 0038 は「上限を持つのはサーバーだけ。フロントは事前に判定しない」と決めて
いる。両方に上限を持たせると、片方だけ変えたときに「フロントは通すがサーバーが
弾く」がどちらの言い分か分からなくなるためで、ここは変えない。一方で、開いた
時点で「このままでは保存できない」と伝えるには、フロントが**保存できるかどうか**
を知る必要がある。上限の**数値**を知る必要はない。

## 決定

### 判定結果を真偽値として返し、上限の数値は返さない

`GET /api/boards/{id}` の応答（`BoardDetail`）に `sceneOverLimit: boolean` を足す。
`usecase.SceneExceedsLimit(scene)`（`len(scene) > MaxSceneBytes`）の結果をそのまま
返すだけで、`MaxSceneBytes` の値そのものは境界に出さない。

これは `projectAccess` の `unknown` / `allowed` / `denied`（ADR 0017）や
`capabilities`（ADR 0030）と同じ型で、**判定はサーバーの持ち場のまま、フロントは
結果を見せるだけ。** ADR 0038 が禁じているのは上限の数値の複製であって、
判定結果を境界に出すことではない。

413 判定（`validateScene`）とこの真偽値は同じ `usecase.SceneExceedsLimit` を
呼ぶ。2 箇所で `len(scene) > MaxSceneBytes` を書くと、上限を動かしたときに片方
だけ直し忘れる。

### 保存が成功したら、フロントは手元だけで判定を倒す

保存が成功した = そのシーンはサーバーの上限を満たした、という事実からそう言える。
上限の数値を持たなくても、この推論だけで警告を下ろせる。読み直して
`sceneOverLimit` を取り直す口は作らない。取り直す理由（GitHub 側の実体が変わる
作成先の表示名などとは違い）が無いのに増やすと、保存のたびに余計な問い合わせが
増える。

### 内訳（どの画像が何バイトか）は出さない

issue のタスクには「シーン内の画像の内訳を出すかを決める」があったが、今回は
出さない。上限超過は上限導入前 or 引き下げ後にしか起きないレアケースで、警告さえ
出れば「画像を減らす」という次の一手は Excalidraw の通常操作（要素を選んで削除）
で行える。中核思想 3 は「状態を見せて選ばせる」であって、操作の代行までは
求めていない。要れば別 issue として切り出す。

## 結果

- 上限を導入する前に保存された大きいボードは、開いた瞬間に「このボードは保存
  できる上限を超えています」という警告が出る。押してから 413 で気づくのではない。
- `BoardDetail` に真偽値が 1 つ増える（契約は `api/openapi.yaml` が正本、ADR 0011）。
  数値を返さないので、上限を動かしても契約は変わらない。
- ADR 0038 の「上限を入れる前に保存された大きいボードは、開けるが保存し直せない」
  という結果そのものは変わらない。**変わるのは「気づけるタイミング」だけ。**
  画像を減らさない限り保存できない状態は今回も直さない（ADR 0038 の
  「切り捨てない」判断を踏襲）。

## 採らなかった案

- **上限の数値も返す（`GET /api/capabilities` の延長）。** ADR 0038 が検討して
  保留にした案。数値を返すとフロントが「あとどれくらいか」を計算できるように
  なるが、上限を動かしたときにフロントの表示ロジックも連動して変える理由が
  生まれ、複製に近づく。真偽値だけで「開いた時点で分かる」という目的は満たせる。
- **読み直しのたびに `sceneOverLimit` を取り直す。** 保存以外に判定が変わる
  経路が無い（上限を動かすのはデプロイ時だけ）ので、増やす問い合わせに見合う
  価値が無い。
- **フロントで `sceneBytes(scene)` と何らかの定数を比べる。** 定数を置いた
  時点で上限の複製になり、ADR 0038 の判断に戻ってしまう。
