# 0052: 作った項目は同じ下書きから新規に作らせない

ステータス: 採用

## 文脈

draft issue は削除できない（ADR 0009）。重複を作らせないために、作成の入口には
解釈時点のハッシュの照合（ADR 0010）と、更新先の照合（ADR 0026）を積んである。

**いちばん押しやすい経路が、その照合をそのまま通っていた**（#139）。

- 作成が済んでも、同じ解釈結果のまま「GitHub に作成する」を押せた。ボタンを
  止めるのは実行中・下書きの不備・保存中・取り込み中だけで、作成の結果は効いて
  いなかった。下書きも全項目が選ばれたまま残る。
- サーバーも止めない。作成しても保存済みシーンは変わらないので、2 回目も
  ハッシュの照合を通る。`previousItemId` を持たない項目は、そのまま新規に作られる。

「押しても反応が無かった気がする」も、「途中で失敗したので、もう一度押せば残りが
作られるはず」も、どちらも自然な操作である。後者は画面が「作れたところまでは
GitHub 側に残っています」と言ったうえで、作れた項目まで選ばれたまま残していた。

## 決定

**作れた項目は、その下書きから新規には送らない。選択を外し、選び直したら作った
draft issue の書き換えとして送る。**

- 作成の応答に載った項目の選択を外す。全部作れたら何も選ばれていないので、
  ボタンは既存の「作るものが 1 件も選ばれていません」で止まる。途中で失敗した
  なら、残りだけが選ばれたまま残る。
- **作った項目を選び直すと、作った ID を更新先として送る。**「新しく作る」には
  倒せない。LLM が対応づけた先（`previousItemId`）より優先する。LLM の答えは
  書き換えずに残す（ADR 0026）。
- **作ったものは下書きではなく解釈の側に持つ。** 下書きは解釈を選び直すと
  作り直されるので、下書きの中だけに持つと、戻ってきたときに作成済みの項目が
  全部選ばれた状態に戻る。解釈と同じく、保存で捨てる。

### 途中で失敗したあとに残りを作る

epic は issue より先に作るので（子の親を epic のタイトルで指すため、ADR 0006）、途中で失敗するとふつうは「epic は
作れて、子の issue が残る」形になる。子の親は**同じリクエストに載った epic の
タイトル**で解決するため、作れた epic を外したまま子だけを送ると、子は親なしで
作られる。

**epic を勝手に選び直さない。** 選択が外れた epic の子は「epic に属さない issue
として作られます」と画面に出る（ADR 0024）。開発者が epic を選び直せば
「epic の書き換え + 子の作成」で送られ、親子がつながる。親なしで作るか、epic を
書き換えてつなぐかは開発者が決める（中核思想 3）。

### 採らなかった案

- **作れた項目を外して触れなくする。** いちばん単純だが、上の形で子が必ず親を
  失う。途中で失敗したあとの親子を、GitHub 上で手で直すしかなくなる。
- **作成が済んだら下書きごと止める。** 追加で作るには解釈し直すことになり、
  途中で失敗したぶんの残りを作るだけで LLM をもう一度呼ぶ（課金を伴う、
  ADR 0044）。
- **サーバーでも止める**（同じハッシュで作った項目を再送したら 409）。作った
  項目を選び直して書き換える操作とぶつかる。画面の側で新規に送らない形にすれば、
  サーバーに届くのは正当な書き換えだけになる。**API を直接叩いた二度押しは
  止まらない**が、それは解釈を直接叩ける経路と同じ扱い（ADR 0010 は古い解釈の
  まま作ることを塞いでおり、同じ解釈を 2 回送ることは塞いでいない）。

## 結果

- 作成が済んだあとに同じ解釈から押しても、draft issue は増えない。
- 途中で失敗したあとは、残りだけが選ばれた状態から始められる。
- 作った項目の書き換えは、これまでどおりハッシュと更新先の照合を通る。作った
  直後の item は畳み込みに入っているので、更新先の照合を通る。
- 解釈し直した結果は別の下書きで、作ったものは引き継がない。前回ぶんとの
  対応づけは LLM に解釈させる（ADR 0026）。
