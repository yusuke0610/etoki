# 0044: ボードの持ち出しと取り込みは etoki の口 1 つに寄せる

ステータス: 採用

## 文脈

ボードを 1 枚だけ取り出す手段が無かった。バックアップは SQLite ファイルを丸ごと
コピーするしかなく、すでに Excalidraw で描いたものを etoki に持ってくる導線も
無い。ブレストの実体がツールの中に閉じていると、etoki をやめるコストがそのまま
蓄積する（#42）。

**ただし「手段が無い」は正確ではなかった。** etoki は `Excalidraw` に `UIOptions`
を渡していないので、ライブラリの既定メニューがそのまま出ている。そこには
すでに「開く」（`.excalidraw` を読んでシーンを丸ごと置き換える）と「名前を付けて
保存…」（`.excalidraw` として書き出す）が並んでいる。`.excalidraw` をキャンバスへ
ドロップしても同じことが起きる。

**問題は手段が無いことではなく、手段が etoki の状態と噛み合っていないこと
だった。**

- **同じ画面に「保存」が 2 つある。** ヘッダーの「保存」はサーバーへ、メニューの
  「名前を付けて保存…」はファイルへ。押し間違えると「保存したのに残っていない」
  が起きる。未保存のまま離れさせないと決めた（ADR 0021）以上、その入口の隣に
  別の意味の「保存」を並べたままにはできない。
- **書き出したファイルにボード名が付かない。** ライブラリはボード名を知らない。
- **確認の文言がライブラリのもので、etoki の未保存の約束と別系統になる。**

## 決定

### 書き出しはキャンバスから出す

保存済みシーン（`board.scene`）ではなく、いま画面にあるものを出す。未保存の
描き足しが黙って落ちるのは、状態を見せて選ばせるという中核思想 3 に反する。

保存と**同じ直列化**（`serializeAsJSON(..., "local")`）を通す。書き出したファイルは
保存が送るバイト列そのものなので、ヘッダーに出ている大きさ（ADR 0038）が
そのままファイルの大きさになる。直列化の式は 1 箇所（`web/src/excalidraw/transfer.ts`
の `sceneJSON`）に置き、保存・大きさの計測・書き出しの 3 つが同じものを見る。

**未保存でも押させる。** 解釈は入力が 2 つ（テキストは保存済みシーン、画像は
キャンバス）あるので揃うまで押させない（ADR 0018）が、書き出しの入力は 1 つ
しかない。同じ制約を掛ける理由が無く、掛けると「揃えるべきものがあるから」では
なく「なんとなく揃えた制約」になる。

**viewer にも出す。** 見えているものを出すだけで、共有した相手にはすでに全部
見えている（ADR 0017）。

### 取り込みはキャンバスに載せるだけ。保存は人が押す

サーバーには何も送らない。**確定させるのは人間の保存操作だけ**という約束
（中核思想 3、ADR 0021）を、ここでも崩さない。

この形にすると、取り込んだシーンの検証・衝突検知・大きさの上限が**保存の経路の
まま効く**。取り込み専用の口をサーバーに足すと、`validateScene`（ADR 0038）と
版の照合（ADR 0020）を通る経路がもう 1 本増える。**バックエンドは変えない。**

置き換え先を新しいボードにはしない。新規ボードとして取り込む形は既存の内容を
消す道が無い代わりに、**バックアップからの復元でボードが増える。** 注釈の
element ID は同じでも `sync_runs` は元のボードに紐づいたままなので、復元した側は
すべて uncreated になり、そこから作り直すと GitHub に同じ draft issue が二重に
できる。既存ボードへ戻す形なら 3 状態も実行の履歴もそのまま噛み合う。

### 読めるかどうかの判定はライブラリに任せる

`loadFromBlob` を使い、読めなければキャンバスに触らない。**etoki が Excalidraw
のスキーマを判定しない。** 判定を書くと、ライブラリが読める形の集合を etoki 側に
複製することになり、ライブラリを上げた日にずれる。

**サーバーの `validateScene` と二重定義ではない。** 見ているものが違う。

| どこ     | 見るもの                      | 目的                                     |
| -------- | ----------------------------- | ---------------------------------------- |
| フロント | Excalidraw として復元できるか | 壊れたものをキャンバスに渡さない         |
| サーバー | JSON として読めるか、上限内か | 壊れたもの・大きすぎるものを保存させない |

**バイト数の上限はフロントに持たせない**（ADR 0018 / 0038）。大きいファイルは
キャンバスに載り、ヘッダーの大きさに出て、保存で 413 になる。既存の文言で
「貼った画像が大きすぎる」と案内できるので、ここに上限を複製する理由が無い。

### 取り込むのは要素と画像と背景色。表示状態は今の画面のものを保つ

スクロール位置・ズーム・選択中のツールは取り込まない。取り込んだ絵が画面の外に
あると押しても何も起きていないように見えるので、**置いた先へ寄せる**
（`scrollToContent`、ADR 0040 で図のドラフトに対して決めたのと同じ形）。

背景色（`viewBackgroundColor`）は取り込む。保存はこれを含めて書くので、自分の
ボードの書き出しを取り込み直したときに背景だけ変わるのは、往復で戻らない
ということになる。

### ライブラリの「開く」「名前を付けて保存…」は閉じる

`UIOptions.canvasActions` で外し、口を etoki のヘッダー 1 つにする。同じことを
する口を 2 つ並べると、片方だけが etoki のボード名と未保存の確認を知っている、
という不揃いが画面に残る。

閉じるのは 3 つ。**`.excalidraw` を書き出しているのは `saveAsImage` ではなく
`export` のほうで、日本語の表示が「名前を付けて保存...」になる。** 見た目で
選ぶと、隣の「画像のエクスポート...」と取り違える。

| キー               | メニューの表示      | 何をするか                     |
| ------------------ | ------------------- | ------------------------------ |
| `loadScene`        | 開く                | 読んでシーンを置き換える       |
| `export`           | 名前を付けて保存... | `.excalidraw` として書き出す   |
| `saveToActiveFile` | —                   | 上で開いたファイルへ上書き保存 |

`saveToActiveFile` はファイルを開いていないと出ないので、上の 2 つを閉じた時点で
出番が無い。それでも閉じるのは、**出る条件を作るのが上の 2 つだから**。片方だけ
残すと、開く手段を戻した日に書き出しだけが黙って復活する。

**画像のエクスポート（`saveAsImage`）は残す。** 答えている問いが違う（持ち出し
ではなく、絵を他所に貼ること）。

**閉じきれない経路が 1 つ残る。** `.excalidraw` をキャンバスにドロップすると
ライブラリがシーンを置き換える。これは `UIOptions` では止められない。**塞ぐために
`onDrop` を横取りしない。** 取り込みの入口を 2 つに増やして片方だけ etoki が
知っている形になるうえ、ドロップも `onChange` を通るので未保存にはなり、
サーバーへの反映は人が「保存」を押すまで起きない。**失われるのは確認だけで、
状態の見え方と確定の仕方は変わらない。**

## 結果

- ボードは 1 枚ずつ `.excalidraw` として持ち出せる。ファイル名はボード名から
  作る（`exportFileName`）。**安全のための門番ではない**（ブラウザも独自に
  均す）。目的は、書き出したファイルがどのボードのものか読めることだけ。
- **上限を超えて保存できなくなったボード**（#103）も持ち出せる。書き出しは
  キャンバスから出すだけで、保存の経路を通らない。
- 取り込みは既存ボードの中身を置き換える。未保存の変更があるときは確認を出す
  （ADR 0021 と同じ形）。**確認と置き換えのあいだに待ちを挟まない**ように、
  ファイルを読んでから訊く（`App.open` の「取ってから訊く」と同じ）。
- 取り込みは**キャンバスの編集**であって保存ではないので、引いた解釈は捨てない。
  捨てるのはこれまでどおり保存したときだけ。未保存になるので、解釈は保存するまで
  押せない（ADR 0018）。
- **他のボードから書き出したファイルを取り込むと、注釈の element ID が変わる。**
  元のボードの `sync_runs` はその ID を指したままなので、状態は uncreated から
  始まる。これは正しい状態なので特別扱いしない（#42）。取り残した draft issue は
  GitHub に残る（ADR 0026 と同じ扱いで、消す判断は etoki がしない）。
- 取り込みは editor 以上だけ。viewer に描かせないのと同じ理由で、保存できない
  人がキャンバスを置き換えても捨てるしかない（ADR 0017）。
- 作成中は取り込ませない。保存と作成を相互に排他する約束と揃える。
