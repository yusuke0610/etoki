# 0056: 操作どうしの排他は 1 つの表に集め、UI はそれを読むだけにする

ステータス: 採用

## 文脈

`BoardPage.tsx` は 1 か月で 389 行から 1,700 行に育った（#146）。育ったこと
自体より、**排他が 5 箇所に分かれていた**ことのほうが効いていた。

| 何を守っていたか       | 実体                                 |
| ---------------------- | ------------------------------------ |
| 取り込み ⇔ 作成        | `exclusiveOperation`（ref）          |
| 保存 ⇔ 取り込み ⇔ 作成 | `saving` / `importing`（state）      |
| 同上（作成の側）       | `creations` からの導出（`creating`） |
| 図を置く二重押し       | `placing`（ref）                     |
| 履歴の二重読み         | `loadingRuns`（ref の `Set`）        |

「押した時点の値を見るために ref」「表示のために state」という判断がコメントで
積み上がっていて、**どの操作とどの操作が排他かを知るにはファイル全体を読む**
ことになっていた。押せない理由の文言も、ヘッダー（`BoardPage`）と注釈パネル
（`CreationSection`）が同じ条件から別々に組み立てていた。

分かれていたぶん、**穴も分かれて残っていた。**

- 保存は `saving`（state）しか見ておらず、同じ tick の 2 回目が通る。
- 保存中の作成、作成中の保存は `disabled` だけで止めていた。`disabled` は
  表示の約束でしかない（`.claude/rules/async-ui.md`「押させない側は代わりに
  ならない」）。

## 決定

**`web/src/board/exclusion.ts` に表を 1 つ置き、判定も文言もそこから引く。**

- 排他の対象は `saving` / `importing` / `creating` の 3 つ。**互いに排他で、
  同じ操作の二重起動も弾く。** 門は ref で、表示は state。取るのも離すのも
  `useExclusion().run(op, f)` の 1 経路にする。
- **表の値は、そのまま画面に出す本文。** 判定と文言を別に持つと、止める条件
  だけ変えて文が古いまま残る。`disabled` の条件も表から導く。
- **「押せない理由を出さない」と「通す」を分ける。** 走っている操作と同じ
  操作（表の対角）は理由を出さない。ボタン自身が「保存中…」と名乗っている
  ので、隣に「保存が終わるまで保存できません」と出しても打ち手は増えない。
  **弾くこと自体は `useExclusion` が行う。**
- **同じ対象への二重押し（`placing` / `loadingRuns`）は表に入れない。**
  守っている対象が違う。あちらは*別の操作*の組、こちらは*同じ操作*の連打で、
  対象ごとに独立している（注釈 A の履歴を読んでいても B は読める）。ただし
  探す場所は 1 つにしたいので、同じファイルに `useReentryGuard` として置き、
  違いを doc コメントで名指しする。
- **表は単体テストで全マス固定する**（`exclusion.test.ts`）。1 マス書き換えたら
  落ちる。以前は E2E でしか気づけなかった。

### 走らない操作も表に並べる

作成先の変更（`changeTarget`）は `BoardPage` の中で進行中になることが無い
（選び直すとキャンバスごと外れる）。止められる側にしか現れないが、**押せない
理由を組む場所を 2 つに分けない**ために表へ並べた。いまも止めていない組
（取り込み中・作成中）は `null` を明示して置き、**止めていないことが読める形**
にしてある。

### 未保存は表に入れない

作成先の変更は「未保存だから押せない」も出す。これは進行中かどうかの話では
ないので、表の手前で見る。`blockingReasons`（下書きだけを見る純関数）に UI の
一時的な状態を混ぜないのと同じ切り分け。

### 採らなかった案

- **1 つの reducer にまとめる。** 排他だけでなく `creations` の注釈ごとの
  進み具合まで抱えることになる。あちらは表示のための状態で、寿命も単位も違う
  （注釈ごとに残り、排他はボード全体で 1 つ）。
- **`disabled` の条件をそのまま残し、文言だけ表に出す。** 止める条件と文言が
  別々に古くなる形が残る。実際に、保存中の保存だけが `disabled` にあって
  ロジックに無かった。
- **`placing` / `loadingRuns` も同じ表に入れる。** 「何が走っていたら何を
  止めるか」の表に、対象ごとに独立したものが混ざる。図を置いているあいだ
  保存を止める、という判断はしていないので、入れると表が嘘になる。

## 結果

- 排他の全体が 1 ファイルで読める。`BoardPage` が持つのは `exclusive.run(...)`
  の呼び出しと、表から引いた文言だけ。
- 塞がった穴が 3 つ。保存中の保存、保存中の作成、作成中の保存が、`disabled`
  ではなくロジックで止まる。**画面の見え方は変わらない**（`disabled` は
  これまでも止めていた）。
- 残した穴が 1 つ。**別の注釈を作成中でも、作成ボタンは押せる。** 押しても
  黙って弾かれる。理由を出すには押せないボタンが 1 つ増え、`a11y.spec.ts` にも
  1 行足すことになるので、出すかどうかは別に判断する。表の対角にコメントで
  残してある。
- 文言は 1 文字も動かしていない。句点の有無が揃っていないのも現状のままで、
  揃えるなら E2E の期待文言と同じコミットで動かす。
