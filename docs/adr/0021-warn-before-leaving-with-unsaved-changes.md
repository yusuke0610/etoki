# 0021: 未保存のまま離れる直前に確認を出す（自動保存も下書きも持たない）

ステータス: 採用

## 文脈

保存は明示操作である。自動同期・自動更新・自動作成を実装しないという中核思想
どおり、シーンも開発者が「保存」を押したときにだけ書く。

一方で、離脱を止める仕組みが何も無かった。`beforeunload` の登録もローカルへの
下書き保存も無いので、未保存のままリロード・タブを閉じる・戻るを踏むと描いた
ものが全部消える。画面には「未保存」バッジが出ているが、バッジは離脱を止めない。

ブレストは etoki の最初のフェーズなので、ここで失うと注釈・解釈・作成が全部
やり直しになる。

## 決定

**自動保存も、ローカルへの下書き保存も入れない。離脱の直前に確認を出す。**

- `dirty` のあいだだけ `beforeunload` を登録する。リロード・タブを閉じる・戻るは
  アプリ側で止められないので、ブラウザに確認させるしかない。
- キャンバスが外れる導線（ボードの切り替え、新しいボードの作成先選択、ログアウト）
  では `window.confirm` で確かめる。**確認は外す前に置く。** 外してから訊いても、
  そのときには消えている。
- 断られたら何もしない。承諾されたらそのまま捨てる。**確認の裏で保存しない。**
  捨てるつもりの試し描きまで残ると、保存が明示操作である意味が無くなる。

**自動で保存しないと決めた以上、失う直前に知らせる責任が対になる。** 明示保存は
「押し忘れが起きない」という前提の上に成り立っていない。押し忘れは構造的に起きる。

## 結果

未保存の内容が黙って消えることは無くなった。代わりに、離れるたびに確認が出る場面が
増える。出るのは `dirty` のあいだだけなので、保存してから離れる限り目に入らない。

`beforeunload` の文面はブラウザが決める。アプリから渡した文字列は表示されないので、
何を失うのかは `window.confirm` を出せる側（ボードの切り替え）でだけ説明できる。

「未保存かどうか」はキャンバスを持つ `BoardPage` が決め、離れる導線は `App` が
持っている。判断の材料を親に上げる形にしてあり、`App` から `dirty` を作り直しては
いない。作り直すと「未保存」の定義が 2 箇所になる。
