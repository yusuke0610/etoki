# 0097. 画面とサーバーの往復は、実物と偽の上流に繋いだ E2E で CI でも確かめる

- 状態: 採用
- 日付: 2026-11-09

## 背景

ブラウザ → Gin → ユースケース → SQLite / アダプタ → 上流、という並び全体を
自動で通すテストが無かった。

| 層                                      | 実 DB | 実ブラウザ | 自動で回るか |
| --------------------------------------- | ----- | ---------- | ------------ |
| Go の `internal/httpapi` / `etoki_test` | ○     | ×          | ○            |
| モックの E2E（ADR 0012）                | ×     | ○          | ○            |
| `make try-fake`（ADR 0050）             | ○     | 手で触る   | ×            |

ADR 0050 は「CI で回すかどうかは、手元の導線を使ってみてから別に決める」と保留して
いた。使ってみて、隙間に落ちるものの形が見えた（#422）。

- **サーバーの状態が動く流れ。** モックは書いた人が書き換えない限り状態が動かない。
  作成 → 作成済み → 変更あり → 更新の並びは、画面で通したことが無かった（#139）。
- **画面とサーバーの形のずれ。** モックの口は手書きで、型は契約から取れても、
  ブラウザが実際に送る本文を Go が読めるかは誰も見ていない（#354）。
- **ビルドした画面を etoki が配る構成でしか起きないこと**（#114）。モックの E2E は
  Vite の dev サーバーに対して走る。

`make try-fake` で見つかったもののうち、#289・#290・#294・#298 は人が画面を
読んで「分かりにくい」と判断したもので、自動のテストでは代われない。代われるのは
上の 3 つのような「本物どうしで噛み合っているか」だけ。

## 決定

### 実物のバイナリ・偽の上流・一時の SQLite に繋いだ E2E を数本、CI で PR ごとに回す

`make test-e2e-stack` が、ビルドした etoki と偽の GitHub / LLM を一時の DB で
立て、Playwright を走らせる。CI では `check` / `e2e` と並ぶ別の job にする。

**ADR 0012 は覆さない。** 画面の約束（失敗の見せ方、細かい状態の出し分け）は
これまでどおりモックの E2E で固める。モックのほうが状態を作りやすく、速い。
こちらで見るのは「画面とサーバーが本物どうしで往復できるか」だけで、本数を
増やす理由は無い。増やすと、ADR 0012 が避けた遅くて壊れやすいテストがそのまま
増える。

**ADR 0050 の「CI に入れない」はこの E2E について引き直す。** `make try-fake`
自体は手元の導線として残し、`make test` にも入れない。

### 画面はビルド成果物を etoki が配る形で通す

隙間の 3 つ目（#114）は本番の配り方でしか起きない。Vite の dev サーバーとプロキシ
で組めばビルドを待たずに済むが、その経路はモックの E2E がもう通っている。

### 起動の手順は `make try-fake` と 1 か所で持つ

本物の鍵を外す変数の一覧（ADR 0050）が 2 か所に分かれると、片方だけ外し忘れて
偽物へ本物の鍵を送る。手順は `scripts/fake-stack.sh` に置き、どちらも Makefile の
`fake-stack` を通す。

### 置き場所と設定をモックの E2E と分け、モックを持ち込ませない

`web/e2e-stack/` と `web/playwright.stack.config.ts` に置く。**1 つでもモックを
差すと、その口だけ本物を通らずに緑になり、どこが本物かは spec を読んでも
分からない。** 画面の操作のヘルパーは使い回すが、モックの口と `route` は
eslint が落とす。

### 自分で立てたものだけを検査する

既に何かが応答しているポートには立てない（#383 と同じ理由）。etoki は
「listening」をポートを掴む前にログへ出すので、その行を待っても自分が掴めたかは
分からない。Playwright は待ち終えたあとに起動したプロセスが落ちても気づかない。
そこで起動のスクリプトが「ポートが空いていた」「自分の 2 つがまだ生きている」を
確かめてから、準備できたと言う。

## 採らなかった案

- **定期実行だけにする。** PR は速いままだが、壊した PR を後から辿ることになる。
  本数が少ないので、別の job で並べれば待ちはビルドのぶんしか延びない（#269）。
- **`web/e2e/` の中で Playwright の project を分ける。** 設定が 1 つで済むが、
  モックと実物が同じディレクトリに並び、混ぜないことを規律で守ることになる。
- **Postgres などの DB サーバーを立てる基盤を持つ。** SQLite の一時ファイルで足り、
  Postgres の実装はスコープの外。
- **テスト用の基盤を、長く残す専用のブランチに置く。** 基盤が検査するコードと
  別の版で動き、古いコードを検査したまま緑になる。基盤は同じコミットで持つ。

## 結果

- 保存の往復（画像込み・2 回目の保存）、作成 → 変更あり → 更新、2 つのタブでの
  衝突、ビルドした画面が外へ出ないこと、が PR ごとに本物どうしで確かめられる。
- 認証ありの構成と図のドラフト生成は通さない（偽物ではログインできず、偽の LLM は
  解釈と同じ JSON しか返さない。ADR 0050）。
- **本物の GitHub と一致していることは、これでも確かめられない。** 偽物を本物に
  似せる線は ADR 0050 のまま、spec が要る口だけを足す。
- 偽の GitHub の記録は 1 回の実行のあいだ spec どうしで共有される。spec は
  ボードを自分で作り、記録は自分の書いた語で絞って読む。
