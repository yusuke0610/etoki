# 0007. マッピングは実行単位で履歴を残す

- ステータス: 採用
- 日付: 2026-07-30

## 文脈

当初案の `mappings` は `PRIMARY KEY (board_id, annotation_element_id)` に
`draft_node_id` を 1 カラム持つ形だった。しかし LLM は epic と issue の階層を
出力するため、**1 つの注釈から複数の draft issue が生まれる**。1 対 1 では
表現できない。

さらに、注釈を再実行したときの扱いが問題になる。

```text
1 回目: 注釈 X を実行 → epic e1 / issue i1, i2 を作成（3 件）
        ↓ ボードを編集 → 「変更あり」
2 回目: 注釈 X を再実行 → epic e1' / issue i1', i2', i3' を作成（4 件）
```

etoki は自動で何も消さないため、**GitHub 側には 1 回目の 3 件が残ったまま**に
なる。DB 側の持ち方には 3 案あった。

| 案 | 問題 |
| --- | --- |
| 追記のみ | `local_id` が衝突する。どれが最新か判別できない |
| 置き換え | 1 回目に作成した 3 件を追跡できなくなる。GitHub には残っているのに etoki は知らない状態になる |
| 実行単位で履歴を残す | — |

## 決定

`annotation_syncs` を `sync_runs` に置き換え、実行 1 回を 1 レコードとする。
`sync_items` は `run_id` に紐づく。テーブル数は 3 のまま変わらない。

3 状態判定は「その注釈の**最新 run** の `content_hash`」と現在のハッシュを
比較する。

**最新 run は `created_at` ではなく `id` で決める。** 時刻は呼び出し側が
与える設計にしており、同一時刻の run がありうるため `created_at` だけでは
順序が定まらない。`AUTOINCREMENT` の `id` は単調増加するので一意に定まる。

`SaveRun` は run と items を 1 トランザクションで保存する。部分的に書き込まれた
run が残ると、3 状態判定が「作成済み」と誤答してしまうため。

## 結果

- 「前回この注釈から何を作ったか」を開発者に見せられる。自動で判断せず状態を
  見せて選ばせる、という方針が再実行のケースでも成立する。
- 最新 run を取るのに `ORDER BY id DESC LIMIT 1` が必要になる。単純な主キー
  参照より一手間増える。
- run は増え続ける。単一ユーザーのローカルツールである以上、当面は問題に
  ならないと判断した。肥大化が問題になったら古い run の削除を別途足す。
- **どの draft issue が GitHub 上でまだ有効かは etoki には分からない。** 記録は
  「etoki が作成した」という事実だけであり、その後 GitHub 側で削除・変更された
  かどうかは追跡しない。逆方向同期を実装しない方針の帰結である。
