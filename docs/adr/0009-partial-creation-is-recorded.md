# 0009. 途中まで作れた run も記録する

- ステータス: 採用
- 日付: 2026-08-04

## 文脈

1 つの注釈から draft issue を作る処理は、GitHub への複数回の呼び出しになる。
epic を作り、issue を作り、それぞれに種別と親のカスタムフィールドを設定する。
どこかで失敗しうる。

ここで 2 つの性質がぶつかる。

- **GitHub 側に作られた draft issue は削除しない。** 削除を実装すると、開発者が
  手で編集したものまで消しかねない。etoki は作るだけで消さない。
- **`SaveRun` は 1 トランザクション。** run と items はまとめて保存される
  （ADR 0007）。

つまり途中で失敗したとき、GitHub には draft issue が残るのに、記録が残らない
という状態がありうる。**etoki からは存在を知りようがない draft issue** が生まれる。

## 決定

**作れたところまでを run として記録し、そのうえで失敗を返す。**

- 1 件でも作れていれば `SaveRun` する。
- 1 件も作れていないなら記録しない。空の run を残すと状態が `created` に変わり、
  何も無いのに「作成済み」と表示されてしまう。
- 記録そのものに失敗した場合は、作成済みの item ID をエラーに載せる。ここが
  最も追跡困難な状態なので、手で追える情報だけは残す。

記録漏れと余分な記録を比べると、**記録漏れのほうが取り返しがつかない。** 余分な
記録は開発者が run の中身を見れば分かるが、記録されていない draft issue は
etoki からは存在しないのと同じで、GitHub を直接見に行くしかなくなる。ADR 0007 で
「過去の run を消さない」と決めたのと同じ理由による。

## 結果

- 途中失敗のあと、状態は `created` になる。実際には一部しか作られていない。
  UI は run の中身を見せるので、開発者はそこで気づける。
- **再実行すると重複が生まれる。** 作成済みのぶんも作り直されるため、GitHub 側に
  同じタイトルの draft issue が並ぶ。etoki は自動で判断しないので、消すか残すかは
  開発者が決める（中核思想 3）。差分だけを作り直す機能は、必要になってから
  検討する。
- エラーは「途中まで作れた」と分かる形で返す必要がある。単なる失敗として扱うと、
  開発者は何も作られていないと誤解して再実行し、重複を増やす。
