# 0068. ボード一覧で注釈の 3 状態の件数を返し、シーンは 1 枚ずつ読む

- 状態: 採用
- 日付: 2026-09-30

## 背景

ボード一覧はボード名と作成先しか返していなかった（ADR 0019）。どのボードに
「未作成」や「変更あり」が残っているかは、開くまで分からない。状態を見せて
開発者に選ばせる（中核思想 3）なら、開く前の一覧でも見えているほうがよい
（#62 のアートボード「ボード一覧」、#200）。

3 状態は保存済みシーンと最新の run から決まる（`internal/CLAUDE.md` の
「3 状態判定のデータフロー」）。**一覧はシーンを読んでいない。** シーンには画像が
base64 で入りうる（上限は ADR 0038）ので、一覧の問い合わせ
（`BoardRepository.List`）はわざと読まない形にしてある。件数を出すには、この
前提のどこかを崩す必要がある。

## 決定

**一覧を返すたびに、ボードごとにシーンを読んで数える。**

- **シーンは 1 枚ずつ読み、数えたら手放す。** 一覧の問い合わせはシーンを読まない
  まま残し、数えるときに 1 枚ずつ引く。同時にメモリへ載るのは 1 枚までになる。
  **読む量そのものは減らない。** ボードの数だけシーンを読み、run を引く。
- **判定は注釈の状態の一覧と同じ関数を通す**（`usecase` の `judgeAnnotations`）。
  別に書くと、同じ注釈がパネルと一覧で違う状態に見えうる。
- **件数は一覧の要素（`BoardListEntry`）にだけ載せる。** `BoardSummary` に置くと、
  それを取り込む `BoardDetail` を返すすべての応答で数えることになる。開いた
  ボードの状態は注釈の一覧が持っている。
- **1 枚のシーンが読めなくても一覧は返す。** そのボードの件数だけを `null` に
  する。1 枚が壊れているだけで、ほかのボードまで開けなくなるのを避ける。run を
  引けないのは DB の失敗なので、そちらは一覧ごと失敗にする。
- **キャンバスから消えた注釈は数えない。** 3 状態を持たない（ADR 0046）。

## 帰結

- 一覧の応答が、ボードの数とシーンの大きさに比例して遅くなる。単一ユーザーの
  ローカルツール（ADR 0004）で並ぶボードの数なら効かないと見ている。
- **遅くなったら、下の「保存時に件数を控える」を比べ直す。** そのときは、判定の
  入力を変えたときに控えを作り直す手段まで用意してから移る。
- 一覧の件数は保存済みシーンが基準なので、開いているボードの未保存の変更は
  反映されない。注釈のパネルと同じ扱い。

## 採らなかった案

- **保存時に件数を `boards` に控える。** 一覧は軽いままで済むが、件数が変わる
  のはシーンの保存と run の記録で、別々のユースケースにある。どちらかで書き
  忘れると、控えと実際がずれたまま一覧に出る。**判定の入力を変えたときは、
  書き直す経路がそもそも無い。** ADR 0047 で種別を足したときのように、コードの
  変更だけで全ボードの状態が一斉に変わる。
- **件数を出さず、更新時刻だけにする。** 何も崩さずに済むが、状態がボードを
  開くまで見えない。
- **一覧を返したあと、ボードごとの件数を別の API で取りにいく。** 一覧は速く
  出るが、問い合わせがボードの数だけ増え、読む量は変わらない。
