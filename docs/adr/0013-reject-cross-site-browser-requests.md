# 0013: ブラウザ由来の cross-site リクエストを Host と Origin で弾く

ステータス: 採用

## 文脈

ADR 0004 で、認証・認可を実装せず `127.0.0.1` へのバインドだけを防御とすると
決めた。そこでは「複数人で共有サーバーを立てたら壊れるもの」を列挙したが、
**ローカル起動のままでも成立する経路**を見落としていた。

実物のルーターで確認した事実は 2 つ。

- **クロスサイトからの POST が通る。** `Content-Type: text/plain` は CORS の
  simple request なのでプリフライトが起きず、ブラウザは etoki が CORS ヘッダを
  返さなくてもリクエストを送る。そして `c.ShouldBindJSON` は `binding.JSON` を
  明示的に使うため Content-Type を検査せず、本文を JSON として読む。実測で
  `application/json` / `text/plain` / ヘッダ無しのすべてが `201` を返した。
  レスポンスは CORS で読めないが、副作用はすでに起きている。
- **Host ヘッダを見ていない。** 攻撃者のドメインを短い TTL で `127.0.0.1` に
  向け直すと、ページと etoki が同一オリジンになる。CORS の制約が一切かからず、
  レスポンスの読み取りまでできる。

実害が大きいのは `POST /api/boards/{id}/annotations/{aid}/items` で、GitHub に
draft issue を勝手に作れる。etoki は作成したものを削除しないため取り消せない
（ADR 0007 / 0009）。

## 決定

認証は導入しない。ADR 0004 の「単一ユーザーのローカルツール」という前提は
維持する。代わりに `internal/httpapi` にミドルウェアを 1 つ置き、
**ブラウザ由来の cross-site リクエストだけを弾く。**

- **`Host` がループバックを指さなければ弾く。** DNS リバインディングを塞ぐ。
  読み取りが目的なので GET にも適用する。
- **`Origin` があり、それがループバック由来でなければ弾く。** CSRF を塞ぐ。
- **`Origin` が無いリクエストは通す。** ブラウザは cross-origin の POST に必ず
  `Origin` を付ける一方、curl やスクリプトは付けない。攻撃者のページから
  `Origin` を省略・偽装することはできないので、この非対称性は安全側に働く。
  ここを塞いでも守れるものは増えず、CLI からの利用だけが壊れる。
- 弾いたら `403` を返し、`WARN` で記録する。何を許すかは応答に載せない。

**ポートは見ない。** `make dev` では Vite の dev サーバー(:5173)がプロキシする
際に `Host` と `Origin` を書き換えずに転送するため、サーバーには `:8080` では
なく `:5173` が届く（実測）。リッスンポートに絞ると開発時に落ちる。ポートを
問わないことで別のローカルアプリからも叩けるようになるが、利用者の端末で任意の
サーバーを立てられる相手には、そもそもこの防御が意味を持たない。

`ETOKI_ADDR` は利用者が上書きできる。ループバック以外にバインドしたときに
自分で自分を締め出さないよう、`ETOKI_ALLOWED_ORIGINS` で追加のオリジンを
指定できるようにする。オリジンから `host[:port]` を導いて `Host` の許可にも
使う。2 つの環境変数に書き分けさせると、片方だけ足して 403 のままになる。

`/healthz` も同じ扱いにする。守る情報は無いが、経路ごとに規則が変えると
「ここは素通し」が増えていく。

### 採らなかった案

| 案 | 理由 |
| --- | --- |
| 認証を導入する | ADR 0004 の前提を覆す。設計判断そのものを変える話で、この問題の対処としては過剰 |
| `Content-Type` を `application/json` に強制する | プリフライトを起こさせる形にはなるが、CORS ヘッダを返さないというブラウザ側の挙動に依存した間接的な防御。併用はできるが主たる対策にはしない |
| CSRF トークンを発行する | 状態を持つことになる。`Origin` で足りる |

## 結果

- 許可していないオリジンのページから、状態を変える API を叩けなくなった。
  読み取りだけの `Origin` 無し GET には隙が残る（後述）。
- **curl やスクリプトからの利用は変わらない。** `Origin` を送らないため。
- ループバック以外にバインドする場合、`ETOKI_ALLOWED_ORIGINS` を設定しないと
  自分のブラウザからも 403 になる。バインド先を広げる行為が明示的な設定を
  もう 1 つ要求するようになった、と読むべき変更。
- `httptest.NewRequest` の既定の Host は `example.com` なので、ハンドラの
  テストは Host を明示する必要がある。実際に届く形と揃っていない状態で
  緑になっていたのを、ここで正した。
- ADR 0004 の前提（単一ユーザー・ローカル）は変わっていない。共有サーバーに
  する場合に潰すべきものの一覧も、そのまま有効。

### 残る隙

**外部サイトのページは、`Origin` の付かない GET を投げられる。** `<img>` や
`<script>` によるサブリソース読み込みには `Origin` が付かないため、Host の
検証しか効かない。ただし、

- etoki の GET はすべて副作用を持たない。
- レスポンスは CORS で読めない（etoki は CORS ヘッダを返さない）。

ので、攻撃者が得られるのは「etoki が起動しているらしい」という程度の情報に
とどまる。GET でも `Origin` を必須にすればここも塞げるが、その場合ブラウザの
アドレスバーから `/healthz` を開くことすらできなくなる。割に合わないと判断した。

**GET に副作用を持つエンドポイントを足すなら、この判断は成り立たなくなる。**
その時点でこの ADR を見直すこと。
