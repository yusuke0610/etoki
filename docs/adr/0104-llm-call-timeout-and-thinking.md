# 0104: LLM を待つ上限は設定にして呼び出しごとに掛け、思考は手元でだけ切らせる

ステータス: 採用

## 文脈

README のとおり Ollama に直結した解釈が、手元によくある機械（Apple M1 / 16GB、
`qwen3-vl:8b`）で 1 件も結果を出さなかった（#430）。

- コンテキスト長 4096 では、思考だけで出力を使い切って打ち切られた。Ollama は
  思考に対応したモデルでは頼まなくても思考する。etoki は `thinking` を送らない
  （claude-opus-5 は明示的に切ると本文にタグが混ざることがあるため）ので、
  思考を止める手段が無い。
- 16384 に広げると、1 回の呼び出しの上限（5 分）に当たって切れた。上限は
  アダプタの HTTP クライアントに定数で持っていて、設定では変えられなかった。

あわせて、ジョブの上限（10 分、ADR 0085）は 1 回の上限の 2 回ぶんしか無かった。
解釈は 3 回まで呼ぶので、遅い応答が続くと、3 回目は 1 回の上限より先にジョブの
上限で切れる。

## 決定

### 1 回の呼び出しを待つ上限を設定にし、ユースケースが呼び出しごとに掛ける

`ETOKI_LLM_TIMEOUT`（既定 5 分）を足す。上限は再送の手順（`llmRetry`）が
呼び出しごとに `ctx` で掛ける。

- **アダプタに持たせない。** `LLMClient` は差し替えられる（ADR 0005 / 0008）ので、
  アダプタの上限は差し込んだ実装では効かない。アダプタの固定の 5 分は外した。
  残すと、設定で延ばしてもそちらが先に切る。
- **実行全体ではなく、呼び出しごとに掛ける。** 実行全体に掛けると、1 回ずつは
  上限に収まる遅い応答が、再送を重ねたところで切れる。
- 上限に当たったら、その値を失敗の詳細に足す。待ちきれなかったのか向こうが
  断ったのかを見分け、どれだけ延ばせばよいかを読めるようにする。**画面の code と
  文言は変えない**（`llm_unavailable` のまま。分けるかは #444 で決める）。

### ジョブの上限は「1 回の上限 × 呼ぶ回数」から導く

解釈は 3 回、図のドラフト生成は 2 回まで呼ぶので、既定ではジョブの上限が
15 分と 10 分になる。1 回の上限を延ばせば、ジョブの上限も同じ比で延びる。

ジョブの上限を置いた理由（応えない LLM に枠を握らせ続けない、ADR 0085）は
変わらない。応えない LLM は 1 回の上限で切れ、呼び出しの失敗は再送しないので、
**応えない相手に枠を握らせる長さは 1 回の上限のまま**。ジョブの上限は、それでも
止まらないものに対する歯止めとして残す。

### 思考を切る設定を、手元の LLM 向けに置く

`ETOKI_LLM_THINKING=disabled` を設定すると `thinking: {"type": "disabled"}` を送る。
**既定はこれまでどおり送らない。** Ollama の Anthropic 互換の口は、これを思考を
切る指示として受ける（Ollama の文書。切れないモデルはいちばん低い段階で思考する）。

- **接続先が Anthropic（`api.anthropic.com`）なら起動時に断る。** 送らない理由は
  そちらにある。断れるのはホスト名で分かる範囲までで、Anthropic へ転送する
  プロキシは見分けられない。
- **受ける値は `disabled` だけ。** 知らない値は起動時に断る。読めない値を既定に
  倒すと、切ったつもりの思考が黙って残る。

## 採らなかった案

- **ストリーミングで受け、「最初の応答まで」と「全体」の上限を分ける。** 応えない
  相手と遅い相手を見分けられるが、アダプタの読み方と失敗の写し方を書き換える
  ことになる。いま足りないのは延ばす手段で、解釈はジョブなのでリクエストは
  待たせていない（ADR 0085）。延ばしても足りないと分かってから決める。
- **上限をアダプタに残し、設定で変えられるようにする。** 差し込んだ実装では
  効かない（上記）。
- **1 回の上限だけを設定にし、ジョブの上限は据え置く。** 延ばした分だけ、最後の
  呼び出しがジョブの上限で切れる。
- **思考を既定で切る。** 既定を変える判断は別に要る。Anthropic の接続先では
  切れない理由もある。
- **`enabled` などほかの値も受ける。** 要るのは切ることだけで、思考させたいなら
  モデルの既定のままで足りる。
- **README に勧めるモデルと所要時間を書く。** 実物で測ってから足す。書くのは
  設定の仕方と、確かめた事実（#430 の現象）まで。

## 結果

- 既定の 1 回の上限（5 分）と、思考を送らないことは変わらない。変わるのは
  ジョブの上限（解釈 10 分 → 15 分）で、ADR 0085 の「既定 10 分」を改めた。
- 差し込んだ `LLMClient` も `ctx` で上限を受ける。自前の上限（HTTP クライアントの
  `Timeout` など）を持っていれば、短いほうで切れる。既定のアダプタに
  `HTTPClient` を差す構成も同じ。
- 公開の組み立て口に `Options.LLMCallTimeout` が増えた（ADR 0001）。0 は既定、
  負の値は `etoki.New` が落とす。
