# 0086: LLM の呼び出しの失敗は、打ち手ごとに code を分ける

ステータス: 採用

## 文脈

解釈と図のドラフト生成で LLM の呼び出しが失敗すると、原因にかかわらず
`llm_unavailable` になっていた（#291）。画面は「API キーと接続を確かめて
ください」と出す。次のどれもこの文になる。

- 応答が出力の上限で打ち切られた（`stop_reason` が `max_tokens`）。ローカル
  LLM の既定のコンテキスト長で起きる（#252）。
- モデルが応答を拒んだ（`refusal`）。
- 上流が混んでいるか、向こう側でエラーになった（429・5xx・Anthropic の 529）。

どれも API キーとは関係が無く、打ち手が違う（コンテキスト長を広げる、頼み方を
変える、待つ）。#256 で詳細とログでは見分けられるようになったが、手掛かりが
英文の詳細にしか無いので、導入した人はまず鍵を疑って遠回りする。**ADR 0034 が
code を分けた理由（ステータスだけでは打ち手が決まらない）が、ここでは効いて
いなかった。**

原因が分かるのはアダプタだけで、ユースケース層は `port.LLMClient` の返す
`error` しか見ない。

## 決定

### 打ち手の違う 3 つに code を分ける

| 原因                       | code              | ステータス |
| -------------------------- | ----------------- | ---------- |
| 出力の上限で打ち切られた   | `llm_truncated`   | 502        |
| モデルが拒んだ             | `llm_refused`     | 502        |
| 上流が混んでいる・5xx      | `llm_overloaded`  | 502        |
| それ以外（認証・接続など） | `llm_unavailable` | 502        |

**分ける基準は原因ではなく打ち手。** 5xx を「混雑」と同じ code にしたのは、
向こう側のエラーも混雑も、こちらでできるのは時間をおくことだけだから。401 /
403 / 400 は分けない。鍵・権限・リクエストの形の話で、打ち手は設定の側にあり、
いまの `llm_unavailable` の文がそのまま当たる。

### 原因は port の sentinel で名乗る

`port` に `ErrLLMTruncated` / `ErrLLMRefused` / `ErrLLMOverloaded` を足し、
既定の実装（`internal/adapter/llm`）がそれを名乗る。ユースケース層は自分の
sentinel に写し替えて返し、httpapi の表が code に写す。

**写し替えでは sentinel を入れ子にしない。** port の sentinel まで `errors.Is`
で辿れると、`ErrLLMUnavailable` と新しい sentinel が同時に真になりうる形が残り、
httpapi の表が「入れ子にならない」前提で 1 つに決めている写し先が、並び順しだいに
なる。port のエラーは文言だけ残す。

**解釈と図の生成は同じ写し替えを通す。** 片方だけ写すと、同じ打ち切りが経路に
よって別の code になる。

### 外部の実装は名乗らなくてよい

`LLMClient` を自前で実装する外部リポジトリ（ADR 0005 / 0008）は、新しい
sentinel を返さなくてよい。**返さなければ、いままでどおり `llm_unavailable` に
落ちる。** 動かなくなるものは無く、画面の案内が原因に合わせて変わらないだけ。
`port.Usage` を埋めるかどうかを任意にしたのと同じで、差し込む側の負担を
増やさない（ADR 0031）。

### 上流の混雑を `rate_limited` に畳まない

上流の 429 は `rate_limited` / `concurrency_limited`（ADR 0044）とは別の code で、
ステータスも 429 にしない。**どれも待つ話だが、相手が違う。** あちらは etoki
自身が置いた上限で、待つ長さは etoki の設定で決まり、続くなら etoki の設定を
見直す。こちらは向こうが断ったもので、続くなら向こうの状態か契約を見る。畳むと
画面はどちらとも言えない文しか出せない。429 にしないのは、etoki に対する要求が
多すぎたわけではないため。

### 再送の判断は変えない

打ち切り・拒否・混雑のどれでも、ユースケース層は投げ直さない。打ち切りと拒否は
同じ入力で同じ結果になる。上流の混雑に待って投げ直す仕組みも今回は足さない。
待つかどうかは開発者が決める（中核思想 3）。

## 採らなかった案

- **`llm_unavailable` の文を鍵と接続に決めつけない書き方にするだけ。** code は
  増えないが、打ち手を言えなくなる。原因が分かっているのに画面が言えない状態を
  文言で覆うことになる。受け皿としての `llm_unavailable` の文は、この案に沿って
  広げた（「API キー・接続先・モデルなどの設定」）。
- **打ち切りの中でさらに分ける**（向こうのコンテキスト長か、etoki の上限か）。
  応答からは決まらない場合があり（ADR 0031 の「0 は報告なし」）、決まっても
  画面の打ち手は「広げる」で同じ。誰が切ったかはアダプタが詳細に残している。

## 結果

- 画面は打ち切り・拒否・混雑で別の打ち手を出せる。文言は `errorMessage.ts` が
  持つ（ADR 0034）。図の生成でも同じ code が返るので、文は「解釈」と言い切らない。
- **`port/` の公開 API が 3 つ増えた**（ADR 0001）。sentinel の名前と意味は
  外部実装との約束になり、変えると破壊的変更になる。増やすのは打ち手が違う原因が
  出てきたときだけにする。
- 記録の出し分けは変えない。4 つとも呼び出しそのものの失敗として、これまでの
  `llm_unavailable` と同じ扱いでログに残す。分けたのは画面の打ち手であって、
  障害として記録すべきかどうかは変わっていない。
- 名乗らない失敗は元のエラーを包んだまま `ErrLLMUnavailable` に落ちる。待って
  いた相手がいなくなった（`context.Canceled`）ことを httpapi が辿れるのは
  こちらの経路だけで、新しい 3 つには取り消しが混ざらない。
- 5xx のうち、間に置いたプロキシが向こうに繋がらずに返す 502 / 503 も
  `llm_overloaded` になる。応答からは区別できないので、文言は「続くなら接続先を
  確かめる」まで言う。
