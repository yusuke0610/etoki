# 0031: LLM の呼び出し実績はログに残す（port は任意の口で受ける）

ステータス: 採用

## 文脈

**どれだけ LLM を使ったかが、どこにも残っていなかった。**

- `internal/adapter/llm/anthropic.go` の `apiResponse` は `content` /
  `stop_reason` / `stop_details` しか読まず、Messages API が返す `usage` を
  捨てていた
- 1 回の解釈は再送を含めて最大 `maxAttempts`（既定 3）回 LLM を呼ぶが、
  何回呼んだかは呼び出し側に返らない。失敗したときのエラー文字列
  （`(%d attempts)`）にしか出ない
- リクエストログが持つのは method / path / status / took / user だけ

つまり**成功した解釈については、呼んだ痕跡が took 以外に何も無い**。

これが塞がっていないと困るのは 3 つ。

- **解釈の実行に上限を設ける（#45）とき、上限を何にするかを決める材料が無い。**
  勘で決めることになる
- 解釈には注釈範囲の画像が乗る（最大 4 MiB の PNG、ADR 0018）。**入力トークンは
  注釈の大きさで桁が変わる**のに実測が無い
- スキーマ違反による再送はそのぶん課金される。何回に 1 回再送しているかが
  分からないので、`interpretationSystemPrompt` を直す判断ができない

## 決定

**トークン数を `port.VisionResponse` で受け取り、解釈 1 回ぶんに積んでログに
残す。保存はしない。**

### port は変える。ただし「埋めなくてよい」形にする

`port.VisionResponse` に `Usage`（`InputTokens` / `OutputTokens`）を足す。

**インターフェースのシグネチャは変えない。** `LLMClient` を自前実装する外部
リポジトリ（ADR 0001 / 0008）は、`Usage` を埋めなくてもコンパイルも動作も
通る。トークン数の名前も数え方も基盤ごとに違い、そもそも返さない基盤もある
ので、**必須にすると差し替えの負担がそのぶん増える。**

port を変えない案（アダプタの中で `slog` に出すだけ）も採れた。いちばん安く
外に影響も出ないが、**「何回呼んだか」はユースケース層にしか無い**ので、
集計するときに 2 つのログを時刻で突き合わせることになる。いちばん見たいのは
「1 回の解釈にいくら払ったか」なので、そこが 1 行で読めない形は選ばなかった。

**0 は「使っていない」ではなく「報告が無い」と読む。** 実際に 0 トークンで
返る呼び出しは無いので、実測として区別する必要が無い。

ADR 0005 の「`LLMClient` は 1 回の呼び出しだけを担う」は崩していない。
`Usage` は**その 1 回の応答に付随する事実**であって、再送ループの責務ではない。

### 積むのは解釈 1 回ぶん

1 回の解釈は最大 `maxAttempts` 回 LLM を呼ぶので、**呼び出し 1 回ぶんだけを
見ても払った量にならない。** `InterpretationService.complete` が積んで返し、
`Interpret` が 1 行で残す。

- **呼んだ回数は呼ぶ前に数える。** 接続が落ちた回も「呼んだ」に含めないと、
  上限に対して実際に何回叩いているのかが読めない
- **失敗しても残す。** 再送して直らなかったぶんも課金されている。成功した
  ときだけ記録すると、実績が実際より小さく見える。成否は `ok` で載せる。
  載せないと、払った量のうちどれだけが無駄だったのかが読めない
- **LLM を呼ぶ前に弾いた入力では出さない**（画像の上限違反など、ADR 0018）。
  払っていないため

**打ち切り（`max_tokens`）と refusal のぶんは取りこぼす。** アダプタがそれらを
エラーとして返し、返り値の `VisionResponse` を捨てるため。拾おうとすると
「エラーでも中身を読め」という約束が port に増える。**自前実装する側の負担を
増やさない方を採った。** 頻度が高いのは再送（HTTP 200 で返るので拾えている）
のほうで、そちらは取れている。

### 保存はしない。ログだけにする

表を作れば画面に出せるが、**そのとき「誰の実績か」を決める必要がある。** それは
実行の上限をどう絞るか（ボード単位 / 利用者単位、#45）と揃えて決める問いなので、
先に片方だけ決めない。

上限を決める材料を取ることが目的なので、ログで足りる。

### 金額は持たない

**トークン数まで。円やドルにしない。** モデルごとの単価は外の世界の値なので、
etoki が抱えるとモデルを差し替えるたびに古くなる。ADR 0019 で `projectNumber` を
表示用のスナップショットに留めたのと同じ判断。

### キャッシュ関連のトークンは読まない

`cache_creation_input_tokens` / `cache_read_input_tokens` は読まない。
`cache_control` を送っていないので常に 0 になる。送るようにしたときは、
`input_tokens` がキャッシュぶんを含まないことを踏まえて足し直す必要がある。

### プロンプトそのものは残さない

何を送ったかまで残すと、**ボードの中身の複製が増える。** 解釈の前に何を渡すかを
見せる話（#68）とは別で、こちらは事後の実績。混ぜない。

## 結果

`interpretation llm usage` の 1 行に、ボード / 注釈 / 呼んだ回数 / 入力・出力
トークン / 成否が出る。#45 はこれを見てから上限を決められる。

**画面には出ない。** 実績を見られるのはサーバーのログを読める人だけで、
招待された利用者は自分がどれだけ使ったかを見られない。中核思想 3（状態を
見せる）に照らすと途中までである。出すには保存が要り、そのとき誰の実績かを
決めることになる。

**`Usage` を埋めない `LLMClient` 実装では、トークンが 0 のまま出る。** 回数と
成否は残るので、上限の材料が完全に消えるわけではない。
