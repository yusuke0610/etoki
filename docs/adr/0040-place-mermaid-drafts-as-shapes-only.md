# 0040: mermaid のドラフトは手で直せる図形のときだけ置く

ステータス: 採用

## 文脈

プロンプトから生成した図のドラフトをキャンバスに置く（#58 / #60）。LLM に
出させるのは mermaid で、Excalidraw の要素への変換は
`@excalidraw/mermaid-to-excalidraw` に任せる。**変換は mermaid → Excalidraw の
一方向で、逆は無い。**

この変換器は、知らない記法を渡されると**失敗しない。** mermaid に SVG を
描かせ、それを base64 のデータ URL に畳んで**画像 1 枚**として返す
（`convertSvgToGraphImage`）。いまの版（2.2.2）で要素に分解する経路を持って
いるのは flowchart / sequence / class / er / state だけで、それ以外はすべて
この落とし方になる。

つまり、**呼び出す側が何もしなければ、置けたか置けなかったかの区別が付かない。**
図に見えるものは返ってくる。

## 決定

### 画像 1 枚で返ってきたら置かない

この機能の値打ちは「白紙から描き始めなくてよい」ことではなく、**直すところから
始められる**ことにある（#58）。画像は動かせても直せない。ノードの言葉を 1 つ
変えるにも描き直しになるので、叩き台として成立しない。

置かない代わりに、変換が失敗したこととして返す。**図に見えて直せないものを
黙って置くほうが、置けなかったと言うより悪い。** キャンバスに残ったものが手描き
なのか生成物なのかも、置いたあとでは見分けが付かなくなる。

副次的に、シーンに base64 のデータ URL が載らない。保存の上限（ADR 0038）に
近づく経路が生成物側から生えないのは、フロントが上限を知らないまま
（`web/CLAUDE.md`）でいられる条件でもある。

### frame が返ってきても置かない

いまの変換器は frame を返さない。それでも門番を置くのは、返すようになった
ときに**注釈にできる frame を etoki が配ったことになる**ため。注釈の frame は
人がフレームツールで作る、という線（ルートの `CLAUDE.md`）が、依存の更新で
黙って崩れる。

置かずに止めれば、崩れたときに機能が動かなくなる形で気づける。テストは
「今日は返さないこと」と「返ってきたら止めること」を両方固定してある。片方だけ
だと、門番が本当に効くのか、門番が要るのかのどちらかが確かめられない。

### 失敗は例外ではなく値で返し、理由を 2 つに分ける

読めなかったのは etoki の不具合ではなく LLM の出力なので、**呼び出し側が次の
一手を決められる必要がある。**

| 理由          | 何が起きたか                 | 次の一手                        |
| ------------- | ---------------------------- | ------------------------------- |
| `syntax`      | mermaid として読めなかった   | 同じ種類のまま生成し直す（#59） |
| `unsupported` | 読めたが、置けない形で返った | **再送しない。** 種類を変える   |

1 つに畳むと、投げ直しても同じ結果にしかならない失敗に対して呼び出しを
繰り返すことになる。**課金を伴う呼び出しなので、繰り返しても直らないものは
繰り返さない**（#59 の上限と同じ考え）。

### 置き場所は既存の絵の右外。付箋とは逆にする

付箋は**見えている範囲の中央**に置く（`stickyNotePosition`）。ドラフトは
**既存の絵をすべて含む矩形の右外**に置く。判断が逆なのは、操作の性質が違うため。

- 付箋は描いている最中の 1 手で、手数の少なさがそのまま値打ちになる。視界の外に
  出すと「押しても何も出ない」ように見える。
- ドラフトは**見てから置く**操作で、置いた先へ寄せる間がある。そして図 1 枚ぶんの
  大きさがあるので、重なったときに巻き込む範囲が付箋 1 枚とは違う。

**重ねないことのほうを優先する。** 重ねると、生成物と手描きの区別が付かなく
なり、気に入らないドラフトを選び分けて消せない（#58 の「既存の絵には触らない」
は、要素を書き換えないだけでなく、見分けが付く状態で残すところまでを含む）。

視界の外に出ることは織り込みで、置いたあとにその範囲へ寄せる
（`scrollToContent`）。寄せるのは呼び出し側の責務にしてある。純関数の側に
キャンバスを触らせないのは、置くかどうかを人が決める形（中核思想 3）を
変換の都合で崩さないため。

## 結果

- **#52 の 5 種のうち、mindmap と architecture はいまの版ではドラフトにできない。**
  変換器が要素に分解しないので、必ず画像に落ちて拒まれる。逃げ道は #59 の
  プロンプト側にあり、mindmap を **flowchart の記法で書かせる**（`flowchart LR`
  の木）と要素として置ける。**「mermaid で書けること」と「Excalidraw の要素に
  なること」は別**であり、種類の語彙を決めるときに効くのは後者。上の判断は
  変換器が何を分解できるかに依らないので、対応が増えたら**拒まれる種類が
  減るだけ**で、決定は変わらない。
- 変換そのものは差し替え可能にしてあるが（`MermaidParser`）、これは
  **jsdom で本物を確かめられない**ため。mermaid は SVG の実寸を測って図を
  組み立てるので、jsdom では図の種類によって本物と違う経路を通る。単体テストが
  固定するのは「返ってきた形をどう扱うか」までで、**種類ごとの結果はブラウザ
  （#61 の E2E）でしか確かめられない。**
- 依存のバージョンが 1 つ増えた。`@excalidraw/excalidraw` が内部で使っている
  ものと同じ版に固定する。理由と手順は `web/CLAUDE.md`。
