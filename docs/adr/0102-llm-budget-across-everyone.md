# 0102: LLM の費用の上限は全員の合計で持ち、日ごとの合計を DB に積む

ステータス: 採用

## 文脈

LLM を叩く実行の上限は、利用者ごとの同時実行と回数だけだった（ADR 0044）。数えは
プロセスのメモリにあり、全員の合計を縛るものは無かった。ADR 0044 の前提は
「招待した相手が叩く」までで、不特定の人に出すことは入っていない。

ホストして人を呼ぶ（#464）と前提が変わる。

- LLM の費用は月 1000 円までと決めた。告知した日に人が集まると、利用者ごとの
  上限を全員が守っていても、合計で月の予算を 1 日で使い切る。
- 載せる先（Cloud Run）はアイドルのインスタンスを止めるので、メモリの数えは
  そのたびに 0 に戻る。ADR 0044 が「常駐させずに使う構成では回数の上限が実質
  効かない」と書いた形にそのまま当たる。
- 回数の上限はプロバイダを叩く回数を縛らない（再送）。入力の大きさでも費用は
  変わる。

ADR 0031 は使用量を保存しないと決めていた。理由は「表を持つと誰の実績かを決める
必要がある」だった。

## 決定

### 全員の合計の枠を、利用者ごとの枠の手前に足す

`LLMLimiter` が、利用者ごとの同時実行と回数（ADR 0044）の前に、全員の合計を見る。
見る順は **合計の枠 → 同時実行 → 回数**。合計の枠は読むだけで何も消費しないので、
断ったリクエストはどの枠も消費しないまま保てる（ADR 0044 の「弾いたリクエストは
どちらの枠も消費しない」）。

**同じ `LLMLimiter` に載せる。** 解釈と図のドラフト生成には同じものを渡している
（ADR 0044）ので、合計の枠もどちらか片方に掛け忘れることが無い。

### 費用はトークンで数え、入力と出力を分ける

**金額にしない**（ADR 0031）。モデルごとの単価は外の世界の値で、抱えると差し替える
たびに古くなる。

**入力と出力を別々に数え、上限も別々に持つ。** 単価が 5 倍ほど違うので、合わせて
数えると「出力は入力の何倍か」という単価の比を抱えることになる。運用者が予算から
割って、日と月の入力と出力に 4 つの上限を置く。どれも設定したときだけ効き、
**既定値は置かない**（ADR 0044 の回数と同じ理由。妥当な値は料金プランと使い方で
決まる）。

### 日の上限と月の上限。境目は UTC

月の上限が予算そのもの。日の上限は、告知した日に月の予算を使い切らないために
置く。

**境目は UTC にする。** サーバーの置き場所や設定の時刻に左右されない。日本時間では
9 時に切り替わる（README と画面の文言に書く）。

### 超過は始めた実行のぶんまで受け入れる

**判定は始める前に 1 度だけ。** 使った量は終わったあとに積む（再送のぶんも、失敗
した実行のぶんも。どちらも課金されている）。次の 1 回がどれだけ使うかは呼ぶまで
分からないので、届く前には断らない。**届いたら断る。** 同時に始まった実行は
そろって通るので、そのぶんだけ上限を超えうる。

試行ごとに枠を見直す形は採らない。再送の途中で断ると、払ったぶんが結果に
ならない（ADR 0044 が試行ごとの枠を退けたのと同じ理由）。

**数えを読めなければ呼ばない**（500）。予算を超えるほうが取り返しがつかない。
**終わったあとに積めなかったときは、結果は返して記録に残す。** 払ったものは
戻らないので、結果まで捨てると払ったぶんが丸ごと無駄になる。積むのはリクエストの
取り消しから切り離して行う（run の記録と同じ、ADR 0051）。

### 断るときは 429。code は本人の上限と分け、日と月でも分ける

`llm_daily_budget_exhausted` と `llm_monthly_budget_exhausted`。**`rate_limited` に
畳まない。** あちらは本人の使いすぎで「時間をおく」、こちらは全員に効き、待つのは
境目まで。日と月では待つ長さが違う（ADR 0034）。画面は全員の枠であることと、いつ
戻るかを言う。

残り枠は返さない（ADR 0044 のまま）。capabilities にも出さない。上限は設定の
不足ではない（ADR 0030）。

### 日ごとの合計を DB に積む（ADR 0031 を改める）

`port.LLMUsageRepository`。SQLite では `llm_usage_days`（UTC の日ごとに、実行の
回数・入力・出力のトークン数）。**再起動とアイドルの停止で消えないよう、プロセスの
外に置く。**

**改めるのは「保存しない」のうち、全員の合計の数えだけ。** 誰が使ったか（利用者
ごとの台帳）、金額、プロンプトは持たない。全員の合計なら「誰の実績か」を決める
必要が無い。1 回の実行の実績は、これまでどおりログの 1 行（ADR 0031）。

**上限を設定していなくても積む**（置き場所を渡したとき。`cmd/etoki` は必ず渡す）。
上限は実測を見てから決める、という順番を取れるようにする。費用の上限を持つのに
置き場所が無い組み立ては `etoki.New` が断る。

## 結果

- 月の予算と日の予算を、全員の合計で守れる。再起動とアイドルの停止でも数えは
  消えない。
- 尽きると全員が同じ境目まで使えない。本人の使いすぎではないことを、code と文言で
  分けて見せる。
- **打ち切り（`max_tokens`）と拒否のぶんは数えから漏れる。** アダプタがエラーで
  返し、`VisionResponse` を捨てるため（ADR 0031 の既知の穴）。打ち切りは出力の
  上限ぶんを払っているので、頻発する構成では数えが実際より小さくなる。
- 利用者ごとの同時実行と回数は、まだメモリにある。DB に移すのと、利用者ごとに
  データで上限を持つのは #467 の 2 回目、ゲストと IP の上限は 3 回目（#466 の後）。
- 複数のプロセスで同じ DB を使う構成（#457）では、判定と積み増しのあいだに
  プロセス同士の隙間ができる。超過は始めた実行のぶんまで、の範囲は同じ。

## 採らなかった案

- **金額で数える。** 単価を抱えることになる（ADR 0031）。
- **入力と出力を合わせたトークン数で数える。** 単価の比を抱えるか、安い入力の
  上限で高い出力を素通りさせるかのどちらかになる。
- **呼ぶ前に入力のトークン数を見積もって、届きそうなら断る。** 画像のトークン数は
  モデルとアダプタしだいで、etoki が見積もると外の世界の値を抱える。出力は呼ぶまで
  分からない。
- **費用の上限もメモリに置く。** Cloud Run のアイドルの停止で 0 に戻り、月の予算を
  守れない。
- **既定の上限を置く。** 妥当な値は料金プランと使い方で決まり、抱えると必ず誰かに
  合わない（ADR 0044）。
