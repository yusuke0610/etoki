# 0032: ビルド済みフロントエンドは外から渡し、指定されたときだけ配る

ステータス: 採用

## 文脈

**`make build` が作った `web/dist` を配るものが無かった。**

`internal/httpapi/router.go` に静的配信のルートは無く、Go 側で `embed` している
のは `migrations/*.sql` だけ。`make build` は `bin/etoki` と `web/dist` を別々に
作って終わる。**画面を開ける経路は `make dev` の Vite dev server（:5173）だけ**
で、README の Callback URL も `ETOKI_PUBLIC_URL` も :5173 を前提にしている。

**バイナリだけを動かした人には画面が無い。**

ADR 0017 で招待できるようにした構成は、誰かが動かし続けているインスタンスを
前提にする。そのインスタンスの立ち上げ方が無いので、代わりに Vite dev server を
人に向けることになる。ホットリロードとソースマップを持つ開発用サーバーを、
自分以外が使う口にする形になっていた。

ADR 0013（Origin 検証）が同一オリジンで組めているのも、いまは Vite の proxy 設定
（`web/vite.config.ts`）がその同一オリジンを作っているからで、**構成ではなく開発
ツールに依存している。**

## 決定

**置き場所を `ETOKI_WEB_DIR` で外から渡す。未設定なら配らない。**

### バイナリに焼かない

`go:embed` は自分のパッケージより上のディレクトリを参照できないので、`web/dist`
を焼くには **Go のツリーの中へ成果物を写す手順**が要る。そのうえ `web/dist` は
gitignore 済みなので、`bun run build` を通す前は `go build ./...` も
`go test ./...` も golangci-lint も通らなくなる。**フロントエンドのビルド順序が、
Go を触るすべての経路に乗る。** `go.mod` の `ignore ./web`（node_modules に
混ざった Go ファイルを避けるための指定）とも噛み合わない。

得られるのは「1 ファイルで完結する」ことだが、**etoki はリリースバイナリを配って
いない。** 動かす人は clone して `make build` するので、`web/dist` は必ず隣に
ある。**払う代償のほうが大きい。** バイナリを配り始めたら、そのときに焼く判断を
やり直せばよく、そのときは配布物を作る手順の中でだけ順序を持てる。

### 未設定なら配らない

`make dev` では Vite が同じものを配っている。**両方が配ると、画面の出どころが
構成によって変わる。** 既定を「配らない」にしておけば、配るのは明示的に指定した
ときだけになる（中核思想 3）。

**代わりに、指定したら起動時に `index.html` の有無を確かめて落とす。** 指定した
のに配られない状態を実行時の 404 に持ち越すと、画面が開けない原因がパスの
打ち間違いなのか、`bun run build` を忘れたのか、フロントエンド側の不具合なのかを
404 の並びから切り分けることになる。

### SPA の fallback は持たない

**未知のパスに `index.html` を返さない。** フロントエンドに client-side routing は
無く（`react-router` を入れていない）、ログイン後の戻り先も `/` である。配る必要が
あるのは `/` と実在するファイルだけ。

先回りして fallback を置くと、**打ち間違えた URL が 404 ではなく 200 + HTML で
返る。** これは `/api` を fallback の対象にしたときに起きる「JSON のはずが HTML」
と同じ失敗を、API 以外のすべてのパスに広げることになる。ルーティングを入れる
ときに、必要になった時点で一緒に足す。

`/api` と `/healthz` を配信の対象外にするのは、この判断とは別に必要である。配信は
ルートに当たらなかったものだけを見る位置（`NoRoute`）に置き、そこで最初に弾く。

### 認証の外側に置く

配信は `requireAuth` の外にある。**ログイン画面そのものがここから配られる**ので、
内側に置くとログインできない。API は従来どおり内側のまま。

### 変えないもの

- **既定のバインド先は `127.0.0.1`**（ADR 0004）。配れるようになっても、既定では
  手元にしか出ない。
- **Origin と Host の検証**（ADR 0013）。公開インターフェースにバインドするなら
  `ETOKI_ALLOWED_ORIGINS` が要る。**これまでは API だけが 403 になっていたが、
  これからは画面も開けない。** 設定を忘れたときの見え方が変わる。

## 結果

`make build` のあと `ETOKI_WEB_DIR=web/dist bin/etoki` で、dev サーバー無しに
画面が開く。`make start` が同じことをする。Callback URL と `ETOKI_PUBLIC_URL` は
:5173 ではなく :8080（`ETOKI_ADDR` で変えたならそのポート）になる。

**`make build` の順序は変わらない。** Go のビルドはフロントエンドの成果物に依存
しないままなので、`build-api` と `build-web` はどちらから走ってもよい。

**バイナリ 1 つでは完結しない。** 配る人は `bin/etoki` と `web/dist` の両方を運ぶ
必要がある。

**E2E は Vite 前提のままにしてある。** E2E はバックエンドを起動せず契約の型で
モックする（ADR 0012）ので、配信経路は E2E の守備範囲に無い。配れていることは
`internal/httpapi/webui_test.go` が固定する。

**静的ファイルへのリクエストもリクエストログに出る。** 画面を開くたびに asset の
ぶんだけ行が増えるが、間引く仕組みを足すと「記録に出ない経路」を作ることになる
ので、そのままにしてある。
