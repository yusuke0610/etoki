# 0103. 「作るものは無い」を解釈の答えとして受け取る

- 状態: 採用
- 日付: 2026-11-19
- ADR 0029 の制約の表から「items は少なくとも 1 件」を外す

## 背景

LLM が `{"summary": "作るものは見当たりませんでした。", "items": []}` を返すと、
不正な出力として扱い、指摘を添えて呼び直していた（3 回まで）。3 回とも空なら
`interpretation_failed` で、画面は「LLM の出力が期待した形になりませんでした。
もう一度試してください。」と言う（#431）。プロンプトにも「囲んだ範囲から作るものが
1 つも無い、という出力はしないでください」と載せていた。

囲みに作るものが本当に無いことはある（感想、メモ、結論の出ていない議論）。その
とき LLM は何かを作るよう強いられる。従えば中身の薄い issue が並び、従わなければ
3 回ぶんの料金を払って「もう一度試して」と言われ、押し直しても同じ答えになる。
「作れるものが無い」はモデルの読みとして正しい答えで、開発者に見せるべき情報
（中核思想 3）。

## 決定

**空の items を「作るものは無い」という答えとして受け取る。** 呼び直さず、画面は
summary と「そう読んだ」ことを出し、作成の口は出さない。

- **答えにするのは `items: []` と書いたときだけ。** キーが無い・`null` は書き忘れと
  して、`[]` の書き方を添えて呼び直す。書き忘れを「作るものは無い」と取り違えると、
  形を守れないモデルの出力が黙って「何も無い」になる。
- **伝えるのは出力の形の側。** 「作るものが無いと読んだら items を空の配列にし、
  なぜ無いと読んだかを summary に書く」をプロンプトの出力形式の節に置く。これは
  守らせる制約ではないので、制約の表（`domain.Rules`）には置かない。表に置くと、
  それを破る入力が無いので ADR 0029 の両方向の検査が成り立たない。
- **粒度に epic が指定されていても空を許す。** 粒度は「作るならこの単位で」という
  指定で、作るものがあることまでは言っていない。指示を「項目を出すなら epic を
  少なくとも 1 件」に直した。
- **作成の入口は空を弾き続ける**（400 `invalid_input`）。「作るものを 1 件以上選んだか」
  は作成の依頼の性質で、解釈の制約ではない。検査は `CreationService` に置き、
  **GitHub に問い合わせる前に返す。** これまでも空の依頼は弾いていたが、Project の
  フィールドを引いて、作るものが 1 件も無いと分かってからだった。入力だけで決まる
  400 が、GitHub が落ちているときに別の失敗に化ける。
- **空の結果も解釈の履歴に積む。** 引いた解釈は LLM の読みで、空もその 1 つ。
  積まないと、描き足して絵解き直したときに比べる相手が消え、履歴に空だけの扱いが
  要る。

## 採らなかった案

- **「items は少なくとも 1 件」を表に残し、指示を空にする。** ADR 0029 は指示の無い
  制約を「LLM の出力では起こりえない」と読む約束にしている。空は LLM が出してよい
  答えになったので、その読み方と合わない。
- **空のときに etoki が項目を補う。** 作るものを決めるのは LLM の読みと開発者で、
  etoki が補うと、作れないものを作ったことにする。

## 影響

- 空の答えには料金が 1 回ぶんしか掛からない。以前は 3 回ぶん払って失敗だった。
- 小さいモデルが空を言い訳に読むのを怠る、という向きの崩れは画面では区別できない。
  どちらに崩れるかは評価セット（#465）の「作るものは無い」を正解にするケースで
  測る。
- ADR 0009 の「空の run を保存しない」は変わらない。空の解釈からは作成に進めない。
