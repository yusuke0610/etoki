# 0026: changed の出口を作る（対応づけは LLM に解釈させ、決めるのは開発者）

ステータス: 採用

## 文脈

3 状態のうち `changed` を検知しても、開発者にできるのは「もう一度解釈して、もう
一度作る」だけだった。再作成すると GitHub 側には**前回ぶんと今回ぶんの両方が
残る**。draft issue は削除できないので、片付ける手段も無い。

3 状態判定は etoki の中心である。`uncreated → created` の出口はあるが、
**`changed` の出口だけが空いていた。** 示せていたのは「前と違う」までで、そこから
先が「重複を作るか、何もしないか」の二択になっていた。判定に投じたものが使い道に
繋がっていない。

ここで 2 つの穴が見つかった。

**1. 今回の解釈結果と前回の run を繋ぐ安定キーが無い。** `localId` は解釈ごとに
振り直され、`sync_items` の UNIQUE も `(run_id, local_id)` である。

**2. 記録している ID では更新できない。** `sync_items.item_id` に控えてあるのは
ProjectV2Item の ID だが、GitHub の `updateProjectV2DraftIssue` が要求するのは
DraftIssue content の ID で、この 2 つは別物である。

## 決定

### 対応づけは LLM に解釈させ、開発者が確かめる

タイトル一致で寄せるルールベースの推測は採らない。`changed` の典型は「文言を
直した」であり、そのときタイトルは変わる。**いちばん当てたいケースを外す。**
ADR 0024 で開発者がタイトルを手直しできるようにしたので、なおさら当てにならない。

それ以上に、これは中核思想 2 が禁じている形そのものである。「付箋の空間的近接や
コネクタから構造をルールベースで推測しない」の対象が、座標から文字列に変わった
だけで、やっていることは同じ推測である。

**解釈のときに前回ぶんを LLM へ見せ、「これは前回のどれの更新か」を答えさせる。**
候補を出すのは LLM、決めるのは開発者（中核思想 2 と 3）。

- **LLM に見せるのは `p1` のような短い ref。** node ID（`PVTI_lADOA...`）を復唱
  させると取り違える。解決は `domain.ParseInterpretation` の 1 箇所に閉じ、境界へ
  出るのは解決済みの `previousItemId` にする。
- **ref の綴り間違いと取り合いは `ValidationErrors` で返す。** そのまま修正指示に
  なって再送で直せる（ADR 0005）。パースの失敗にすると 1 往復で 1 箇所しか直せない。
- **迷ったら新規に倒すようプロンプトで指示する。** 新しく作るほうが取り返しが
  つく。対応づけを間違えると、別のものを書き換えてしまう。

### 更新先がその注釈のものであることをサーバーが確かめる

`previousItemId` はリクエストボディから来る。確かめずに通すと、**任意の node ID を
書いて無関係な draft issue を書き換えられる。**

`CreationService.Create` の入口で、畳み込み集合に属することを確かめる。1 件でも
見知らぬ ID があれば何も作らず何も更新せずに止め、409 を返す。半分だけ進めると、
取り消せないのに「どこまで進んだか」が分からなくなる。

解釈と作成のあいだに別の run が積まれて対応づけが古くなった場合もここに来る。
`contentHash` の照合（ADR 0010）と打ち手は同じで、解釈からやり直す。

### run は実行の記録のまま、いま在るものは履歴を畳んで出す

更新の経路が入ると、1 つの run に「新しく作った」と「前のを書き換えた」が混ざる。
どちらだったのかを `sync_items.action` に持たせる。

**触っていない item をコピーして新しい run に積まない。** 積むと run が「1 回の
実行」ではなく「そのときの全体像」に変わり、ADR 0007 の意味が失われる。

代わりに、**いま GitHub に在るものは run 履歴を `item_id` で畳んで出す。** 更新は
同じ `item_id` に吸収され、今回触らなかった item も残り続ける。最新 run だけを
見せると、更新の run のあとに「前回作ったが今回は触らなかった」item が画面から
消える。GitHub 側には残っているのに etoki が見せなくなるのは、状態を見せるという
方針に反する（中核思想 3）。

**並びは最初に作られた順で固定する**（`MIN(id)` の順に `MAX(id)` の記録を採る）。
最新の記録の順にすると、1 件更新しただけでその item が末尾へ動き、同じものを見て
いることを確かめ直すことになる。

### content ID は控えず、更新のたびに引き直す

`sync_items` が控えているのは ProjectV2Item の ID だけである。控える側を content の
ID に変える手もあるが、そうすると**列を足す前に作った run だけが更新できないまま
残る。** 引き直せば古い run も救えるので、更新のたびに 1 往復増やすほうを採った。

引き当てた content が draft issue でなければ書き換えない。Project には本物の issue
も並ぶし、etoki が作った item が誰かの手で置き換わっていることもある。確かめずに
更新を投げると、他人の issue を書き換えうる。

### 取り残しは見せるが、消す判断はしない

今回の作成でどこからも指されない前回ぶんは、GitHub 側に残る。**作成ボタンの手前で
「残ります」と見せる。** 押したあとに気づいても削除できない。

選択を外すと、その項目の更新先は取り残しに戻る。**外したことで何が起きるかを、
押す前に見せる。** ADR 0024 が「親を失うことは黙って起こさない」と決めたのと同じ
形である。

## 結果

- `changed` に「重複を作る／何もしない」以外の出口ができた。
- **種別と親は更新でも張り直す。** 手直しで kind を変えられるし（ADR 0024）、親の
  epic のタイトルが変われば子の Parent 値は古くなる。親子は epic のタイトルによる
  手作りの外部キーなので（ADR 0006）、張り直さないと子が迷子になる。
- **取り残した item の Parent 値は古いままになる。** epic のタイトルを書き換えた
  とき、張り直せるのは今回の解釈に入っている子だけである。これは ADR 0006 で
  外部キーを文字列にした帰結であり、既知の限界として残す。UI は作らない。
- **解釈の入力が 1 つ増えた。** テキスト（保存済みシーン）、画像（キャンバス、
  ADR 0018）に加えて、前回ぶん（`sync_items` の畳み込み）が入る。
- ref は保存しない。1 回の解釈のあいだだけ通じる一時 ID であり、`localId` が解釈
  ごとに振り直されるのと同じ扱い。
- `ProjectV2.url` と同じく、**GitHub の GraphQL に依存する形が 1 つ増えた**
  （`updateProjectV2DraftIssue` と `ProjectV2Item.content`）。
