# 0057: 作成した draft issue へは、Project の URL に item の識別子を添えて 1 件ずつ辿らせる

ステータス: 採用

ADR 0025 の「リンクはリストごとに 1 本」を置き換え、「URL は組み立てない」を
部分的に緩める。

## 文脈

作成した draft issue を確かめる導線は、リストごとに 1 本の Project へのリンク
だけだった（ADR 0025）。7 件を作ったあと、どの行から辿っても着地点は同じ
Project で、**目当ての 1 件はそこから自分で探すことになる。**

いちばん確かめたいのは「途中で失敗しました（3 件は作成済み）」のとき
（ADR 0009 / 0043）で、そこで知りたいのは「どの 3 件か」である。更新
（ADR 0026）のあとに書き換わった 2 件が意図どおりかを確かめる相手も、Project
ではなくその 2 件だ。**見せている粒度（item）と、辿れる粒度（Project）がずれて
いた。**

GitHub の GraphQL スキーマを当たると、次のことが分かった（issue #169）。

- `DraftIssue` にも `ProjectV2Item` にも `url` は無い。**ADR 0025 の前提は
  いまも正しい。**
- `ProjectV2Item.fullDatabaseId: BigInt` がある。`databaseId` は 64 ビットに
  収まらないとして削除が告知されている。**BigInt は文字列で届く。**
- 作成（`addProjectV2DraftIssue`）は item を返すので、そこで取れる。更新
  （`updateProjectV2DraftIssue`）は `DraftIssue` を返すので取れない。更新は
  もともと item から content を引き直しているので、そこに足せば往復は増えない。
- Project の画面は `?pane=issue&itemId={数値}` で item のペインを開く。

## 決定

### 土台は GitHub が返した URL のまま、後ろにクエリを足す

```text
{boards.project_url}?pane=issue&itemId={sync_items.item_database_id}
```

ADR 0025 が禁じたのは「URL を組み立てること」そのものではなく、**知らないもの
（owner が user か org か）を決め打つこと**だった。ここで足すのはクエリだけで、
知らない部分は GitHub が埋めたままになる。

- **`project_url` が空なら item ごとのリンクは出さない。** リポジトリの Projects
  タブに `itemId` を足しても item は開かない。番号や owner から土台を組み立て
  直すと、ADR 0025 を裏で覆すことになる。落とし先はリストごとの 1 本で、今日と
  同じ。
- **文字列連結ではなく `URL` で組む。** 控えた URL にクエリや fragment が付いて
  いても壊れず、既に `itemId` があれば置き換える。
- 組み立ては `web/src/board/projectLink.ts` の `projectItemLink` 1 つに閉じる。
- **この形が成り立つのは作成先が最初の run で固定されるから**（ADR 0014）。
  作成先が後から変わりうるなら、古い item のリンクが別の Project を指しうる。
  固定を緩めるときは、ここも一緒に見直す。

### 識別子は作成時に控え、境界の内側では整数で持つ

`sync_items.item_database_id`（`INTEGER NOT NULL DEFAULT 0`、`0` は「知らない」）。
title / body と同じく作成時に控えるが、**意味は違う。** あちらは「そのとき
書いたものの写し」（ADR 0023）で、これは item の不変の属性である。

**アダプタで `int64` に読み、読めなければ `0` にする。** 文字列のまま運んで
`href` に差すと、ADR 0025 が `projectUrl` に置いた門番（`https://github.com`
だけを通す）と同じものが、別の列にもう 1 つ要る。整数にしてしまえば、URL に
載せる余地のある値は型の時点で消える。**門番を増やさずに済むのは「整数だから」
ではなく「整数にするから」。**

フロントは `Number.isSafeInteger` を満たさない値でもリンクを出さない。JSON の
数値として丸められた識別子は別の item を指しうる。今日の値は 2^53 から遠いが、
丸めは黙って起きるので、起きたときにリンクが無いほうへ倒す。

### 取れなくても作成は失敗させない

`fullDatabaseId` が返らない、または読めないときは `0` で保存して作成を続ける。
**確認のための表示が取れないことを理由に、取り消せない操作を失敗扱いにしない。**
失敗にすると、GitHub に作ったのに記録が無い item ができる（ADR 0009）。
ADR 0025 が `projectUrl` を任意にしたのと同じ扱い。

### 畳み込みではこの列だけ MAX を採る

いま GitHub に在るものは run 履歴を item で畳んで出し、各列は最新の行
（`MAX(sync_items.id)`）から読む（ADR 0026）。**この列だけはグループ全体の
`MAX(item_database_id)` を採る。** 不変の属性なので、どの行が持っていても同じ
値になる。

- **列を足す前の item は、更新した時点で埋まる。** 更新の経路は item を引き
  直すので、取りにいく処理を足さずに済む。
- **後の run が値を取り損ねても、前に知った値を失わない。**

### 行ごとのリンクを足し、リストごとの 1 本も残す

ADR 0025 が行ごとのリンクを置かなかった理由は「飛び先がどの行でも同じ」だった。
飛び先が行ごとに違うようになったので、この理由は消えた。

置く場所は 4 つ: 注釈カードの「GitHub にある N 件」、作成結果、取り残しの予告、
シーンから消えた注釈（ADR 0046）。

- **リストごとの 1 本は残す。** Project 全体を見にいくのは、item を 1 件
  見にいくのとは別の用事である。
- **識別子を知らない行は、リンクを出さないだけにする。** 注記は足さない。
  混ざるのは列を足す前の run だけで、行の下のリストごとのリンクから辿れる
  ことは今日と変わらない。
- 同じ文言のリンクが行の数だけ並ぶので、アクセシブルな名前にタイトルを含める
  （ADR 0039）。見える文言も名前に含める。

### `port.GitHubClient` は返り値の形を変える

`CreateDraftIssue` と `UpdateDraftIssue` は `port.ProjectItemRef{ItemID,
DatabaseID}` を返す。`port/` は外部リポジトリが実装する公開面（ADR 0001）なので
破壊的な変更になるが、**別メソッドにはしない。** 別にすると往復が 1 つ増え、
更新の経路では引き直しと二重になる。`DatabaseID` は `0` でよいと契約に書いて
あるので、実装側は値を返さない選択もできる。

## 採らなかった案

- **node ID から識別子を復号する。** `PVTI_…` は base64 で中に数値が入っているが、
  GitHub が不透明と言っているものの中身を読むのは推測で、形が変わった日に黙って
  壊れる。
- **識別子を持たない古い item を、GitHub に取りにいって埋める。** 自動で取りに
  いって書き戻さない（中核思想 3）。更新のついでに埋まる経路で足りる。
- **サーバーが `itemUrl` を組んで返す。** リンクの形を Go が知り、落とし先の
  判断をフロントが持つ、という割れ方になる。契約が運ぶのは素材
  （`itemDatabaseId`）までにする。
- **本物の issue を作る。** 固有の URL はあるが、etoki が何を作るかの変更で、
  リンクを足すという話ではない。

## 結果

- 作成した item を、作成結果・カード・取り残し・消えた注釈の一覧から 1 件ずつ
  開ける。
- **`/views/{n}` を省いた URL でペインが開くかは、実物で確かめていない**
  （issue #169）。見つかった文献はどれも `/views/{n}` を含む形で、省いた形に
  ついて書いたものは無かった。開かなかった場合も着地先は Project で、今日の
  リストごとのリンクと同じところに落ちる。必須だと分かったら、view 番号を
  作成先を選んだ時点のスナップショットとして控える（ADR 0019 / 0025 と同じ扱い）。
- 識別子を知らない item が混ざる。列を足す前の run と、GitHub が値を返さな
  かった run。前者は更新すれば埋まる。
