# 0076. 認証ありの構成では、etoki が認可サーバーになって `/mcp` を OAuth で開く

- 状態: 採用
- 日付: 2026-10-09

## 背景

ADR 0071 は `/mcp` を認証なしの構成でだけ開き、GitHub App を設定した構成では
503 を返すことにした。利用者を決める手段が無いまま開くと、ログインせずに全ボードが
読めるため。認証ありの構成でも MCP のクライアント（Claude Code など）から使えるように
したい（#185）。MCP の仕様は、HTTP の入口の認証を OAuth 2.1 で行うと定めている。

画面のログインも OAuth だが、**etoki の立場が逆になる。**

- **画面**：etoki は OAuth の**クライアント**で、GitHub がトークンを発行する。
- **MCP**：etoki がトークンを**発行する側**（認可サーバー）に立つ。MCP のクライアントは
  etoki のメタデータを読み、クライアントとして登録し、etoki が発行したトークンで
  `/mcp` を叩く。

GitHub を認可サーバーとして直接指せれば発行側に立たずに済む。採らないのは、
**GitHub のトークンを MCP のクライアントに預けることになる**ため。そのトークンは
etoki のボードを読む権限ではなく、利用者が App に許した GitHub への権限そのもので、
etoki の側で範囲を絞れず、etoki の画面からは取り消せない。あわせて、MCP のクライアントが
前提にする登録の仕組み（動的登録、Client ID Metadata Document）を GitHub が受ける
という記述は、2026-10 時点で GitHub の文書に見当たらない（実機では未確認）。

## 決定

### 認可サーバーを etoki の中に持つ。「誰であるか」は既存のログインに任せる

認可のエンドポイントは**既存の GitHub ログインをそのまま使う。** 利用者を決めるのは
`port.IdentityProvider` で、画面のセッションがあればそれを使い、無ければ画面と同じ
ログインに送る。そのあとで etoki のトークンを発行する。

**発行した利用者は `port.ContextWithUserID` で運ぶ。** これで次の 2 つがそのまま効く。

- ボードのメンバーと権限（ADR 0017）。道具は `/api` と同じ組み立てを通るので（ADR 0071）、
  画面で見えないボードは MCP でも見えない。
- GitHub を叩くトークン（`port.GitHubTokenSource`）。`AuthService.Token` は ctx の利用者から
  画面のログインで保存した GitHub の資格情報を引く。**MCP のために GitHub の資格情報を
  別に持たない。** 読み取りだけの今は使わないが、書き込みの道具を足すときに継ぎ目を
  増やさずに済む。

### 継ぎ目：発行の処理は port にしない。保存先だけを新しい port で切る

**発行の処理（認可・トークン・登録）は `internal/usecase` に置き、`port` のインター
フェースにしない。** 外部の認可サーバー（Okta など）に置き換えたいという要望はまだ無い。
どこからも型アサートされないインターフェースは守れない約束になる（ADR 0015）。要る
ことになったら、置き換えるのは「`/mcp` に届いたトークンを検証する」1 点で、そのとき
検証の継ぎ目を足す。

**保存先は `port.OAuthGrantRepository` として新しく切る。** ADR 0015 の 3 つの継ぎ目の
どれにも入れない。

- `port.SessionRepository` にメソッドを足すと、それを自前実装している外部リポジトリが
  コンパイルできなくなる。
- 発行した許可は画面のセッションと寿命も失効の仕方も違う（下記）。同じ型に混ぜると、
  片方の都合でもう片方を壊す。

`etoki.Options` に足すのは `OAuthGrants port.OAuthGrantRepository` と、CIMD を受けるか
（`OAuthClientMetadataDocuments`、下記）の 2 つ。**`OAuthGrants` は nil でよい。** nil
なら、認証ありの構成では `/mcp` をこれまでどおり 503 のままにする（ADR 0071）。認証
なしの構成ではこの設定を見ない（`/mcp` は認証なしで開く）。

CIMD の文書を取りに行く口は `internal/` に置き、`etoki.New` が組み立てる。外部
リポジトリは `internal/` を import できないので、差し込む口ではなく真偽値で受ける。

### 許可（grant）を単位にする

「どの利用者が、どのクライアントに、どの scope を許したか」を 1 件の**許可**として
持つ。アクセストークンと refresh token は許可にぶら下がる。**失効は許可ごとに行う。**
トークン 1 本ずつを人に選ばせても、人には見分けがつかない。

### 同意を省かない。同意の画面は React に置く

`/oauth/authorize` は**何も書かず、検証もせずに**、要求のクエリを 1 つの値に包んで
画面（`/?authorize=<要求>`）へ転送する。画面はログインしていなければ既存のログインに
通し（戻り先は ADR 0059 の `returnTo` で、要求ごと運ばれる）、要求をそのまま
`GET /api/oauth/authorization` に送ってクライアントの名前・戻り先・scope を見せ、
許可か拒否を `POST /api/oauth/authorization` で受ける。許可したら code を付けて
クライアントに戻す。

- **同じクライアントでも毎回聞く。** 登録は誰でもできるので（下記）、一度許したことを
  理由に自動で許すと、ログイン済みの利用者の code を別のページから取られうる。中核
  思想 3（システムは自動で判断しない）にも沿う。
- **許可は POST で受け、要求はそこで検証し直す。** Origin の検証（ADR 0013）が効く。
  画面に見せたときの検証を信じると、そのあいだに要求を差し替えられる。
- **`/oauth/authorize` は副作用を持たない。** 副作用を持つ GET は `/api/auth/callback`
  だけに留める（ADR 0013）。要求をサーバーに控える形も考えたが、そうすると 2 つめの
  例外になる。**検証もここではしない。** CIMD の取得（外向きの通信）を、ログイン
  していない誰でも起こせることになるため。検証はログインした画面が `/api` を叩いた
  ときに行う。
- **要求の誤りはクライアントに戻さず、画面に出す。** 戻り先を確かめる前に戻すと
  オープンリダイレクトになる。確かめたあとの誤りも画面に出すのは、戻すかどうかで
  分岐を持つほどの得が無いため。断るとき（「許可しない」）だけは、戻り先を確かめて
  から `error=access_denied` を付けて戻す。
- **同じ名前のパラメータが 2 つ付いた要求は断る**（RFC 6749 3.1）。先頭だけを読むと、
  画面に見せた値と使う値が食い違いうる。
- **画面に置く。** ログイン・`returnTo`・テーマ・文言（ADR 0034）の仕組みがそのまま
  使える。サーバーが HTML を返す形にすると、見た目と文言が画面と別の系統になる。

### クライアントは動的登録と Client ID Metadata Document の両方で受ける

- **動的登録（RFC 7591）。** `POST /oauth/register`。Claude Code をはじめ、いまの
  クライアントの多くが前提にしている。
- **Client ID Metadata Document（CIMD）。** MCP の 2025-11-25 版で推奨になった。
  `client_id` が https の URL で、etoki はそこからクライアントのメタデータを取りに行く。
  登録の口を叩かずに済み、クライアントが名乗る名前の出どころが URL のドメインで
  見える。

どちらも**公開クライアントだけを受ける**（`token_endpoint_auth_method=none`）。MCP の
クライアントは利用者の手元で動き、秘密を守れない。**PKCE（S256）を必須にする。**

戻り先（`redirect_uri`）は**ループバックの http か https だけ**を受ける。ループバックは
RFC 8252 に従い、ポートの違いを許す（ネイティブアプリは空いているポートで待つ）。

#### 登録の口は回数で絞り、使われない登録は掃除する

**`/oauth/register` は、ログインしていなくても書き込みが起きる 2 つめの口**になる。
ログインの開始（`MaxLoginStarts`、#147）と同じ形で、窓の中の回数をプロセス全体で数えて
429 で断る。許可が 1 件も付かないまま 24 時間たった登録は消す。

#### CIMD の取得は外向きの通信なので、行き先を絞る

`client_id` の URL は他人が決める値で、etoki はそれを取りに行く。何もしなければ
**SSRF の入口になる**。

- https だけ。リダイレクトは追わない。
- 名前を引いた結果が**ループバック・プライベート・リンクローカルなら繋がない。**
  引いた後のアドレスで判定し、そのアドレスに繋ぐ（引き直しで差し替えられないように）。
- 本文は 5 KiB まで、5 秒で打ち切る。
- 取った文書の `client_id` が URL と一致しなければ断る。
- 取った結果は HTTP のキャッシュ指示に従って短く持つ（上限 1 時間）。

### トークン

- **乱数の不透明な値にし、DB には SHA-256 だけを置く。** 画面のセッションと同じ
  （ADR 0015）。JWT にしない。失効を即時に効かせたいので、どのみち毎回 DB を引く。
- **アクセストークンは 1 時間、refresh token は 30 日。** refresh token は**使うたびに
  入れ替える**（OAuth 2.1 が公開クライアントに求める）。**一度使った refresh token が
  もう一度来たら、許可ごと失効させる。** 漏れた値が使われたと見なす。
- **トークンを使える先は `/mcp` に限る**（RFC 8707 の `resource`）。認可と
  トークンの要求で `resource` が `/mcp` の正規の URL と一致しなければ断る。
  **`/api` は Bearer を受けない。** 画面の cookie と MCP のトークンを同じ口で受けると、
  どちらで来たかで振る舞いを変える分岐が `/api` の全部に入る。
- **scope は `read` の 1 つだけ。** 道具が読み取りだけなので（ADR 0071）。書き込みの
  道具を足すときに scope を増やし、同意の画面に出す。

### 失効は画面と CLI の両方から

- **画面：**利用者は自分が許した許可の一覧（クライアント名・許可した日時・最後に
  使った日時）を見て、1 件ずつ取り消せる。**他人の許可は見えない。**
- **CLI：**`etoki grants` で一覧を出し、`etoki revoke [--yes] <grant-id>` か
  `etoki revoke [--yes] --login <login>` で取り消す。`etoki claim` と同じく DB に直接
  当たる、サーバーを動かしている人のための道具。**取り消す前に対象を見せて `y/N` で
  確かめる**（ADR 0053 と同じ。既定は止める。端末でない入力では `--yes` が要る）。

**ログアウトしても MCP の許可は消さない。** GitHub のトークンを取り消さないのと同じで
（`AuthService.Logout`）、ブラウザを閉じる操作が手元の CLI の接続を切るのは意図に
合わない。消したいなら一覧から取り消す。

**利用者のセッションが無くても、MCP のトークンは単独で通る。** 読み取りの道具は
GitHub を叩かないので、GitHub の資格情報の状態に依らない。書き込みの道具を足すと、
資格情報が失効していて更新もできない利用者は `ErrNotAuthenticated` になる。その
ときの見せ方は、書き込みの道具を足すときに決める。

### メタデータ

- `GET /.well-known/oauth-protected-resource/mcp`（RFC 9728）。パスを挟まない
  `/.well-known/oauth-protected-resource` でも同じものを返す。先にそちらを引く
  クライアントがある。
- `GET /.well-known/oauth-authorization-server`（RFC 8414）。CIMD を受ける構成では
  `client_id_metadata_document_supported: true` を載せる。認可の応答に `iss` を載せる
  （RFC 9207）。
- `/mcp` は Bearer が無い・無効なとき 401 と `WWW-Authenticate`（`resource_metadata`）を
  返す。

**SDK の `auth.RequireBearerToken` と `auth.ProtectedResourceMetadataHandler` は使わ
ない。** どちらも URL を固定値で受けるので、リクエストの Host から URL を組む etoki
（下記）では構成ごとに作れない。返す形は SDK と同じにしてある。

**issuer と `/mcp` の正規の URL は、ログインの `redirect_uri` と同じ規則で組む**
（`ETOKI_PUBLIC_URL`、無ければリクエストの Host）。Host は originGuard（ADR 0013）が
すでに許した値だけが届く。

### Origin の検証との関係

`/oauth/register` と `/oauth/token` は MCP のクライアントがブラウザの外から POST するので
`Origin` が付かず、originGuard はいまのまま通す。**ブラウザで動く MCP のクライアントは
cross-origin になり弾かれる。** 許すには `ETOKI_ALLOWED_ORIGINS` に足す。CORS は
開けない（etoki は手元のツールで、画面以外のブラウザから叩かれる前提を持たない）。

`/oauth/authorize` は副作用を持たないので、`origin.go` が前提にしている「GET に副作用
は無い（コールバックだけが例外）」は崩れない。code の発行は Origin の効く POST の
後ろにある。

### SDK と置き場所

受ける側も発行側も自前で書く（受ける側の理由は上の「メタデータ」）。**fosite などの
認可サーバーのライブラリは入れない。** 要るのは公開
クライアント・認可コード + PKCE・refresh の 1 組だけで、ライブラリの面の大半を
使わないまま依存と設定を抱えることになる。

HTTP の口は `internal/httpapi`、発行の規則は `internal/usecase`、保存は
`internal/adapter/sqlite`。**OAuth の口（`/oauth/*`、`/.well-known/*`）は
`api/openapi.yaml` に載せない。** 形を決めているのは RFC で、etoki の契約ではない。
同意の画面が使う `/api/oauth/*` と、許可の一覧・取り消しの `/api/oauth/grants` は
画面の契約なので載せる（ADR 0011）。

### 保存

コードとトークンは SHA-256 だけを置く。**使ったコードと refresh token は期限まで
残す。** 使い回しに気づくためで、消すと 2 回目が「知らない値」になり、許可を失効
させられない。使用済みにする照合は UPDATE 1 文に置く。同じ値が 2 本同時に来ても、
1 回目になれるのは 1 本だけ。

時刻は小数 9 桁の固定幅で書く。期限の判定を文字列の大小で行うので、桁数が揃って
いないと順序が時刻と食い違う。

## 帰結

- 認証ありの構成でも MCP のクライアントからボードを読める。見える範囲は画面と同じ。
- 認証ありの構成で `/mcp` を開くには、配線（`cmd/etoki`）が `OAuthGrants` を渡す
  必要がある。SQLite の実装は既定で渡す。
- ログインしていなくても書き込みが起きる口が 1 つ増え（登録）、外へ出ていく通信が
  1 種類増える（CIMD の取得）。どちらも上の制限で絞る。
- etoki は認可サーバーとしての規則（PKCE、`resource`、refresh の入れ替え）を自分で
  持つ。仕様の改版に追いつくのは etoki の仕事になる。
- **ADR 0071 の帰結の 1 つを改める。** `make dev` の Vite は `/mcp` を転送しないと
  していたが、`/mcp`・`/oauth`・`/.well-known` を転送する。認証ありの構成では許可の
  途中で画面に転送され、画面を配っているのが Vite だから。Host は書き換えないので、
  issuer と `/mcp` の URL は :5173 で組まれ、トークンの向き先と食い違わない。
- トークンは発行したときの `/mcp` の URL に結びつく。`localhost` と `127.0.0.1` の
  ように別の Host で来れば、別の資源として断る。

## 採らなかった案

- **GitHub を認可サーバーとして直接指す。** GitHub のトークンを MCP のクライアントに
  預けることになり、範囲も取り消しも etoki の手を離れる。
- **画面のセッション cookie を `/mcp` でも受ける。** MCP のクライアントはブラウザの
  外で動き、cookie を持たない。
- **発行の処理を port のインターフェースにする。** 差し込む実装の当てが無い。
- **一度同意したクライアントは次から自動で許す。** 登録が誰でもできるので、自動で
  許すと code を横取りされうる。
- **JWT のアクセストークン。** 失効をすぐ効かせたいので結局 DB を引く。検証の鍵の
  管理だけが増える。
- **動的登録だけを受ける。** 2025-11-25 版で CIMD が推奨になり、これから増える
  クライアントがそちらを前提にする。
- **失効を画面だけにする。** 利用者が画面に入れなくなったとき（GitHub 側でアクセスを
  外したなど）に、サーバーを動かしている人が切る手段が無くなる。
