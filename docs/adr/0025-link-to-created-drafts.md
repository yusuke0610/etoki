# 0025: 作成先の URL は組み立てず、GitHub が返したものを控える

ステータス: 採用

## 文脈

作成結果として画面に出るのは `kind` とタイトルと本文だけで、GitHub へのリンクが
無い。作ったものを確かめるには、利用者が自分で GitHub を開いて Project を探す
ことになる。

draft issue の作成は取り消せない（ADR 0009）。**取り消せない操作の結果を確かめ
られないのは、確認の導線として不足している。** とくに「途中で失敗しました
（3 件は作成済み）」と出たとき（ADR 0009）、何が作られたのかを見にいけないのが
いちばんつらい。

`SyncItem` が持つのは Projects v2 の node ID（`itemId`）で、これは URL に使え
ない。そこで Project へのリンクから入ることにしたが、ここで前提が崩れた。

**etoki は作成先の owner が user なのか org なのかを知らない。** Projects v2 の
URL は次の 2 つに分かれる。

```text
https://github.com/orgs/{owner}/projects/{number}
https://github.com/users/{owner}/projects/{number}
```

`boards` が持つのは `repository_owner` の文字列だけで（ADR 0014）、GraphQL も
`owner { login }` しか取っていない。どちらの形になるかを決める材料が無い。
番号（ADR 0019 で控えたスナップショット）はあるが、番号だけでは形が決まらない。

決め打つと、外したほうのボードでリンクが 404 になる。**確認のための導線が 404 を
返すのは、リンクが無いより悪い。** 「作ったものを確かめられる」と約束しておいて
確かめられないので、中核思想 3 の「状態を見せる」が嘘になる。

## 決定

**URL を組み立てず、GitHub が返した `ProjectV2.url` を作成先を選んだ時点の
スナップショットとして控える。**

`project_number` / `project_title` と同じ扱いにする（ADR 0019）。

- **判定には使わない。** 作成先が選ばれているか（`BoardTarget.Selected`）も、
  固定済みか（`sync_runs` の有無）も、この列とは無関係に決まる。
- **任意。** 送られてこなければ空文字（＝ URL を知らない）で保存する。
- **自動で GitHub に取りにいって書き戻さない。** 取り直すのは作成先を選び直した
  ときだけ（自動更新は実装しない・中核思想 3）。

選択画面はすでに Project 一覧を GitHub から取っているので、問い合わせは増えない。
`url` を 1 つ選択に足すだけである。

### URL を知らないボードはリポジトリの Projects へ落とす

この列を足す前に作成先を選んだボードは、番号と名前は持っているのに URL だけが
空になる。そこでリンクを消すと、**既存のボードすべてが今日から確かめられない
まま取り残される。** 潰したかった痛みがいちばん残っている側に残る。

代わりに `https://github.com/{owner}/{repo}/projects`（リポジトリの Projects
タブ）へ落とす。`repository_owner` と `repository_name` だけで組め、owner の
種別を当てにいかずに済む。着地するのは Project 本体ではなく一覧なので 1 クリック
余分だが、**404 にはならない。**

**番号からは組み立てない。** 落とし先を `/orgs/{owner}/projects/{number}` に
すると、結局 owner の種別を当てにいくことになる。

規則は `web/src/board/projectLink.ts` の純関数 1 つに閉じる。

### 一覧止まりであることを隠さない

Project そのものに着地しないときは、リンクの文言をそう変える
（「GitHub でリポジトリの Projects を開く」）。Project へ飛ぶと言って一覧に着地
させると、リンクの約束が崩れる。**1 クリック余分なことより、言ったとおりの場所
に着かないことのほうが問題である。**

### 受け取った URL は GitHub のものだけ通す

`projectUrl` はリクエストボディから来る。保存された値はフロントがそのまま
`href` に入れるので、**貯めた値はいつか開発者のブラウザで開かれる。**

ボードは共有できる（ADR 0017）。owner が `javascript:` を保存できると、招待した
相手のブラウザでそれが走る。外部ドメインを通せば、「GitHub でこの Project を
開く」という文言のまま別の場所へ送れる。どちらも、リンクを足したことで新しく
開いた穴である。

**`BoardService.Create` と `SetTarget` で、空文字か `https://github.com` の URL
だけを通す。** 違反は `ErrInvalidInput`（400）で弾く。空に落として黙って保存
しない。渡したはずの値が黙って消えたことに、呼び出し側は気づけない（ADR 0018）。

- **パスの形は見ない。** `/orgs/...` か `/users/...` かを判定に入れると、この
  ADR の中心である「形を知らない」を裏で覆すことになる。見るのはスキームと
  ホストだけで、これは知っている。
- **フロント側に同じ判定を置かない。** この列は新規なので、壊れた値が入る経路は
  サーバーの門番しか無い。両側に置くと判定が 2 箇所になり、片方だけ変わる。
- **ホストは定数。** GHES ではホストが変わるが、いまはそれを設定する導線が無い
  （`github.Config.BaseURL` を env から埋めていない）。導線を足すときは、ここも
  一緒に設定可能にする。

### リンクは行ごとではなくリストごとに 1 本

draft issue には個別の URL が無く、飛び先はどの行でも同じ Project になる。行
ごとにリンクを並べると、**行ごとに違う場所へ飛ぶように読めてしまう。**

## 結果

- ヘッダの作成先バッジ、作成結果、前回作成ぶんの 3 箇所から GitHub へ辿れる。
- **リンクの正しさが GitHub 側の値に依存する。** etoki は形を知らないままで
  よくなった代わりに、`ProjectV2.url` が返らない構成では空文字になり、
  フォールバックへ落ちる。落ちても壊れない形にしてあるのはそのため。
- **移行前のボード（作成先が未選択）ではリンクを出さない。** 飛び先が無い。
- 改名や owner の移管で URL は古くなる。番号と名前と同じ古び方をするので、
  選び直しで直す。ADR 0019 が「表示用の値は古くなる」と引き受けた範囲を出ない。
- **item 個別の URL はまだ組めない。** draft issue が Project の外に固有の
  アドレスを持たないため。組めるようになれば行ごとのリンクに意味が出るので、
  そのときは「リストごとに 1 本」の判断ごと見直す。
