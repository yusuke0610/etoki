# 0101: 利用者は自分を消せる。文書へのリンクは設定で受ける

ステータス: 採用

## 文脈

etoki には利用者を消す経路が無かった（ADR 0016 の「結果」）。ボードは owner が
消せる（ADR 0042）が、利用者の行・セッション・保存した GitHub のトークン
（ADR 0015）・MCP の許可（ADR 0076）は残る。

手元で動かす道具には要らなかった。ホストして人を呼ぶ（#464）と、他人のトークンと、
未公開の企画が描かれたボードを預かる。描いた内容は絵解きのときに LLM の提供元へ
送られる。**何を預かり、どこへ送り、どう消せるかを言えないまま人を呼ぶことに
なる。** 言うための文書（利用規約・プライバシーポリシー）も無かった。

## 決定

### 利用者が自分を消す口を開く

- **`GET /api/account/deletion` で消えるものを先に返し、`DELETE /api/account` で
  消す。** ボードの削除（ADR 0042）と同じ形で、画面は利用者のメニューの
  「アカウントを削除…」から確認を開き、押す前に見せる。**見せた中身を消すときの
  前提条件にしない**（ADR 0042 の「押す前に見せた数を、実行時の前提条件にしない」）。
  消すものは消すときに引き直して決める。
- **消すのは、その人だけが owner のボードと、その人のメンバーの行と、利用者の行。**
  利用者の行を消せば、セッション・トークン・MCP の許可はスキーマの
  `ON DELETE CASCADE` が一緒に消す。消える範囲を Go に書き下さない（ADR 0042 と
  同じ）。
- **共有していても、その人だけが owner なら消す。自動では移さない。** 誰に移すかを
  etoki が決めると中核思想 3 に反する。owner が共有したボードを消せるのは今と同じ
  （ADR 0042）。残したいなら、先に参加者をオーナーにしてもらう（今ある操作）。
  確認では、消えるボードごとに**ほかのメンバーの数**を出す。
- **ほかにも owner がいるボードは消さず、メンバーの行だけを外す。**
- **消す順番は、ボード → メンバーの行 → 利用者の行。** `board_members` には外部キーが
  無い（ADR 0016）ので、利用者の行を先に消すと持ち主の無いボードが残る。ボードは
  1 枚ずつ、ボードの削除と同じロックの中で消す（作成の途中で消さない、ADR 0042）。
  **途中で失敗したら、消えたものは戻さない。** もう一度消せば続きから消える。
- **認証を設定した構成でだけ開く。** 認証なしの構成の利用者は空文字の 1 人
  （ADR 0016）で、消すと全ボードが消える。`etoki.New` が口を組み立てず、
  ユースケース層も空文字を断る。capabilities に `accountDeletion` を出す
  （ADR 0030）。
- **消さないもの。** GitHub に作った draft issue（ADR 0042）、GitHub 側のアプリの
  認可、プロセスのログ（リクエストログの利用者 ID、ADR 0016）。アプリの認可を
  etoki から取り消さないのは、取り消しを GitHub に頼むと、消すことが GitHub の
  可用性に縛られるため。保存したトークンを消せば、etoki はもう使えない。
  利用者には、GitHub の設定から取り消せることを確認の中で言う。

### 運用者が消す CLI を足す

- **`etoki delete-user [--yes] <login>`。** 画面に入れなくなった利用者に頼まれた
  ときの道具。消し方は画面の口と同じユースケース（`AccountService`）を通す。
  `claim` / `revoke` と同じく、引き当てた利用者と消えるものを見せて確かめる
  （ADR 0053）。
- **動いているサーバーとは排他を共有しない。** ボードのロックはプロセスの中にしか
  無い（ADR 0014）。作成が走っていないとき（止めてから）使う、と案内する。

### 文書はホストする側が持ち、コアはリンクの口だけを持つ

- **`ETOKI_TERMS_URL` / `ETOKI_PRIVACY_URL` で受け、ログインの画面と利用者の
  メニューに出す。** 中身と連絡先はホストする側（#472）が用意する。コアに文書を
  置くと、運用者ごとに違う約束をリポジトリが 1 つに決めることになる。
- **未ログインでも読める `/api/auth/session` の応答に載せる。** 何を預かるのかを、
  預ける前に読めるようにする。capabilities は認証の内側にあるので使わない。
- **http(s) の絶対 URL だけを受け、`etoki.New` で検査する**（設定値は組み立てで
  検査する、`.claude/rules/validation-boundaries.md`）。打ち間違えたリンクに、
  押されたときに初めて気づくことにしない。
- **「ログインすると同意したものとみなす」のような文言はコアに置かない。** 同意を
  どう取るかは文書の側が決めることで、etoki が持つのはリンクの口だけ。

## 結果

- ホストした etoki で、利用者は自分の持ち物を消せる。消えないもの（draft issue・
  アプリの認可・ログ）を文書にそのまま書ける。
- **共有ボードの参加者は、owner が消えるとボードごと失う。** owner がボードを
  消したときと同じで、確認の画面が「ほかに N 人のメンバーがいます」と先に言う。
- ADR 0016 の「結果」の「etoki に利用者を消す経路は無い」は成り立たなくなった。
  消えた利用者のメンバーの行は消すときに外すので、いない人を指す行は残らない
  （DB を直に触った場合を除く）。
- 法的な要件（何を書けば足りるか）はこの判断では扱っていない。公開（#476）の前に
  人が確かめる。

## 採らなかった案

- **共有ボードはほかのメンバーへ自動で移す。** 誰に移すか（最古の editor など）を
  etoki が決めることになる（中核思想 3）。移された側は、知らないうちに作成先の
  変更や招待の責任を負う。
- **共有ボードがあるうちは消させない。** 消したい人を、ほかの人の操作待ちで
  止めることになる。移すかどうかは本人が先に選べる（オーナーにする）。
- **GitHub のアプリの認可も etoki から取り消す。** 上に書いたとおり、消す操作が
  GitHub の可用性に縛られる。取り消しに失敗したときに、etoki 側を消すかどうかの
  判断も生える。
- **文書をリポジトリに置く。** 運用者ごとに違う約束（連絡先・保存期間）を 1 つに
  決めることになる。
