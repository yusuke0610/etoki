# 0099. リリースは、Nix で作った配布物と、それを詰めたコンテナイメージにする

- 状態: 採用
- 日付: 2026-11-17
- #446
- ADR 0032 の「配り始めたら焼く判断をやり直す」に答える（焼かないままにする）
- ADR 0070 が別に扱うとした、バイナリに焼いた Go の依存の表示を扱う

## 背景

etoki を手に入れる手段は、clone して Nix の devShell で `make` を回すことだけ
だった。タグもリリースもコンテナイメージも無い。ホストして人に出すと決め
（#464）、載せる先（Cloud Run、#472）はコンテナイメージを前提にする。

動いている版を知る口も無かった。不具合の報告が、どの版の話かが分からない。

## 決定

### 版はタグ（vX.Y.Z）で付け、v0 のあいだは互換を約束しない

公開 API 面（`port/`・`etoki.go`、ADR 0001）も含める。破壊的な変更は
リリースノートに書く。使う人が少ないうちに約束を固めると、直せないものが増える。

### 版の値は make が git から取り、ビルド時に埋める

`git describe --tags --always --dirty` を、`-ldflags -X` で `internal/version` に
埋める。`etoki version` と `/healthz` がそれを言う。

**Go が VCS から埋める値は、埋めていないときの控えにだけ使う。** 作業ツリー
（`.claude/worktrees/`）はリポジトリの中にあり、`.git` がファイルなので、Go は
外側のチェックアウトを VCS の根と見なし、その版と「変更あり」を埋める。作業
ツリーで作った配布物が、別のコミットを名乗ることになる。

### フロントはバイナリに焼かない（ADR 0032 のまま）

配布物とイメージに `web/dist` を同梱し、イメージは `ETOKI_WEB_DIR` を既定で渡す。
焼くとフロントのビルド順序が `go build`・`go test`・lint のすべてに乗る、という
ADR 0032 の理由は、配っても変わらない。順序は、配布物を作る手順（`make dist`）の
中でだけ持てばよい。

### 成果物は devShell の make で作り、Dockerfile は詰めるだけにする

`make dist` が linux / darwin の amd64・arm64 を作る。CGO は切る。SQLite
（modernc）が純 Go なので、ほかの OS 向けにもそのまま組める。Dockerfile は linux の
2 つを詰めるだけで、自分ではビルドしない。Dockerfile の中で Go や Bun を入れると、
道具の版が `flake.lock` の外で決まる（ADR 0002）。docker は `gh` と同じく
ホストの道具として扱い、devShell に入れない（ADR 0002 の追記）。

**Dockerfile に RUN を置かない。** 置くと、ほかの CPU 向けのイメージを組むときに、
その CPU の真似（QEMU）が要る。利用者は数字の UID で、DB の置き場所は持ち主
ごと写す空のディレクトリで用意する。

### イメージは alpine を土台にし、root でない利用者で動かす

シェルがあれば、SQLite の複製の道具（Litestream など）を上に重ねたとき、起動の
手順（戻す → 移行 → 起動）をシェルで書ける（#472）。

既定は `ETOKI_ADDR=0.0.0.0:8080`・`ETOKI_DB_PATH=/var/lib/etoki/etoki.db`・
`ETOKI_WEB_DIR` で、どれも環境変数で変えられる。コンテナの中ではループバックの外で
待ち受けないと届かないので、既定の `127.0.0.1`（ADR 0004 / 0016）を変える。
手元で使うときにループバックだけに出すのは、ホストの側（`-p 127.0.0.1:8080:8080`）
で決める。

### マイグレーションは起動のたびに当てない

今のまま、足りなければ起動を止めて案内する。案内は `etoki migrate` にした
（配った物には make が無い）。起動のたびに当てると、版を上げただけで DB が
書き換わり、戻せない。いつ当てるかは動かす人が決める（中核思想 3 と同じ向き）。

### Go の依存のライセンス表示を配布物に同梱する

`go-licenses` で各モジュールの LICENSE を写し、モジュールの根にある NOTICE 類
（取り込んだコードの表示）も写す。Go 本体（標準ライブラリ）は `go-licenses` が
数えず、Nix の Go は LICENSE を持たないので、Go のリポジトリから写したもの
（`third_party/go/LICENSE`）を置く。**本文を推測で書かない**（ADR 0070 と同じ線）。

### 書く権限はタグの job にだけ渡す

`release.yml` の `publish`（タグのときだけ）に `contents: write` と
`packages: write` を渡す。トークンを使うのは、リポジトリのコード（依存を含む）が
動き終えたあとだけで、それまでは環境にもファイルにも置かない。PR の確かめ
（`verify`）は読むだけ。

**リリースは下書きで作る。** タグを打つのも、下書きを公開するのも持ち主。

### イメージは PR で組んで、起動まで見る

手元に docker のデーモンが無くても壊れたことを知れるよう、リリースの手順に
関わるファイルを触った PR で `make image-check` を回す。組む → 版 → 移行 →
起動 → `/healthz` → 画面、の順に見る。送らない。

## 検討したが採らなかった案

### Dockerfile の中でビルドする（多段）

いちばんよく見る形だが、Go と Bun の版が `flake.lock` の外で決まり、手元と CI と
イメージで別の道具が動く。

### Nix でイメージを組む（dockerTools）

道具は flake に閉じるが、Go の vendorHash と、Bun の依存をオフラインで取る
仕組みを保守することになる。ADR 0002 が checks を絞ったのと同じ理由。

### シェルの無い土台（distroless）

小さく、攻撃面も狭い。ただ、複製の道具を重ねたときに起動の手順を書けず、重ねる
側が土台を替えることになる。

### 署名・SBOM・来歴を付ける

使う人が増えてから決める。いま付けても、確かめる側の手順が無いまま形だけが
残る。

### Windows 向けを配る

確かめる手段が無い。

## 影響

- タグを打つと、リリースの下書き（アーカイブ 4 つとチェックサム）と、
  `ghcr.io/<リポジトリ>:<タグ>` のイメージができる。
- `/healthz` の応答に `version` が増えた（契約を変えた）。
- 依存を上げたときの表示は `make dist` が写し直す。Go 本体の LICENSE の本文が
  変わったら、`third_party/go/LICENSE` を写し直す。
- GHCR のパッケージの公開範囲は GitHub の設定で決まり、ここでは決めていない。
