# 0020: シーンの保存は版を照合し、衝突を検知だけする

ステータス: 採用

## 文脈

`PUT /api/boards/{id}/scene` はシーン全体を書く。ボードは共有できるので
（ADR 0017）、2 人が同じボードを開いて別々に描く状況は例外ではない。

版の照合が無いと、後から保存した側が丸ごと勝つ。失われるのは「相手が触った
要素」ではなく相手の作業すべてであり、Excalidraw の undo はブラウザローカルな
ので、消された側に復元手段が無い。しかも警告が出ない。

一方で「ボードのスナップショット / バージョニング」はスコープ外に置いてある。
履歴を持てば 3 方向マージも巻き戻しもできるが、そのために保存の設計を変える
つもりはない。

## 決定

**履歴は持たず、衝突の検知だけを入れる。**

保存リクエストに、編集の基準にしたボードの `updatedAt` を `baseUpdatedAt` として
必須で載せる。現在の版と違えば `409 Conflict` を返し、シーンは書き換えない。
成功時は保存後の版を返し、それが次の保存の基準になる。

- **照合は UPDATE と同じ 1 文で行う**（`WHERE updated_at = ?`）。先に SELECT して
  比べる形にすると、比べてから書くまでの隙間に入った保存を上書きする。照合したい
  相手はまさにその隙間に現れるので、隙間を作った時点で守れない。
- **`baseUpdatedAt` は任意にしない。** 任意にすると API を直接叩く経路で照合を
  素通りでき、防ぎたい後勝ちがそのまま残る（ADR 0010 と同じ理由）。
- **版として使うのは既存の `updated_at`。** 版番号の列を足さないのは、保存が
  `updated_at` を必ず進める以上、2 つ持っても同じものを 2 回持つだけだからである。
- **書けた保存では版を必ず進める。** 時計の読みが前回と同じ（あるいは巻き戻った）
  ときは、基準の 1ns 後にする。検知を時計の分解能に預けない。同じ値を書くと、次に
  来た古い基準がそのまま一致し、照合を置いた意味が無くなる。書けた保存では
  「基準 = そのときの版」なので、基準より後にすれば版は必ず進む。
- **エラーは「無い」と分ける。** 非メンバーには 404 のままにする。版の食い違いと
  して返すと、書けなかった理由からボードの存在を確かめられる（ADR 0016 / 0017）。
- **フロントは 409 を受けても編集を捨てない。** 未保存のまま「他の人が保存した」
  ことを見せる。読み直して揃えると、消えるのは相手ではなくこちらの作業になる。

自動マージも、強制上書きのボタンも入れない。どちらも「システムが自動で判断せず、
状態を見せて開発者に選ばせる」から外れる。

## 結果

同時編集で黙って作業が消えることは無くなった。代わりに、衝突した側は自分の変更を
控えてからボードを開き直すことになる。これは失われるものが「まだ保存していない
自分の変更」だけになったということであり、相手の保存済みの作業が消えるのとは
別の話として扱う。

版は時刻の形をしているが、意味は「何番目の保存か」に近い。書けた保存は必ず値を
進めるので、**検知は時計の分解能に依存しない。** 時計が粗い環境でも、止まっていても、
巻き戻っても、同じ版が 2 度書かれることはない。その代わり `updated_at` は実時刻から
最大で保存回数 × 1ns ずれうるが、表示にも判定にも効かない差である。

既存のクライアントは保存リクエストに `baseUpdatedAt` を含める必要がある。保存の
応答は 204 ではなく 200 になり、次の基準を返す。
