# 0022. 作成した draft issue の本文を記録する

- ステータス: 採用
- 日付: 2026-08-16

## 文脈

`sync_items` は作成した draft issue の `item_id` / `kind` / `title` / `local_id` /
`parent_local_id` を持つが、**本文は持っていなかった。** 本文は解釈結果から作成
リクエストまで運ばれ、GitHub に送られたあと、記録を組み立てるところで写されずに
消えていた。

その結果、「前回作成した N 件」に出せるのはタイトルだけになる。「変更あり」の
注釈で、前回何を作ったのかを開発者が確かめようとしても、いちばん中身のある部分が
見えない。

ここで効いてくるのが、すでに決めてある 2 つの方針である。

- **GitHub → ボードへの逆方向同期は実装しない**（スコープ外、ADR 0007）。記録は
  「etoki が作成した」という事実だけを持ち、GitHub 側の現在を取りに行かない。
- **draft issue の作成は取り消せない**（ADR 0009）。

つまり本文は、**作成の瞬間に控えなければ二度と取れない。** 後から足せる種類の
記録ではない。

## 決定

**`sync_items` に `body` を持ち、GitHub に送った本文をそのまま控える。**

- `ALTER TABLE sync_items ADD COLUMN body TEXT NOT NULL DEFAULT ''`。空文字は
  「記録していなかった頃の run」と「本文が空のまま作った item」の両方を表す。
  区別しないのは、どちらも画面上は「読むものが無い」で同じ扱いになるため。
- **`AnnotationStatus.items` と `CreatedRun.items` で中身を出し分けない。** 同じ
  `SyncItem` が経路によって違う中身になるほうが、後から効いてくる。転送量を
  惜しんで型の意味を曖昧にしない。

判断の軸は ADR 0009 と同じ。**記録漏れと余分な記録を比べると、記録漏れのほうが
取り返しがつかない。** 余分な記録は開発者が run の中身を見れば分かるが、記録して
いない本文は GitHub を直接見に行くしかなく、etoki の画面には item への URL も
無い。

DB が太ることは受け入れる。ADR 0007 が「run は増え続けるが、単一ユーザーの
ローカルツールである以上、当面は問題にならない。肥大化が問題になったら古い run の
削除を別途足す」とすでに態度を決めており、ここでその方針を変える理由は無い。

## 結果

- `ListLatestRunsByBoard` はボード内の全注釈ぶんの本文を毎回運ぶ。注釈の一覧を
  取るたびに転送量が増える。問題になったら、削るのは列ではなく古い run の側。
- 移行前に作られた item は本文を持たない。画面には「本文なし」と出る。**後から
  埋めない。** 埋めるには GitHub を読みに行くことになり、逆方向同期を入れない
  という判断と衝突する。
- 本文は解釈結果でも作成結果でも同じ見え方で出す。作成前の確認（取り消せない
  操作の直前）と、作成後の確認は、見ているものが同じであるため。
