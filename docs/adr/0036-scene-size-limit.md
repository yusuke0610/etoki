# 0036: シーンの保存に上限を置き、超えたら 413 で弾く

ステータス: 採用

## 文脈

保存されるシーンに上限が無かった。フロントは `serializeAsJSON` に
`getFiles()` ごと渡すので、キャンバスに貼った画像が base64 でシーンに乗る。
`boards.scene` は TEXT 列 1 つなので、画像を数枚貼ったボードが数十 MB になり、
保存・一覧・解釈のすべてに効いてくる。

**壊れ方が「保存に失敗する」ではなく「だんだん重くなる」なので気づけない。**
解釈に渡す画像には上限があり、超えたら縮小せず弾くと決めてある（ADR 0018）。
保存側だけ無制限なのは、同じボードに対して言っていることが揃わない。

## 決定

### 超えたら縮小も切り捨てもせずに弾く

ADR 0018 と同じ扱いにする。黙って縮めたり切り捨てたりすると、開発者が描いた
ものが本人の知らないところで消える。保存はシーン全体を書くので、切り捨てる
対象は「余分なデータ」ではなくブレストの中身そのものになる。

上限は `usecase.MaxSceneBytes`（8 MiB）。**解釈に渡せる画像 1 枚
（`MaxImageBytes` = 4 MiB）を base64 で載せてなお余る**ところに置いた。それより
小さいと、解釈できる図を描いたボードが保存できないという逆立ちが起きる。

画像の上限と同じファイル（`internal/usecase/limits.go`）に並べてある。片方だけ
動かすと上の筋が通らなくなるため、次に上げる人が両方を見る形にしておく。

### 400 ではなく 413 を返し、専用の code を持つ

`invalid_input` に畳まない。中身の誤りではなく大きさなので、利用者の打ち手が
「送った内容を直す」ではなく「貼った画像を減らす」になる。畳むと画面はどちらとも
言えない文言しか出せない（ADR 0034）。

写し替えの表は sentinel 1 つにつき 1 つのステータスと code を持つ
（`internal/httpapi/errors.go`）ので、413 を返すには `ErrSceneTooLarge` を
別に立てる必要がある。

### 上限を持つのはサーバーだけ。フロントは事前に判定しない

**保存できない = 描いたものが失われる**ので、押す前に気づかせたくなる。それでも
フロントに上限を持たせない。ADR 0018 で「両方に持たせると、片方だけ変えたときに
どちらの言い分か分からなくなる」と決めており、ここで例外を作ると上限が 2 つに
なる。

失われるわけでもない。413 は保存を拒むだけで、キャンバスの内容はそのまま残り、
未保存のまま編集を続けられる。画面は「貼った画像が大きすぎる」と読める文言を
出し、開発者が画像を減らして保存し直せる（中核思想 3）。

事前に見せたくなったときに足すのは上限の複製ではなく、いまのシーンの大きさの
表示になる。判定はサーバーに置いたまま増やせる。

## 結果

- 画像を貼りすぎたボードは、重くなり続ける代わりに保存の時点で止まる。
- 上限を入れる前に保存された大きいボードは、開けるが保存し直せない。**移行で
  切り詰めることはしない。** 保存できない状態は画面に出るので、貼った画像を
  減らすかどうかは開発者が決める（中核思想 3）。
- 上限は設定可能にしていない。単一ユーザーのローカルツールに調整の余地を
  増やすより、値の根拠を 1 箇所に書いておくほうが後から動かしやすい。
- ハンドラはボディの読み込みにも歯止めを置く（`maxSceneBody`）。判定の正本は
  ユースケース層のままで、**歯止めに当たった側も同じ 413 に写す。** 同じ
  「大きすぎる」がボディの大きさしだいで 400 と 413 に割れないようにするため。
