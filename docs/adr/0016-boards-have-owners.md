# 0016. 単一ユーザー前提を捨て、ボードに所有者を持たせる

- ステータス: 採用
- 日付: 2026-08-08
- ADR 0004 を置き換える

## 文脈

ADR 0004 は「利用者は 1 人、サーバー基盤は無い」を前提に、認証・認可・
マルチテナントを実装しないと決めた。そのうえで、**前提が崩れたら何が壊れるか**を
4 つ挙げていた。

| 0004 が挙げた破綻項目                           | いまの状態                                                   |
| ----------------------------------------------- | ------------------------------------------------------------ |
| リッスンアドレス（誰でも叩ける）                | ADR 0013 の Host / Origin 検証と、この ADR の認可で塞ぐ      |
| 環境変数による資格情報（全員が同じ PAT を共有） | **ADR 0015 で解決済み。** 利用者ごとの GitHub トークンを持つ |
| `boards` に所有者の概念がない                   | **これが残っている。この ADR で塞ぐ**                        |
| 監査ログが存在しない                            | **これも残っている**                                         |

ADR 0015 で「誰であるか」は決まるようになったが、**決まった利用者を誰も見て
いない。** ログインした A が、B のボード ID を知っていれば読み書きできる。
認証だけ入れて認可を入れないのは、鍵をかけずに受付を置いたのと同じ。

もう 1 つ、移行の問題がある。認証を後から有効にすると、それまでのボードは
所有者を持たない。**これを誰のものにするかは自動で決められない。**

## 決定

### 所有者はボードの属性にし、永続化層で絞る

`boards.owner_user_id` を足し、**`BoardRepository` のメソッドに所有者を引数で
渡す。** ctx から暗黙に読ませない。

- 引数にすると、**呼び出し側が所有者を渡し忘れるとコンパイルが通らない。**
  ctx から実装が勝手に読む形だと、絞り忘れても動いてしまう。認可は
  「忘れたら気づける」形で持つ必要がある。
- SQL に `WHERE owner_user_id = ?` が並ぶのが目に見える。

**置き場所は ADR 0017 で改めた。** 所有者は `boards.owner_user_id` を落として
`board_members` の owner の行に移り、永続化層が絞るのは「メンバーかどうか」に
なった。操作者を引数で渡す形と、空文字の扱い（下）はそのまま引き継いでいる。

### 空文字は「認証なしの所有者」1 人を表す

所有者は文字列で、**空文字は無効値ではなく 1 人の所有者**として扱う。

認証を設定していない構成では、利用者 ID が常に空文字になる。つまり全ボードが
「空文字の所有者」のものになり、**これまでどおり全部が見える。** 認証を有効に
すると利用者 ID が入るので、空文字のボード（＝それ以前のもの）は見えなくなる。

規則が 1 つで、認証あり / なし / 移行前 の 3 つが同じ式で説明できる。
「所有者が無い」という特別扱いをコードに持たずに済む。

### 既存ボードは自動で誰のものにもしない

`etoki claim <login>` で明示的に引き受けさせる。**初回ログインした利用者に
自動で寄せない。**

「システムは自動で判断せず、状態を見せて開発者に選ばせる」（中核思想 3）に
沿う。加えて、共有サーバーで 2 人が同じ日に初ログインしたとき、先に入った方が
全部を持っていく、という決まり方は説明できない。

起動時に所有者の無いボードがあれば警告を出す。**黙って見えなくしない。**

### 監査ログはリクエストログに利用者を載せる

`requestLogger` に利用者を足す。専用の監査テーブルは作らない。

0004 が言っていたのは「誰が何をしたか分からない」であって、改竄耐性のある
監査証跡ではない。すでに全リクエストを 1 行ずつ記録しているので、そこに
利用者を足せば「誰が」が埋まる。テーブルを足すと、そこへの書き込み失敗を
どう扱うかという別の問題が増える。

### リッスンアドレスの既定は変えない

`127.0.0.1:8080` のまま。認証を設定していない構成が既定であり続ける以上、
既定を広げるのは危険。**認証を設定したうえで** `ETOKI_ADDR` を広げるのは、
これで初めて意味のある選択になった。

**認証なしでループバックの外にバインドしても止めず、起動時に警告する**（#168、
`etoki.go` の `warnIfExposedWithoutAuth`）。この組み合わせでは全ボードが空文字の
所有者 1 人のものになり、届く範囲の誰もがログインなしで読み書きでき、PAT と
LLM の鍵もそのまま使える。

- **止めない。** 広げるのは利用者が明示的に選んだ設定で、拒むとその選択を後から
  覆すことになる。`ETOKI_ALLOW_UNAUTHENTICATED` のような同意の設定を足す案は、
  既存の構成を壊すわりに、知らせるだけで防げるうっかりとの差が小さいので
  採らなかった。
- **置き場所は `etoki.New`。** `cmd/etoki` に書くと、main を写して使う経路
  （ADR 0001）に警告が付いていかない。バインドに失敗した構成でも出るように、
  組み立てた時点で言う。
- **ループバックの判定は Origin 検証と同じ関数を使う**（`IsLoopbackHost`、
  ADR 0013）。守っている側と知らせる側で、同じ問いに 2 つの答えを持たせない。

## 結果

- ADR 0004 の 4 項目がすべて埋まった。**共有サーバーで動かせる。**
- `BoardRepository` のシグネチャが変わる。所有者を取らないメソッドは無くなる。
- **`sync_runs` は所有者で絞らない。** `board_id` で引く経路しかなく、その
  board を取れるのは所有者だけだから。二重に絞ると、絞り忘れたときに
  どちらが効いているのか分からなくなる。
- 認証を設定していない構成の挙動は変わらない。空文字の所有者 1 人として動く。
- **`etoki claim` を実行するまで、移行前のボードは画面から消える。** 起動時の
  警告でそれと分かるようにしてあるが、驚きではある。自動で寄せる案との
  比較で、説明できる方を採った。
- 利用者を削除してもボードは残る。`owner_user_id` に外部キーを張っていない
  のは、消えた利用者のボードを道連れにしないため（`board_members.user_id` に
  移ったあとも同じ、ADR 0017）。**ただし `claim` では引き受けられない。**
  `claim` が拾うのは空文字の所有者のボードだけで、消えた利用者の ID は行に
  残ったままになる。etoki に利用者を消す経路は無いので、起きるのは DB を直に
  触ったときだけ。
- ADR 0004 の決定のうち、ボード ID はサーバーが発番する UUID で `boards`
  テーブルを唯一の正とする、はそのまま引き継ぐ。
