# 0044: LLM を叩く実行に上限を置く（利用者単位・プロセス内）

ステータス: 採用

## 文脈

解釈のエンドポイントに回数の上限も同時実行の上限も無かった。`WithMaxAttempts`
（既定 3）が抑えているのは **1 回の解釈のなかでの再送**だけで、解釈そのものは
editor 以上なら何回でも叩ける。

**解釈は LLM を叩く外部呼び出しで、課金を伴う。** viewer に解釈を許さないと
決めた理由（ADR 0017）と同じ論理が、回数にも当てはまる。閲覧者に外部呼び出しを
許さないのに、editor には無制限に許しているのは筋が通らない。

前提も変わっている。ADR 0004 が想定していたのは単一ユーザーのローカルツール
だった。ADR 0017 で招待できるようにした時点で、**「叩ける人」が etoki の外側で
増える**構成になった。画像を添えると 1 回あたりのトークンも大きい（最大 4 MiB の
PNG、ADR 0018）。

**LLM を叩く経路は 2 つある。** 解釈と、図のドラフト生成（ADR 0041）。あちらには
会話の上限（`MaxDiagramTurns` / `MaxDiagramChatBytes`）があるが、それは 1 回の
呼び出しに載る量の話で、実行の回数は抑えていない。

ADR 0031 はこの判断を待っていた。実績を保存しないと決めた理由が「表を持つと
『誰の実績か』を決める必要があり、それは実行の上限をどう絞るかと揃えて決める
問いになる」だったため。

## 決定

### 利用者単位で絞る

`port.UserIDFromContext` の操作者ごとに数える。

ボード単位にすると、招待された相手が自分のボードを作れば素通りする。課金の主体は
プロセスが持つ 1 つの API キーなので、絞る軸をボードに置くと課金の主体と軸がずれる。
プロセス全体にすると「他人の使いすぎで自分が止まる」に落ち、429 の理由を見せても
当たった側に打ち手が無い。

**空文字は無効値ではなく「認証なしの操作者」1 人**（ADR 0016）。認証を設定して
いない構成ではその 1 人だけが数えられるので、結果としてプロセス全体の上限と一致
する。認証あり / なしを 1 つの式で説明できるので、「操作者が無い」の特別扱いを
増やさない。

### 対象は LLM を叩く経路すべて。枠は 1 つ

解釈と図のドラフト生成を同じ枠で数える。片方だけ絞ると、絞っていないほうが
抜け道として残る。どちらも同じ API キーで同じモデルを叩き、同じ請求に乗る。

**トークン量で重み付けはしない。** 判定は呼ぶ前に済ませる必要があり（弾くと
決めた呼び出しで課金だけ発生させない）、そのとき消費量はまだ分からない。分かる
のは呼んだ後、つまり払った後。数えられるのは回数までである。

**1 回の解釈は 1 回と数える。** `maxAttempts` の再送は同じ解釈の中の往復なので
増やさない。ADR 0031 が「呼び出し 1 回ぶんではなく解釈 1 回ぶんを積む」と決めた
のと同じ単位にしてある。ログの `attempts` と上限の 1 は別のものを数えている。

### 状態はプロセス内のメモリに置き、保存しない

窓の中の回数も、走っている数も、`usecase.LLMLimiter` がメモリに持つ。再起動すれば
消える。依っているのは `BoardLocks` と同じ前提、つまり SQLite のファイルを複数
プロセスで共有する構成を想定していないこと。**この前提の出どころ（ADR 0004）は
ADR 0016 に置き換えられているが、置き換わったのは「認証を持たない」ほうで、
単一プロセスで動かすことそのものは変わっていない。**

**これは実績の記録ではない。** 窓から出た回数は捨てるので、ADR 0031 が保存しないと
決めた「誰が何トークン使ったか」の表は、ここでは要らない。**あちらの据え置きは
続く。** 上限の軸を利用者単位と決めたことで「誰の実績か」には答えが出たが、それは
表を作る理由にはならない。実績を残したくなったときに改めて決める。

### 同時実行だけ既定で有効にし、回数の既定値は置かない

`ETOKI_LLM_MAX_CONCURRENT` は既定 1。同時実行の上限は「押し間違いの二度押し」を
止めるもので、手で押している限り当たらない。既定で効かせても失うものが無い。

`ETOKI_LLM_RATE_LIMIT` は未設定なら無制限。**回数の既定値は etoki が決められない。**
妥当な値は料金プランと使い方という外の世界の値で決まり、抱えると必ず誰かに合わない。
ADR 0031 が「金額にしない。単価は外の世界の値で、抱えると差し替えるたびに古くなる」と
した理由と同じ。設定したときだけ効く。

**0 を「無制限」と読ませない。** どちらの変数も、設定するなら 1 以上でなければ
起動時に落とす。0 を無制限と読ませると、未設定（既定 1）と 0（無制限）で意味が
逆向きになる。無制限にしたい人は変数を外すか、大きい数を書く。
`ETOKI_LLM_RATE_WINDOW` だけを設定した場合も落とす。効かない設定を黙って受けると、
設定したつもりの上限が外れる（中核思想 3）。

### 枠を取るのは LLM を呼ぶ直前。順序は同時実行 → 回数

判定は認可と入力の検証をすべて通ったあと、`llm.Complete` の直前に置く。

- 認可より手前に置かない。置くと、他人のボード ID を叩くだけで枠を潰せる。
- 入力の検証より手前に置かない。404 や 400 で返るリクエストが枠を食う。
- **同時実行を先に見る。** 逆にすると、同時実行で断ったリクエストが回数だけ
  消費する。弾いたリクエストは、どちらの枠も消費しないのが筋。

**どちらで弾いても LLM を 1 回も呼ばない。** 呼んでから捨てると、課金だけが
発生する（`validateImages` を LLM の手前に置いてあるのと同じ理由）。

### 待たせず 429 で断り、code を 2 つに分ける

同時実行の枠が空くのを待たない。待たせると、ブラウザ側では「止まった」のか
「並んでいる」のかが見えない。**状態を見せて開発者に選ばせる**（中核思想 3）なら、
断って理由を返すほうが正しい。

`rate_limited` と `concurrency_limited` を分ける。**ステータスだけでは打ち手が
決まらない**（ADR 0034）。前者は時間をおく話、後者はいま走っているぶんの終わりを
待つ話で、待つ長さも次にすることも違う。畳むと画面はどちらとも言えない文言しか
出せない。

`BoardLocks` は流用しない。あれは「作成先の固定を判定する側と、その前提を崩す側」を
揃えるためのボード単位の排他で、軸も目的も違う。解釈は何も書かないので直列化する
対象が無い（`DiagramService` が使っていないのと同じ理由）。

### 残り枠は返さない

429 のときに理由を返すだけで、平常時のレスポンスに残り回数を載せない。`Retry-After`
も返さない。

`DiagramDraft.TurnsRemaining` には「上限に当たってから知らせるのでは遅い」という
前例があるが、あれは**必ず効いている**上限で、会話は積み上がるほど直しが効きにくく
なるので押す前に見える必要があった。こちらの回数上限は**設定した構成にしか存在
しない**。無い上限の残りを常時レスポンスに載せることになる。見せたくなったときに
足すのはそのときの判断で、契約は狭いまま始める。

`GET /api/capabilities` にも出さない。あれは「何を設定すれば使えるようになるか」を
見せる口（ADR 0030）で、上限は設定の不足ではない。

## 結果

- 招待した相手が解釈を回し続けても、利用者ごとに止まる。止まるのは本人だけで、
  他の人の解釈は通る。
- **既定の構成では、回数の上限は無い。** 入れたのは同時実行 1 だけなので、
  設定を足さない利用者にとっての変化は「二度押しが 429 になる」ことだけ。
- 上限はプロセスが再起動すると消える。意図的にそうしてある一方、常駐させずに
  使う構成では回数の上限が実質効かない。効かせたい構成は再起動しない前提になる。
- 上限を持つのはサーバーだけ。フロントは残りを数えないし、押す前に止めもしない
  （ADR 0018 / 0038 と同じ扱い）。画面がするのは 429 を読める文言にすることまで。
- `LLMLimiter` は `InterpretationService` と `DiagramService` の**コンストラクタの
  引数**にしてある。任意の設定にすると、片方に渡し忘れたときに絞りが素通りする
  （`BoardLocks` と同じ形）。
