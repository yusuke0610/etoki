# 0029: 検査と LLM への指示を 1 つの表に結ぶ

ステータス: 採用

## 文脈

解釈結果の制約は 2 箇所にあった。

- `domain.Interpretation.Validate` — 出力を弾く検査
- `usecase.interpretationSystemPrompt` — LLM に出す指示

`interpretationSystemPrompt` の直上には「制約は `domain.Interpretation.Validate`
と対応している。片方だけ変えると、守れない指示を出したり、指示していない制約で
弾いたりすることになる」と書いてあった。**その対応は人が覚えているだけで、
どこにも確かめる仕組みが無かった。**

ADR 0028（epic のタイトルの一意性）を入れたとき、実際に片方だけが動いた。検査を
足してプロンプトに書かず、レビューで指摘されるまで気づかなかった。同じ PR の中で
**3 回**、同じ規則を書いた 4 箇所のどれかを直し忘れている。

### なぜ「気をつける」では足りないか

食い違いの向きによって症状が違う。

| 向き                   | 起きること                                                                                                                   |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| 検査にあって指示に無い | **LLM は直しようのない再送を繰り返す。** 何が悪いかは `ValidationError` で伝わるが、最初から避けられたはずの往復が毎回起きる |
| 指示にあって検査に無い | 守らせるつもりの無いことを指示している。出力の質は落ちるが失敗はしない                                                       |

前者は費用が実行のたびに掛かる。**LLM の呼び出しは有料で、再送は上限まで走る**
（ADR 0005）。人の注意力に頼る種類の間違いではない。

## 決定

**制約を `domain.Rules` に宣言し、検査と指示の両方をそこから引く。**

### `ValidationError` は必ず制約を名乗る

`ValidationError` に `Rule RuleID` を足し、組み立てを `newValidationError` に
通した。構造体リテラルを直に書ける限り、`Rule` を書き忘れてもコンパイルは通る。
**関数を通すことで、指摘を足すときに「どの制約か」を必ず選ばせる。**

### プロンプトの制約一覧は `Rules` から組み立てる

`domain.InterpretationConstraints()` が `Rules` を箇条書きにし、
`interpretationSystemPrompt` はそれを埋め込む。**プロンプト側は制約を書き写さない。**
usecase が持つのは役割・出力形式・再送の枠組みだけになった。

`internal/` の外に出る話ではないので、`port/` には出さない。LLM に何をどう伝えるか
は usecase の仕事だが、**「何が妥当か」の文言はドメインの言葉**である。分けると、
検査の隣に指示が無い状態に戻る。

### 指示の無い制約を許す

`Rule.Instruction` が空文字なら「LLM の出力では起こりえない」を意味する。
`previousItemId` の検査がこれにあたる。LLM が出すのは `previousRef` で、
`previousItemId` は `ParseInterpretation` が解決した結果だから、画面や API を
直接叩く経路でしか検査に掛からない（ADR 0026）。

**伝えようのないものを伝えると、出しようのないフィールドの説明がプロンプトに
混ざる。** 例外を認めず全部を載せるほうが仕組みとしては単純だが、単純さのために
プロンプトを汚す判断はしない。

### テストで両方向を塞ぐ

`TestRules_MatchValidation` が固定する。

- 検査が名乗る `RuleID` は必ず `Rules` にある（**検査 → 指示**）
- `Rules` の制約はすべて、それを破る入力で報告される（**指示 → 検査**）

制約を破る入力は制約ごとに 1 つずつ書く。**`Rules` に足したらテストにも足す**
必要があり、足さなければ到達不能として落ちる。

## 結果

**入れた時点で 3 件の食い違いが見つかった。** どれも「検査にあって指示に無い」側
だった。

- `localId` を空にできないこと
- `items` が少なくとも 1 件必要なこと
- 粒度指定（`epic` / `issue`）に従うこと

粒度は `granularityInstruction` が「この範囲は epic 相当です」と伝えていたが、
epic を 1 件以上含めるという規則自体は制約一覧に無かった。規則を `Rules` に移した
ので、`granularityInstruction` はどちらが指定されたかだけを言うようになった。

### 塞げていないもの

**既存の `RuleID` を使い回して、その指示文が実際には覆っていない検査を足す経路。**
文の意味までは機械で見られない。`RuleTitle`（「title は空にできません」）に
「title に改行を入れない」の検査を相乗りさせる、といった形がこれにあたる（#93）。

指摘文と指示文が別物になるなら `RuleID` を分ける、という約束で運用する。

### 制約が増えるとプロンプトが伸びる

`Rules` に足せば必ずプロンプトに出る。**出さない自由が無くなった。** 制約が細かく
なるほど指示が長くなり、LLM が読み落とす確率も上がる。長さが問題になったら、
そのときは「制約を減らす」か「まとめて言い換える」を選ぶ。**表から外して黙って
弾く選択肢は残さない。**
