# 0008. LLM の差し替えは 2 段の継ぎ目で受ける

- ステータス: 採用
- 日付: 2026-08-02

## 文脈

ADR 0005 で既定実装の wire format を Anthropic Messages API 形状に固定し、
「別の形式が必要なら `port.LLMClient` を自前実装して差し込む」と決めた。しかし
実際に想定される差し替えは、粒度の違う 3 通りある。

1. **ローカルで認証なし** — Anthropic 互換プロキシを手元で立てる。wire format も
   認証方式も同じで、鍵が要らないだけ。
2. **社内ゲートウェイ** — wire format は同じだが、認証が `x-api-key` ではなく
   `Authorization: Bearer` や独自ヘッダ。
3. **クラウド基盤への載せ替え** — Bedrock / Vertex AI など。認証も wire format も違う。

ADR 0005 の答えは 3 にしか効かない。1 と 2 まで「`port.LLMClient` を自前実装せよ」
とすると、**リクエスト組み立て・再送との噛み合わせ・エラー変換を丸ごと再実装
させることになる**。差分がヘッダ 1 つでも同じコストがかかる。

一方で、認証方式の分岐を `Config` や `Complete` に持ち込むと、コアが特定の基盤を
意識することになり ADR 0001 の前提が崩れる。「認証方式」という列挙が etoki 側に
生まれた時点で、新しい基盤が出るたびに etoki を変更する構図になる。

## 決定

差し替えを 2 段の継ぎ目で受ける。**どちらの段にも etoki 側の分岐を作らない。**

| 何が違うか | 継ぎ目 | 既定実装 |
| --- | --- | --- |
| 向き先だけ | `Config.BaseURL` | そのまま使う |
| 認証・ヘッダ | `Config.HTTPClient` の `RoundTripper` | そのまま使う |
| wire format | `port.LLMClient` を自前実装（ADR 0005） | 使わない |

あわせて **API キーを任意にする。** 空なら `x-api-key` ヘッダ自体を送らない。

- 鍵が要るかどうかは向き先次第であり、etoki 側では判断できない。必須にすると、
  認証なしのローカルエンドポイントに繋げなくなる。
- 空文字のヘッダを送ると、認証を要求しない相手がかえって弾くことがある。
- 鍵が要るのに未設定なら、呼び出したときに 401 として返る。これは
  「システムは自動で判断せず、状態を見せて開発者に選ばせる」に沿う。

代わりに `BaseURL` は `New` で検証する。綴り間違いを実行時まで持ち越すと、解釈の
失敗として現れて原因の切り分けが遠回りになるため。

## 結果

- ローカル運用は「鍵あり」「鍵なし」のどちらも設定だけで足りる。コードは同じ。
- 認証方式が違う基盤への載せ替えは、利用者が `RoundTripper` を書いて
  `Config.HTTPClient` に差すだけで済む。etoki 側のコードは触らない。
- etoki は認証方式の一覧を持たない。新しい基盤が増えても etoki は変わらない。
- **`New` は API キーの不足を検出しない。** 起動時に気づける範囲が狭くなる代わりに、
  認証不要の構成を素直に扱える。この判断は「LLM 未設定でもサーバーは起動し、
  解釈の実行時にエラーにする」という方針と対になっている。
- `RoundTripper` は etoki のリクエストを書き換えられる。差し込む側の責任で、
  ここは信頼できるコードを置く前提とする（ADR 0004 の単一ユーザー前提の延長）。
