# 0006. GitHub に作るのは epic と issue の 2 階層のみ

- ステータス: 採用
- 日付: 2026-07-29

## 文脈

当初案では Vision LLM に `project / epic / issue` の 3 階層を出力させることに
なっていた。しかし「project」という語がこの設計の中で 2 つの別物を指していた。

- **GitHub Projects v2 の Project** — カンバンボードそのもの。etoki は
  `projectID` を受け取って「そこに入れる」だけで、新しく作ることはない。
- **LLM 出力の `project`** — 階層の最上位ノード。

つまり LLM が `project` を出力しても、GitHub 側に置き場所がなかった。

加えて Projects v2 の draft issue には次の制約がある。

- ラベルを付けられない。
- native な親子関係を持てない（sub-issue は本物の issue 同士の機能であり、
  draft issue は参加できない）。

その結果、種別と親子関係はカスタムフィールドで擬似的に表すしかない。
`Parent` を Text フィールドに親のタイトルで持つのは実質的に手作りの外部キーであり、
GitHub 側は整合性を一切保証しない。**階層が深いほど、この壊れやすいリンクに
依存する箇所が増える。**

さらに、ワークフロー上ユーザーが指定できる粒度は `epic / issue / 指定なし` であり、
そこに `project` は存在しない。

## 決定

- **GitHub に作成するのは `epic` と `issue` の 2 階層のみ。** Project 自体は
  etoki では作らない。
- LLM の出力 JSON はトップレベルに `summary` を持つ。これは **GitHub には作らず**、
  issue 化を実行する前に「LLM がこの囲みをどう解釈したか」を開発者に見せる
  確認材料としてのみ使う。
- 擬似階層のリンクは `epic ← issue` の 1 本だけに限定する。

## 結果

- Text フィールドによる擬似親子リンクが 1 段で済み、破綻の余地が減る。
- `summary` を作成前に提示することで、「システムは自動で判断せず、状態を見せて
  開発者に選ばせる」という方針が LLM の解釈そのものにも適用される。
- 粒度指定（`epic` / `issue` / 指定なし）と LLM 出力の語彙が一致する。
- 囲み範囲が非常に大きい場合に「まとめノード」が GitHub 上に存在しないことになる。
  必要になったら、`summary` を epic として作る選択肢を後から足せる。
