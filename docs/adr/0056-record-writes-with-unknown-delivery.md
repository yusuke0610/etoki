# 0056: 届いたか分からない書き込みも記録し、停止の猶予をその後始末から導く

ステータス: 採用

## 文脈

ADR 0051 で「接続が切れたら作成を止め、作れたぶんは切れない文脈で記録する」と
決めた。それでも「**GitHub に作ったのに記録が無い**」は 2 つの経路で残っていた
（#170）。ADR 0051 自身が「結果」として書き出したものでもある。

1. **応答だけを失った 1 件。** GitHub が受理したあとで通信エラーになる、または
   1 件の上限（`itemWriteTimeout`）が切れると、`applyOne` はエラーを返し、作った
   ID は分からない。`applyItems` は ID の無いものを記録に載せていなかったので、
   その 1 件は消える。**最初の 1 件でこれが起きると、`len(items) == 0` で run
   自体が保存されない。** 3 状態は `uncreated` のままなので、開き直した開発者は
   何も作られていないと判断して作り直し、消せない draft issue が重複する。
2. **停止の猶予を超えた書き込み。** 停止では猶予（10 秒）の半分でリクエストの
   文脈を切るが、書き込み中の 1 件は取り消しから切り離して最大 60 秒待つ。
   残りの 5 秒で返らないと `Shutdown` が先に諦めてプロセスが終わり、**その run
   で先に作れていた項目まで記録されない。** 失われるのは 1 件ではなく run ごと。

## 決定

### 1. 手を付けた 1 件は、結果が分からなくても記録する

`port.SyncItem` に `Confirmed` を足す。false は「失敗した」ではなく
「**GitHub に届いたかどうかを etoki は知らない**」。

- **分からない側に倒す。** ゼロ値は false。詰め替えの経路（`applyOne` →
  `port.SyncItem` → `toSyncItem` → 契約）で 1 つ写し忘れた行は「確かに作った」
  ではなく「分からない」になる。ADR 0043 が結末のゼロ値を成功に倒さなかったのと
  同じ向き。
- **作成では item ID を空のままにする。** 返ってこなかったのだから知らない。
  埋めると、在りもしない item が更新先の照合（ADR 0026）を通る。
- **更新では item ID を載せる。** 相手は分かっていて、分からないのは書き換えが
  届いたかどうかだけ。
- **畳み込み（ADR 0026）には入れない。** あれは「いま GitHub に在るもの」で、
  在るかどうかが分からないものを混ぜると件数が嘘になる。未確定の作成は item ID
  を持たないので、混ぜると空文字が 1 つのグループになり、別々の書き込みが 1 件に
  見える。`AnnotationStatus.items` とは別のリスト（`unconfirmedItems`）で返す。
  分けるのは ADR 0046（シーンから消えた注釈）と同じ理由。
- **解けた不確かさは消す。** あとで同じ item に確定の記録が付いたら、いま GitHub に
  何があるかは分かっている。item ID を持たない未確定の作成は確定させる手段が
  無いので残り続ける。**自動で GitHub に照合しにいかない**（中核思想 3、
  ADR 0051 の「採らなかった案」と同じ）。
- **押し直しの対象から外す**（ADR 0052 の続き）。作成の応答に載った未確定の項目は
  選択が外れ、送り先が分からないものは選び直せない。受理されていた場合、もう一度
  送ると重複する。出口は「GitHub を見る」1 つで、画面はそこへのリンクを出す。

#### 3 状態は変えない

確定が 1 件も無くても、run があるので状態は `created` になる。**これは
「作成済み」という主張ではなく、`uncreated` に戻さないという選択。** 戻すと、
いちばん押しやすい操作（もう一度作る）が消せない重複を生む。ADR 0009 が
「途中失敗でも `created`」と決めたのと同じ形で、件数と `unconfirmedItems` で
何が在るのかを読ませる。

#### 受理されなかった場合まで「分からない」に倒すこと

GitHub が 401 を返しただけの失敗も未確定として記録される。**区別できないから
そうする。** 区別を `port.GitHubClient` の実装に預けると、差し替えた実装しだいで
守りが変わる（ADR 0051 が停止の判断を実装に預けなかったのと同じ）。
余分な記録は run の `error` を読めば分かるが、記録の無い draft issue は GitHub を
直接見るしかない（ADR 0009）。

### 2. 停止の猶予は、作成の後始末を覆う長さにする

`shutdownTimeout` を固定値ではなく `cancelRequestsAfter + usecase.MaxCreationDrain`
から導く。`MaxCreationDrain` は「始めた 1 件を待ち切る」+「run を記録する」の和。

- **`Shutdown` はハンドラが返り次第すぐ戻る。** ここまで待つのは作成の最中に
  止めたときだけで、ふだんの停止の速さは変わらない。
- **待っていることを知らせる。** 黙って数十秒固まると、人は 2 回目の Ctrl-C を
  「効かないから」押す。何を待っているかと、押せば終われること（そのとき記録が
  失われること）をログに出して選ばせる（中核思想 3）。
- **導くことに意味がある。** 固定値だと `itemWriteTimeout` を動かした日に猶予
  だけが取り残され、**エラーにならずに**経路 2 が戻る。

### 採らなかった案: GitHub を呼ぶ前に「これから作る」を記録する

1 件ごとに、呼ぶ前に ID 未確定の行を書いて応答で確定させる案。プロセスが書き込みの
最中に死んでも残るが、`SaveRun` の「run と items を 1 トランザクション」
（ADR 0007）が崩れ、`port.MappingRepository` に確定用のメソッドが要る。
**決定 2 が「プロセスは記録まで生き延びる」を保証するので、この強さは要らない。**
SIGKILL や電源断には結局勝てず、そこは DB が書けないときと同じ扱い（作った item ID を
エラーとログに残す）になる。

### 採らなかった案: 停止のときだけ書き込みを打ち切る

猶予を 10 秒のまま保ち、書き込み中の 1 件を数秒で打ち切って「分からない」として
記録する案。停止は速いが、「いま停止中か」をリクエストの文脈に流す配線が要る。
タブを閉じた場合まで同じ扱いにすると、ADR 0051 が「始めた 1 件は待つ」で減らした
はずの未確定が日常の操作で増える。**止まるのが遅いことのほうが、取り消せない
書き込みが分からなくなることより軽い。**

## 結果

- 作成の最中に何が起きても、GitHub に送った項目は run に残る。3 状態が
  `uncreated` に戻らないので、押し直しによる重複は起きない。
- **「分からない」という状態が画面に出るようになった。** 開発者は GitHub を
  見て確かめ、要るなら手で消す。etoki は消さないし、勝手に作り直さない。
- 受理されなかっただけの失敗も未確定として残る。run の `error` に理由が入って
  いるので読めば分かるが、**確かめるまで消えない**（自動では解けない）。
- 作成の最中に Ctrl-C すると、最長で `cancelRequestsAfter` +
  `usecase.MaxCreationDrain` のあいだ待たされる。**値はここに書き写さない。**
  導出の式が実装にあり、写すと動かした日にここだけが古くなる（ADR 0051 の
  「10 秒」がそうなった）。待っている理由はログに出る。2 回目の Ctrl-C で即座に
  終われるが、そのとき記録は残らない。
- `sync_items.confirmed` は移行時にすべて 1 になる。この列を足す前は、確定した
  ものしか記録できなかったので嘘にならない。
