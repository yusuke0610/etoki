# 0018: 注釈範囲の画像はフロントで書き出し、保存済みシーンと揃ってからだけ渡す

ステータス: 採用

## 文脈

中核思想 2 番「構造は座標から推測せず、LLM に解釈させる」を満たすには、矢印や
グルーピングのように**テキストに現れない情報**を LLM に渡す必要がある。それは
画像でしか渡せない。`port.VisionRequest` は最初から `Images` を持っているが、
供給する経路が無かった。

画像を作れるのはフロントだけである。Excalidraw の `exportToBlob` はブラウザの
canvas に依存しており、Go 側には同等の手段が無い。

ここで前提が 1 つ崩れる。

> 判定は**保存済みシーンが基準**（`internal/CLAUDE.md`）

フロントが書き出す画像は**画面上の未保存の状態**を写す。テキストを保存済み
シーンから、画像を未保存のキャンバスから取ると、同じ 1 回の解釈の中で入力が
食い違う。`content_hash` の入力はテキストだけなので、この食い違いはハッシュにも
現れず、あとから見分けられない。

## 決定

### 画像はフロントで frame 範囲だけを書き出す

`exportToBlob` の `exportingFrame` に注釈の frame を渡し、その範囲だけを PNG に
する。frame 外の要素は写さない。囲みの外にある別の話題まで一緒に渡すと、
「囲んだ範囲を解釈する」という約束が崩れる。

### 未保存の変更があるあいだは解釈させない

保存してからでないと解釈ボタンを押せないようにする。保存直後はキャンバスと
保存済みシーンが一致するので、テキストと画像の由来が揃う。「保存済みシーンが
基準」という原則を 1 箇所に保てる。

**担保は UI 側だけである。** API を直接叩けば、未保存の画面から書き出した画像を
送れてしまう。作成（ADR 0010）ではそこを `contentHash` の照合で塞いだが、解釈では
同じことをしない。理由は副作用の重さが違うため。

- 作成は GitHub に draft issue を作る。作ったものは削除しないので取り消せない。
- 解釈は GitHub に何も作らず `sync_runs` にも書かない。食い違った入力で解釈しても、
  結果が的外れになるだけで、開発者はそれを見て捨てられる（中核思想 3）。

解釈リクエストにハッシュを載せて照合する道（ADR 0010 と同じ形）は取らない。
フロントがハッシュを組み立てない方針（`Interpretation.contentHash` は受け取った
ものをそのまま送り返すだけ）を崩さずに済ませるには、解釈リクエスト用のハッシュを
別途配る経路が要る。取り消せない副作用が無い操作のために、その経路を増やさない。

### 画像は任意。無くても解釈は動く

`image` を必須にしない。画像なしの解釈（テキストのみ）はこれまでどおり成立し、
CLI やスクリプトからの利用も壊れない。ここは ADR 0010 と判断が逆になるが、
理由は同じ「副作用の重さ」である。作成では任意にすると検証を素通りできてしまう
のに対し、解釈では画像が無いことは劣化であって危険ではない。

### 上限を超えた画像は 400 で弾く

サーバー側で 1 枚あたりのバイト数と枚数に上限を置き、超えたら解釈を実行せずに
400 を返す。黙って画像を捨ててテキストだけで解釈すると、開発者が渡したつもりの
情報が入力から消えたことに気づけない。中核思想 3 の「自動で判断せず、状態を見せて
選ばせる」に反する。

**上限はサーバーにだけ持つ。** フロントは `maxWidthOrHeight` で書き出しの解像度を
抑えるが、バイト数の判定は持たない。両方に持たせると、片方だけ変えたときに
「フロントは通すがサーバーが弾く」がどちらの言い分か分からなくなる。

## 結果

- 解釈の入力に、テキストに現れない図の構造が入る。
- 未保存のまま解釈することはできなくなる。保存の往復が 1 つ増える。
- 画像は Excalidraw の描画結果そのものなので、フォントや配色の変化がそのまま
  LLM への入力の変化になる。プロンプト側は画像の見た目に依存した指示を書かない。
- サーバーは画像を保存しない。解釈 1 回のあいだメモリに載るだけで、`boards` にも
  `sync_runs` にも残らない。残すと、シーンとは別に肥大する複製をもう 1 つ持つ
  ことになる。
