# 0072. フロントエンドのソースは機能ごとのディレクトリに置く

- 状態: 採用
- 日付: 2026-10-06

## 背景

`web/src/board/` に、1 階層で 57 ファイル（単体テスト 15 本を含む）が並んで
いた。ボードの一覧、1 枚のボードの画面、注釈のパネル、図のドラフト、メンバー、
作成先の選択と、少なくとも 6 つの関心が同じ場所にある。`web/src/` の直下にも、
アプリの殻（`App.tsx`）と横断する道具（`theme` / `logger` / `storage` など）が
入口のファイルと並んでいた。

**どれがどの関心に属するかは、import を辿らないと分からなかった。** 注釈の
パネルを触るときに要るファイルと、触らなくてよいファイルが並び順で混ざる。
`BoardPage.tsx` からフックを切り出すと（#146）、同じ階層にさらにファイルが増える。

## 決定

**機能（画面と、その中の関心）ごとにディレクトリを分ける。** 単体テストは
対象の隣に置いたままにする。

一覧（`boards/`）と 1 枚のボードの画面（`board/`）を分け、ボードの画面の中は
右のパネルの関心（注釈・図・メンバー・作成先）ごとに下へ分ける。画面をまたいで
使う道具はアプリの殻と一緒に `app/` に置く。**どこに何があるかの一覧は
`web/CLAUDE.md` の「ファイルの置き場所」に置く。** 置き場所は増えていくので、
決めた日の一覧をここに残しても古くなるだけになる。

- **入口と設定が指すファイルは `web/src/` の直下に残す。** `main.tsx`
  （`index.html` が指す）、`test-setup.ts`（`vite.config.ts` が指す）、
  `index.css`。動かしても関心は見えやすくならず、設定の側を書き換える理由だけが
  増える。
- **`index.ts` で束ねて公開する形（barrel）は作らない。** 束ねると、どこから来た名前かが import の行から読めなくなり、循環も起きやすい。
- **ディレクトリをまたぐ import は禁じない。** 一覧（`boards/`）とボードの画面
  （`board/`）は作成先ごとの分け方（`grouping`）やロールの文言を共有する。
  使う側に写すと、片方だけ古くなる。
- **2 つの画面が使うものは、先に使い始めた側に置いたままにする。** 置き場所を
  決めるためだけに共通のディレクトリを作ると、どの画面にも属さないファイルの
  置き場になり、平らな一覧に戻る。

## 採らなかった案

- **種類ごとに分ける（`components/` / `hooks/` / `lib/`）。** 1 つの機能を
  触るたびに 3 か所を開くことになる。注釈のパネルを直すときに、同じ階層に
  図のドラフトのフックが並ぶのは今と変わらない。
- **平らなまま、ファイル名の接頭辞で揃える。** 名前の規則は守られているかを
  機械で確かめられず、ファイルが増えるほど一覧が長くなるのは変わらない。
- **Go のパッケージも組み直す。** バックエンドは依存の方向（ADR 0001）のとおり
  `domain` / `usecase` / `httpapi` / `adapter` に分かれていて、迷う場所が無い。
  パッケージを動かすと import のパスが変わり、`port/` と `etoki.go` を外部から
  使う側にも響く。大きいファイルは同じパッケージの中でファイルに分ける。

## 結果

- 移動は中身を変えずに行った（import のパスとパスを書いた文書だけを直した）。
  `git log --follow` で移動前の履歴を辿れる。
- `.claude/rules/` の `paths` は `web/src/**` の形なので、この分け方では外れない。
  **特定のディレクトリだけに効く rule を書くときは、ここの分け方に合わせる。**
- `index.css` の分割、`App.tsx` と `BoardPage.tsx` からの切り出しは、この
  分け方の上で別に行う。
