# 0017. ボードを共有し、etoki の権限と GitHub の権限を別々に持つ

- ステータス: 採用
- 日付: 2026-08-10
- ADR 0016 を拡張する

## 文脈

ADR 0016 でボードに所有者を持たせ、他人のボードは 404 にした。認可としては
閉じたが、**閉じ方が 1 人 1 ボードだった。** ブレストは 1 人でやるものではない。
同じボードを複数人で描けないなら、ホワイトボードを模した意味が半分無い。

共有を入れると、性質の違う 2 つの権限が同時に効く。

| | 誰が決めるか | 例 |
| --- | --- | --- |
| そのボードを開けるか | **etoki** | 招待された人は開ける |
| その Project に draft issue を作れるか | **GitHub** | 招待されただけの人は作れない |

要件は次の 3 つで、**1 つの権限では表現できない。**

1. ボードの作成にはリポジトリへのアクセス権が要る
2. 招待される人にはリポジトリへのアクセス権が要らない
3. issue / epic の作成にはリポジトリへのアクセス権が要る

「ボードを開ける人」と「GitHub に書ける人」が食い違う状態が、例外ではなく
**普通に起きる**のがこの機能の本体である。

## 決定

### etoki が持つのは「そのボードを開けるか」だけ

`board_members` を足し、GitHub 側の権限は **etoki の DB に複製しない。**

複製は必ず古くなる。GitHub でリポジトリから外された人が、etoki では作成できる
ままになる。しかも etoki は**実行者のトークン**で GitHub を叩く（ADR 0015）ので、
**GitHub 側の権限は複製しなくてもすでに効いている。** 複製は、効いている判定の
手前に、ずれる判定をもう 1 つ置く行為でしかない。

### 作成の可否は GitHub に訊き、判定ではなく状態として見せる

画面に出す「作れるかどうか」は `viewerCanUpdate` を 1 クエリ引いて表示する。
**それを使って弾かない。** 実際の可否は作成時に GitHub が返したものが正しい。

GitHub が返した 403 は専用のエラーに写し、HTTP 403 として返す。いま素通しすると
500 になり、権限の問題だと分からない。

権限が無い相手にボタンを消して黙らせるのではなく、「あなたはこの Project に
書けない」と見せる（中核思想 3）。ブレストには参加できるのだから、できない理由が
分かる形で残っている必要がある。

### 非メンバーは 404、メンバーの権限不足は 403

ADR 0016 の「他人のボードは 404」は保つ。区別すると ID の総当たりで存在を
確かめられる。

一方、**メンバーがボードの存在を知っているのは前提**なので、owner 専用の操作を
断るときは 403 にする。ここを 404 に揃えると、権限が足りないのかボードが消えたのか
利用者が区別できない。**「存在を隠す必要があるか」で分ける。**

### ロールは owner / editor / viewer の 3 つ

| | owner | editor | viewer |
| --- | --- | --- | --- |
| 閲覧・注釈の状態・メンバー一覧 | ✓ | ✓ | ✓ |
| シーン保存 | ✓ | ✓ | |
| 注釈の解釈 | ✓ | ✓ | |
| draft issue の作成 | ✓ | ✓ | |
| 作成先の変更 | ✓ | | |
| 招待・解除・ロール変更 | ✓ | | |

**viewer に解釈を許さない。** 解釈は LLM を叩く外部呼び出しであり、課金も伴う。
閲覧者に外部呼び出しを許すのは「閲覧」ではない。読むだけの人に渡すのは、
すでに etoki の中にある状態（シーンと注釈の 3 状態）までにする。

**ロールの上下は Go に 1 箇所だけ置く**（`port.BoardRole.AtLeast`）。SQL に
ロールの集合を書くと、Go 側の判定と 2 箇所になり、片方だけ変わる。永続化層が
`WHERE` で見るのは「メンバーかどうか」までにとどめる。

### 招待できるのは一度ログインした利用者だけ

招待は login で指すが、`users` に行ができるのはログインしたときだけなので、
**未ログインの login 宛に招待を積まない。**

login は改名で変わるため同定に使えない（ADR 0015）。未ログインの login 宛に
招待を保留すると、改名で空いた login を取った別人がボードに入る。`etoki claim`
が「一度ログインしてから」を要求しているのと同じ制約に揃える。

### ボードの作成に作成先を必須にする

`POST /api/boards` がリポジトリと Project を要求する。作成先の候補は
`projectsV2(minPermissionLevel: WRITE)` で絞ってあるので（ADR 0014）、
**書ける Project を 1 つも持たない人はボードを作れない。** 要件 1 はこれで満ちる。

「使えるリポジトリが 1 件以上あるか」を作成時に確かめる案は採らない。0 件と
権限不足を GitHub の応答から区別できず（`port.GitHubClient` の注記）、そもそも
「どこかに書ける」は「**その** Project に書ける」ではない。

副産物として、「作成先が未選択のボード」が新規には生まれなくなる。画面が
すでに作成先の選択を挟んでいる以上、これは実態に合わせる変更でもある。

### 所有者の単一情報源を `board_members` に移す

`boards.owner_user_id` は落とす。所有者を 2 箇所に持つと、片方だけ更新される
経路が必ずできる。

空文字の所有者（認証なしの構成、ADR 0016）は `user_id = ''` のメンバー行として
同じ式で表せる。認証あり / なし / 移行前 が 1 つの規則で説明できる性質は保たれる。

## 結果

- **editor で招待された人はブレストと解釈までできる。** 作成だけが GitHub に
  阻まれ、それが画面に見えている。
- `BoardRepository` の `owner` 引数は「操作者」になり、絞り込みはメンバーシップの
  結合になる。**引数で渡す形は保つ。** 渡し忘れがコンパイルエラーになる性質は
  共有を入れても手放さない（ADR 0016）。
- `POST /api/boards` の契約が壊れる。フロントは作成先を選んでから作る形になる。
- `sync_runs` は引き続きメンバーで絞らない。`board_id` で引く経路しかなく、その
  board を取れるのはメンバーだけであるという理由がそのまま残る。
- **誰が作ったのかは記録していない。** 共有すると「この draft issue は誰が
  作ったのか」が問いとして立つが、この ADR では扱わない。必要なら
  `sync_runs.created_by_user_id` を足す判断を別に行う。
- 招待リンク（単回・期限つきトークン）は採らなかった。誰が入ってくるかを etoki が
  決められず、「状態を見せて選ばせる」形にならない。owner が login を指す形の方が
  中核思想 3 に沿う。
