# 0043: 途中で失敗した run は記録に残す（埋めずに「不明」を残す）

ステータス: 採用

## 文脈

作成が途中で失敗しても、作れたぶんは run として記録する（ADR 0009）。応答には
`incomplete` と `error` が載るので、画面はその場で「途中で失敗しました」と
出せていた。

**その事実をどこにも保存していなかった。** `sync_runs` の列は `id` /
`board_id` / `annotation_element_id` / `content_hash` / `created_at` だけで、
`port.SyncRun` にも読み口の `SyncRun` スキーマにも失敗を表す項目が無い。手掛かり
が生きているのは応答 1 回ぶんで、リロードすると消える。

そのため、3 件のうち 1 件だけ作れて止まった run と、もともと 1 件だった run が
履歴上で同じに見える。**困るのは「再実行してしまうこと」ではない。** ADR 0009 は
再実行を止めておらず、重複を消すか残すかは開発者が決める（中核思想 3）。実際、
途中で失敗した後は残りを作るために再実行するのが正しい。困るのは、**再実行すべき
かどうかを決める材料が消えていること**である。

見せられる状態を保存していないという意味で、中核思想 3 が成り立っていなかった。

## 決定

**run の結末を保存し、読み口に出す。止めも警告もしない。**

- `sync_runs` に `outcome`（`complete` / `incomplete`）と `error` を足す
  （`migrations/0010_sync_run_outcome.sql`）。`error` は `incomplete` のときだけ
  入る。
- 保存する理由の文字列は、応答に載せるものと同じ（`ErrCreationIncomplete` で
  包んだ全体）。片方だけ包みを剥くと、同じ失敗が 2 通りの見え方になる。GitHub の
  生の文字列であり利用者向けの文言ではないので、画面は畳んで見せる（ADR 0034）。

### 既存の run は NULL のまま「不明」として読む

**`complete` で埋めない。** 列を足す前にも途中失敗は起きていたので、埋めると
「知らないこと」を成功として断言することになる。ADR 0009 が避けたかった誤解に、
移行のほうから落ちる。

`body`（0007）と `action`（0009 のマイグレーション）は既定値で埋めた。あれが
できたのは、埋めた値が事実だと言えたからである（当時は更新の経路が無く、すべて
新規作成だった）。ここは言えない。

3 値になるが、画面のコストはほぼ無い。**何かを言うのは `incomplete` のときだけ**
で、`complete` と「不明」はどちらも何も出さない。区別を残すのは、あとから読む
機能が誤った前提を掴まないようにするためである。

### 書き忘れは「不明」に化けさせない

`SaveRun` は `Outcome` のゼロ値を弾く（`RunOutcome.Valid()` が偽）。NULL は
「記録していなかった頃の run」を表すので、書き忘れを通すとそこに紛れて後から
見分けられない。`Error` と `Outcome` の食い違いも同じ理由で弾く。

### 3 状態は変えない。一覧には別の印として出す

途中で失敗しても作れたぶんは記録するので、状態は `created` のままである
（ADR 0009 の決定）。**そこは動かさない。** 代わりに `AnnotationStatus` に
`lastRunOutcome` を足し、一覧でも分かるようにした。履歴は `<details>` の中に
あり、開かなければ気づけない。翌日戻ってきた開発者がまず見るのは一覧である。

`lastRunOutcome` に理由は載せない。一覧は「何が起きたか」までを見せる場所で、
手掛かりの本文は履歴（`GET .../runs`）が持つ。載せると、ボードを開くたびに全
注釈ぶんの GitHub のエラー文を運ぶことにもなる。

## 結果

- 途中で失敗した run は、開き直しても履歴と一覧から分かる。何件まで作れたのかは
  これまでどおり `items` の内訳で読む。
- **`ListItemsByAnnotation`（畳み込み）は触っていない。** あれは「いま GitHub に
  在るもの」で、run が成功したかどうかとは別の問い（ADR 0026）。
- 記録していなかった頃の run は、これからもずっと「不明」のまま残る。埋め直す
  経路は作らない。作れば同じ嘘をつくことになる。
- **理由の文字列に上限を置いていない。** GitHub の応答をそのまま持つので、長い
  ものは長いまま入る。同じ文字列は以前から応答に載せているので、新しく増えた
  露出は無い。上限が要ると分かったら、そのとき「切った」と分かる形で足す。
