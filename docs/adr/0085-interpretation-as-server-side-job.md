# 0085: 解釈をリクエストから切り離し、サーバー側のジョブとして走らせる

ステータス: 採用

## 文脈

解釈は 1〜数分かかる。リクエストに結びつけていたので、画面を離れると
次のことが起きた（#307）。

- 画面の state（`useInterpretations`）が消え、「解釈が終わった」ように見える。
- ブラウザは接続を切らない（`fetch` に中断の口が無い）。サーバーは解釈を走らせ
  続け、**同時実行の枠（ADR 0044、既定 1）を握ったまま**になる。
- 利用者が押し直すと、走っている解釈に当たって 429（`concurrency_limited`）で
  弾かれる。画面は忘れ、サーバーは覚えているので、食い違いが利用者に見える。

画面の側だけで直す（state を画面の外に持つ）案は、SPA の中の行き来には効くが、
リロードやタブを閉じると同じ食い違いが戻る。**走っているのはサーバーなので、
走っていることを知っているのもサーバーであるべき。**

## 決定

### 始めるのと受け取るのを別のリクエストにする

`POST …/interpret` は LLM の応答を待たず、ジョブを 202 で返す。結果は
`GET …/interpretation-jobs/{jobId}` で取る。画面は終わるまで見に行く（ポーリング）。

解釈は、リクエストの `ctx` から切り離した `ctx`（値は引き継ぎ、キャンセルは
引き継がない）で走らせる。止める手は、利用者の取り消しと上限時間
（既定 10 分）だけ。上限時間が要るのは、応えない LLM に枠を握らせ続けると
次の解釈が弾かれ続けるため。

### 始める時点で弾けるものは弾く

認可、入力の検証、枠の確保までは `POST` の中で行う。404 / 400 / 429 は始める時点で
返り、ジョブにならない（ADR 0044 の「枠を取るのは LLM を叩く直前」のまま）。

### 同じ利用者が同じ注釈を解釈している最中の再実行は、走っているジョブを返す

二度押しや、戻って押し直したときに、同じ入力で LLM を二度叩いて二度課金しない。
一致を見るのは操作者・ボード・注釈と、その保存済みの内容（`AnnotationHash`）で、
保存で内容が変われば別の入力として新しく始める。別の利用者のジョブは返さない
（ジョブは操作者ごとに持ち、枠も操作者ごと）。
別の注釈は、これまでどおり枠に弾かれる（429）。枠が 1 つなのは、手で押している
限り当たらない二度押しの抑止のためで（ADR 0044）、同じ注釈への再実行は
「弾く」より「同じものを返す」ほうが、押した操作と結果が一致する。

### 読んでも消えない。捨てるのは明示的な操作

ジョブの取得は読み取りで、何度読んでも同じ。**取得した時点で消す設計は採らない**
（採らなかった理由: 返事が途中で失われると、課金した結果を二度と取れない）。

要らなくなったら `DELETE` で捨てる。走っているものには取り消し、終わったものには
結果の破棄になる。**どちらも言いたいことは「このジョブはもう要らない」で同じ**
なので、操作を分けない。画面は結果を履歴に積んだら捨てる。保存でも捨てる
（前提のシーンが変わるので、走っているものは止める）。

### 状態はメモリだけに持つ

ジョブはプロセス内に持ち、再起動で消える。ADR 0044（`LLMLimiter`）、`BoardLocks` と
同じく 1 プロセスに閉じる。複数プロセスで動かすと、別のプロセスが持つジョブを
見失い、枠も数え違える。それは `LLMLimiter` と `BoardLocks` がすでに抱えている
制約で、ここで増やさない。
結果はもともとフロントのメモリにしか持たない設計（引いた解釈は保存で捨てる）で、
DB に持つと「保存しない」と決めた判断（ADR 0031）と食い違う。

終わったジョブは終わった時刻から 1 時間で捨てる。走っている間は数えない。

### 見えるのは、始めた本人のそのボードのジョブだけ

他の利用者のジョブも、別のボードのジョブも、存在しないものと同じ 404 を返す
（ADR 0016 / 0017 と同じ理由）。

### 開いたときに 1 回だけ引く

画面はボードを開いたとき、一覧（結果は含まない）を 1 回引き、走っているものと
受け取っていないものを戻す。注釈ごとには引かない。実行の履歴を押されるまで引かない
決め（`web/CLAUDE.md`）と矛盾しない。あちらは注釈の数だけ問い合わせが増える形を
避けるもので、こちらはボードにつき 1 回。

## 採らなかった案

- **画面の外に state を持つ。** 上記のとおり、リロードで戻る。サーバーの枠は
  解放されないままなので、根本が残る。
- **画面を離れたら中断する。** 「ボードを行き来しても実行中を止めたくない」という
  要望に反する。課金した解釈を、画面を移っただけで捨てることにもなる。
- **結果を DB に保存する。** 上記（ADR 0031）。
- **SSE / WebSocket で結果を押す。** ポーリングなら、サーバーが接続の状態を持たずに
  済む。ジョブの状態を引くだけで、途中で切れても次の問い合わせで追いつく。

## 帰結

- `interpretAnnotation` の応答が 200（結果）から 202（ジョブ）に変わる。結果の形
  （`Interpretation`）は変わらず、`InterpretationJob.result` に入る。
- 図のドラフト生成は同じ枠を共有するが、この ADR では扱わない。リクエストに
  結びついたまま。

## 追記（#330）: 画面から取り消す

`DELETE` は用意したが、画面には取り消しの口が無かった。走っている解釈を止める
手段が「保存する」しか無く、上限（10 分）まで枠を握るあいだ、ほかの絵の絵解きと
図のドラフト生成は 429 に弾かれた。注釈の詳細の帯に「絵解きを取り消す」を置く。

- **取り消せるのは、走っているジョブが分かってから。** 始める途中（画像の書き
  出しと、始める要求の往復）では出さない。その間に取り消せると、取り消した要求の
  応答が返ったときにジョブを捨てることになる。同じ絵を押し直していると、上の
  「走っているジョブを返す」で押し直した側も同じジョブを見ているので、そちらの
  ジョブまで捨てる。始める途中は数秒で終わるので、待たせても困らない。
- **サーバーが受けたと分かってから止める。** 返事を待たずに画面だけ止めると、
  取り消しが届かなかったときにジョブは走り続けて枠を握り、開き直すと戻ってくる。
  取り消せなかったら走っている扱いのまま理由を出し、押し直せるようにする。
  404 はもうサーバーに無いので、取り消せたものとして扱う。
- **失敗にはしない。** 押した人が止めたので、失敗の帯で知らせることが無い。前の
  結果と選択は残す。
- **置くのは詳細の帯だけ。** 右上の「絵解き」は押すと詳細を開く（ADR 0077）ので、
  走っているあいだも詳細から止められる。
- 画面を離れただけでは止めない、は変わらない。止めるのは人が押したときだけ。
