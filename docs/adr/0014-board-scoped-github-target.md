# 0014. 作成先の Projects v2 はボードごとに持ち、最初の作成で固定する

- ステータス: 採用
- 日付: 2026-08-08

## 文脈

作成先の Projects v2 は `ETOKI_GITHUB_PROJECT_ID` でプロセス全体に 1 つだけ
固定されていた。ボードが何枚あっても、すべてが同じ Project に draft issue を
吐く。ボードはテーマごとに切って使うものなので、実際には「このボードは A の
リポジトリ、あのボードは B」と分かれてほしい。

分けるにあたって 2 つ決める必要があった。

### 何に紐づけるのか

要望は「ボードはリポジトリに割り当たる」だった。しかし **draft issue は
リポジトリには属さない。** Projects v2 の item として Project の中にだけ存在し、
issue に変換するまでリポジトリとの関係を持たない（ADR 0006 の制約と同根）。

一方 Projects v2 はリポジトリに紐づけられる。つまり利用者から見た「リポジトリを
選ぶ」は、実装としては「そのリポジトリに紐づく Project を選ぶ」になる。

### いつ変更できなくするのか

作成先を後から変えられると、`sync_runs` が壊れる。`sync_runs` は
「GitHub 側に残っている draft issue の追跡表」であって、単なるログではない
（ADR 0007）。記録された `item_id` は特定の Project の中でしか意味を持たない。
作成先を変えると、過去の run が指す item と現在の作成先が食い違い、3 状態判定は
「作成済み」と言うのに GitHub 上のどこを見ればよいか分からなくなる。

かといってボード作成時に固定すると、選び間違いを直せない。ブレストを始める前は
まだ何も GitHub 側に無いので、変えて困る理由が無い。

## 決定

- **作成先はボードの属性として持つ。** `boards` に `repository_owner` /
  `repository_name` / `project_id` を足す。`ETOKI_GITHUB_PROJECT_ID` による
  プロセス全体の固定は廃止する。
- **利用者にはリポジトリを選ばせ、その中から Project を選ばせる** 2 段にする。
  「リポジトリに割り当たる」という利用者の見方と、「draft issue は Project に
  属する」という GitHub の実体の両方を満たす形はこれしかない。
- **固定するのは、そのボードで最初の draft issue を作った時点。** 判定は
  `sync_runs` に 1 件でもあるかどうかで行う。以後の変更は 409 で拒む。
- **固定はユースケース層で守る。** HTTP ハンドラに置かない。
- **作成と作成先の変更は、ボード単位で直列化する。** 判定材料の `sync_runs` は
  作成の最後に書かれるので、作成先を読んでから run を記録するまでの間は「まだ
  run が無い」。そこを突かれると、作成先 A に作った draft issue が作成先 B を
  指すボードの run として残り、固定が防ごうとしていた食い違いがそのまま起きる。
  判定と記録をまたいで排他を取る（`usecase.BoardLocks`）。
- 未選択は 3 列とも空文字で表す。既存のボードは空のまま移行され、開いたときに
  選択画面に入る。

## 結果

- ボードごとに別の Project へ作れる。ボードを「1 つのリポジトリの作業場」として
  使えるようになり、これは etoki の想定した使い方そのものになった。
- **`ETOKI_GITHUB_PROJECT_ID` は廃止。** GitHub クライアントさえあれば作成機能を
  生やし、作成先が未選択のボードは作成の手前で止める。設定不足を起動時ではなく
  ボード単位で見せる形になり、「状態を見せて開発者に選ばせる」に沿う。
- **トークンに必要な権限が増えた。** リポジトリの一覧に repo の read が要る。
  Projects の read/write しか持たない既存トークンでは一覧が 0 件になる。
- 固定をユースケース層に置いたので、HTTP を経由しない呼び出しでも守られる。
  ハンドラに置くと、`BoardService` を直接使う経路が素通りする。ADR 0010 で
  `contentHash` の検証をユースケース層に置いたのと同じ理由。
- **直列化はプロセス内の排他で足りる。** SQLite のファイルを複数プロセスで
  共有する構成は想定していない（ADR 0004）。その前提が変わるなら、排他も
  DB 側に移す必要がある。
- **作成中のボードでは、作成先の変更が作成の完了まで待たされる。** 作成は
  GitHub の応答を何度も待つので、数秒かかりうる。待った先では run が残って
  いるので 409 になる。切断されたリクエストが並び続けないよう、待ちは
  `context` で打ち切れるようにしてある。
- **作成先を間違えたまま 1 件作ってしまうと、そのボードでは直せない。** 復旧は
  ボードを作り直す運用になる。GitHub 側の draft issue を etoki が消さない
  以上（ADR 0009）、追跡表を壊さずに作成先だけ差し替える方法が無い。
