# 0001. 依存の方向とポートの配置

- ステータス: 採用
- 日付: 2026-07-29

## 文脈

etoki は「コアは基盤を意識しない」を前提としており、クラウド固有の認証が必要な
環境では利用者が `LLMClient` を実装して差し込む想定になっている。

当初案ではインターフェースを `internal/port` に置くことになっていた。しかし Go の
`internal/` は他モジュールから import できないため、外部リポジトリが
`LLMClient` を実装しようとしてもインターフェースを参照できず、この差し込みが
言語仕様上成立しない。

同じ理由で、外部リポジトリが独自の `main` を書けるよう、サーバーの組み立て口も
公開されている必要がある。

## 決定

公開面を `internal/` の外に置く。

- `port/` — インターフェースと、その境界で使う DTO。`internal/` に依存しない
  自己完結したパッケージにする。
- `etoki.go`（ルートの `etoki` パッケージ）— サーバーの組み立てと起動。
- それ以外（`domain` / `usecase` / `adapter` / `httpapi`）は `internal/` に閉じる。

`port/` が DTO も抱えることで `internal/domain` を公開せずに済む。ユースケース層が
ドメインモデルと境界 DTO を詰め替える。

`internal/http` は `internal/httpapi` に改名した。パッケージ名が `http` だと、その
パッケージ内で `net/http` を import したときに名前が衝突するため。

## 結果

- 外部リポジトリは `github.com/yusuke0610/etoki/port` を import して独自アダプタを
  実装し、`etoki.New` に渡すことで差し込める。
- `port/` はモジュールの公開 API なので、変更が破壊的変更になる。インターフェースを
  増やす際は慎重に扱う。
- ユースケース層にドメインモデルと境界 DTO の詰め替えコードが発生する。これは
  境界に DTO を置くヘキサゴナルアーキテクチャの定石どおりのコストとして受け入れる。
