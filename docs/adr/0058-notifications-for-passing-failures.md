# 0058: 通知は過ぎ去ってよい失敗のためのもので、残す必要がある状態は通知にしない

ステータス: 採用

## 文脈

画面全体に出す失敗は `App` の `error: Failure | null` 1 本に集まっていた
（issue #89）。これには 3 つの問題があった。

- **後から来た失敗が前を黙って消す。** 保存の失敗の直後に注釈の状態の取得が
  失敗すると、先に出た「保存できませんでした」が消える。開発者が知る必要が
  あるほうが消える。
- **帯がキャンバスの兄弟としてフローに入る。** 出た瞬間にキャンバスの高さが
  削られ、Excalidraw が描き直して描画位置がずれる。ブレストの最中に、ツールの
  都合で手が止まる（中核思想 1）。
- **閉じる以外の出口が無い。** 保存に失敗したら、帯を読んでからヘッダーの
  「保存」を探して押し直すことになる。

一方で、画面に出ている失敗の表示にはこの帯以外のもの（保存の衝突、注釈ごとの
解釈・作成の失敗、部分失敗、フォームの入力に対する応答）もある。これらを
「通知」としてまとめると、見た目は揃うが、**消えた瞬間に読めなくなる。**

## 決定

**通知は「過ぎ去ってよい失敗」の器として足し、`App` の 1 本の帯だけを置き換える。
残して読ませる状態は通知にしない。**

何をどこに出すかの表は `web/CLAUDE.md`（「画面全体に出す失敗は通知で」）にある。
ここに書くのは、その線の引き方の理由だけ。

- **保存の衝突は帯のまま。** 失敗ではなく状態で、上書きしていないことと次に
  どうするかを読ませる必要がある（ADR 0020）。通知にして閉じられると、相手の
  変更を消したのかどうかが読めなくなる。
- **解釈・作成の失敗と部分失敗は注釈のパネルに残す。** どの注釈で起きたかが
  情報の一部で、部分失敗は作られた draft issue の一覧と一体である。消えると
  何が GitHub に残ったか分からなくなり、重複作成を招く（ADR 0009）。
- **フォームへの応答は入力欄の隣に残す。** 通知にすると、どの操作の結果かが
  入力欄から離れた場所で読まれる。
- **成功は通知にしない。** 保存の成功は「未保存」の消灯で、作成の成功は作成結果
  の一覧で既に示している。同じ事実が 2 箇所に出ると、どちらが状態でどちらが
  履歴か読めなくなる（中核思想 3 の「状態を見せる」は、状態表示のほうが本体と
  いう意味）。型としては `success` / `info` / `warning` も持つが、呼び出し元は
  作らない。

器の形:

- **フローの外に出す**（`position: fixed`）。キャンバスの寸法を変えない。
- **最大 3 件。** 超えたら古いものから落とす。同じ `key` は積まずに置き換え、
  同じ失敗の繰り返しで上限を埋めない。
- **`error` / `warning` は自動で消さない。** 次の一手（`action`）を持つ通知も
  消さない。消える瞬間に押そうとした手が空振りする。
- **押し直して解けるものにだけ「再試行」を付ける。** 保存（409 と 413 以外）と
  ボード一覧の取得。直ったら同じ `key` で下げる。残すと、保存できているのに
  「保存できませんでした」が読める。
- **フォーカスを奪わない。** 出た瞬間にフォーカスが飛ぶと、描いている手が止まる。
- **状態の置き場所は React 標準の Context 1 つ。** etoki は状態を `useState` と
  props で降ろす形で、グローバルな store を持たない。通知だけは深い位置から
  出すので props では降ろせないが、ライブラリは足さない。持たせるのは通知の
  並びと出し入れの口だけで、他の状態を相乗りさせない。

## 採らなかった案

- **既存の失敗表示をすべて通知に寄せる。** 見た目と読み上げは 1 箇所に揃うが、
  上に書いた「残して読ませる状態」が消えるようになる。揃える利益より、読めなく
  なる損のほうが大きい。
- **トーストのライブラリを入れる。** React は `@excalidraw/excalidraw` との組み
  合わせで 18 系に固定してあり、この固定に他の依存を巻き込みたくない。必要な
  機能（上限、置き換え、時間で消える、止める）は 100 行程度で足りる。
- **`createPortal` で body に出す。** `position: fixed` の入れ物を `.app` の中に
  1 つ置けば足り、DOM ノードの管理を自分で持たずに済む。

## 結果

- 2 つの失敗が同時に起きても両方読める。キャンバスの寸法は変わらない。
- 保存の失敗とボード一覧の取得失敗から、その場で押し直せる。
- **`role="alert"` が画面に同時に複数出うる状態は残る。** 通知とフォーム内の
  失敗（`RepositoryPicker` など）が同時に出る組み合わせがある。フォーム側を
  `aria-describedby` で入力と結ぶ形に変えれば解けるが、フォームごとに読み上げの
  扱いを決める必要があり、この変更には含めない。
