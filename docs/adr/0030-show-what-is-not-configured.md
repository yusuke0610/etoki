# 0030: 使えない機能は押す前に見せる（プロセスの設定と利用者の権限を分ける）

ステータス: 採用

## 文脈

LLM や GitHub を設定しなくても etoki は起動する（ADR 0008）。README も
「**LLM を設定しなくても起動します**。ブレストだけ先にやる、という使い方を
潰さないため」と書いている。

サーバー側はその前提で作ってある。`httpapi.Deps` は `Interpretations` /
`Creations` / `Catalog` / `Members` / `Access` の nil を許し、nil のときは
**404 ではなく 503** を返す（「機能が無い」のか「URL が違う」のかを区別できる
ようにするため）。

**画面はそれを先に知る手段を持っていなかった。** 「解釈する」は常に押せて、
押してから 503 が出る。ADR 0034 で文言は読めるようになったが、**読めるのは
押した後**である。

作成先の権限（`projectAccess`）については既に先に見せる形になっていて
（`denied` ならボタンを出さずに理由を出す、ADR 0017）、同じ考え方が「そもそも
設定されていない」には適用されていなかった。

## 決定

**`GET /api/capabilities` を新設し、いま使える機能を返す。**

### なぜ新しい口なのか

| 案                                 | 採らなかった理由                                                                                                          |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| `/api/auth/session` に足す         | あれは「誰であるか」を返す口。プロセスの設定を混ぜると、認証を差し替えたときに関係の無いものまで動く（ADR 0015 の継ぎ目） |
| `/api/boards/{id}/access` を広げる | あれは**ボード単位**。プロセスの設定をボードごとに返すと、ボードによって違いうるように読める                              |

**プロセスの設定と利用者の権限を 1 つに畳まない。** 「GitHub は設定されて
いるが自分は書けない」は普通に起きる（ADR 0017）。畳むと、その状態を表現でき
なくなる。

認証の内側に置く。設定の内訳を未ログインの相手に並べて見せる理由が無い。

### 返すのは 3 つだけ

`interpretation` / `creation` / `sharing`。**使う側がいない値を契約に置かない。**

- `catalog`（作成先の候補）は `creation` に畳んだ。同じ GitHub の設定で決まり、
  片方だけ nil になる配線は `cmd/etoki` に無い。
- 作成先の選択画面（`RepositoryPicker`）には**入れていない。** あの画面は開いた
  瞬間に候補を引くので、押す前に見せる必要が無い。503 はそのまま
  `ErrorNotice` に理由として出る（ADR 0034）。

### 文言を 2 つ持たない

**画面は capability から `ErrorCode` を引き、文言は `ERROR_MESSAGES` から取る**
（`web/src/capability.ts`）。押す前に出す文言と、押した後に 503 で返る理由が
別々になると、片方だけ古くなる。**同じ原因には同じ文**にする。

`*_not_configured` を 1 つの code に畳んでいないのはこのため（ADR 0034）。
設定するものが違うので、畳むと「何を設定すればよいか」を言えない。

### 引けていないうちは止めない

`capabilities` が null（まだ引けていない、または引けなかった）ときは**押させる。**
使えない側に倒すと、確かめていないことを確かめたように見せることになる
（中核思想 3）。押せば 503 が返り、同じ文言が出る。`projectAccess` の `unknown`
を `denied` に倒さないのと同じ判断。

### 消さずに理由を出す

- **「解釈する」は消さずに disabled にし、理由を添える。** 消すと、その構成では
  そもそも解釈という機能があることが分からない。
- **理由はパネルに 1 つだけ出す。** 注釈ごとに同じ文を並べると、読むべき状態が
  埋もれる。押せないボタンはフォーカスも当たらないので、`aria-describedby` で
  その 1 つを指す。
- 「メンバー」はボタンの代わりに理由を出す。押せないボタンを残しても、開く先の
  パネルが 503 しか出せない。作成先の変更を owner 以外に出さないのと同じ形。

## 結果

LLM を設定していない構成でも、画面は「いま何ができないか」と「何を設定すれば
よいか」を先に出せるようになった。`web/e2e/capabilities.spec.ts` が 3 つの構成と
「引けなかったときは止めない」を固定している。

**押す前の案内と押した後の 503 が食い違わないことは、サーバー側のテストが
見ている**（`TestGetCapabilities_MatchesUnavailableEndpoints`）。判定材料は同じ
`handlers` の nil なので、片方だけ変えるとそこで落ちる。

残したもの:

- **ボードを作る導線には出していない。** GitHub が未設定だと作成先を選べず、
  結果としてボードを作れない（ADR 0017）。いまはその理由が選択画面まで進んで
  から出る。手前（サイドバー）に出すかどうかは #62 の UI 見直しで判断する。
- **`capabilities` を引き直さない。** 設定はプロセスの起動時に決まるので、
  画面を開いているあいだに変わらない。変わるなら etoki が再起動している。
