# 0096. 人がつないだ矢印の結び先は、解釈に文字でも渡す

- 状態: 採用
- 日付: 2026-11-01
- ADR 0047 が「設計を見直す合図」とした、矢印の始点・終点を読む口を足す。
  守れていることの印を言い直す
- ADR 0018 の「矢印は画像でしか渡せない」を、人がつないだ矢印について改める

## 背景

「絵解きで作る issue に中身が無い」という相談があった。認証のシーケンス図を
絵解くと、「認証処理」のように矢印のラベルを言い換えただけの issue が並ぶ。

解釈に渡しているのは、囲みのテキストの一覧と、囲みを写した画像（ADR 0018）
である。テキストの一覧には矢印のラベルしか並ばず、**誰から誰へのやり取りか
は画像にしか無い。** ADR 0018 は「矢印やグルーピングはテキストに現れないので、
画像でしか渡せない」とした。

実物の LLM（Ollama の `gemma3:4b`）で、5 種類の図（シーケンス図・やること・
マインドマップ・ER 図・システム構成図）を比べた。画像は本物の画面で「絵解く」を
押したときに送られるものを使った。小さいモデルは画像から矢印の向きと結び先を
読み取れず、ラベルを言い換えるだけになった。矢印のつながりを文字でも渡すと、
次のように変わった（各 2 回の平均。折り返しと出力例の修正（#413）も入れた
条件で比べた）。

| 図             | 矢印（始点・終点・ラベル）が 1 つの項目にそろった割合 |
| -------------- | ----------------------------------------------------- |
| シーケンス図   | 33% → 67%                                             |
| システム構成図 | 0% → 75%                                              |
| マインドマップ | 25% → 67%                                             |

シーケンス図では、epic の本文に「ユーザーが WebApp にリクエストを送る → WebApp が
Database から認証情報を取る → …」と流れが正しい向きでそろい、issue にも主語と
相手が入った。

ADR 0047 は、中核思想 2 を守れていることの印を「`domain.Element` に図の構造を
読む口（矢印の始点・終点、座標、大きさ）が無いこと」とし、矢印の始点・終点を
読む口を足したくなったら設計を見直す合図、としていた。この ADR がその見直しで
ある。

## 決定

### 人がつないだ矢印の結び先とラベルを、テキストの後ろに節として渡す

囲みの中の矢印のうち、少なくとも一方の端が何かにつながっているものについて、
結び先の名前と矢印のラベルを 1 行ずつ並べる。

```text
囲みの中の矢印（描いた人がつないだ先。並びは図の上の順番とは限りません）:
- User → WebApp「リクエスト送信 (例: ログイン)」
- Database ― WebApp「認証結果」
```

- **向きは矢じりで表す**（`→` / `←` / `↔` / `―`）。つないだ順（始点・終点）では
  ない。矢じりの無い線は向きを書かない。
- **名前は結び先の文字**（図形のラベルか、テキスト要素そのもの）で、折り返す前の
  文字にする（#413）。
- **並べ替えない。** 要素の順のまま渡し、その順に意味が無いことを書く。上下の
  位置で並べると、座標から順序を決めることになる。順番は画像で読む。

### 読むのは Excalidraw が書いた結び先だけ。座標は読まない

結び先は、人が矢印を図形につないだときに Excalidraw が書き込む
`startBinding` / `endBinding` から取る。**etoki が座標や近さから「この矢印は
あの図形に向いている」と決めることはしない。** 帰属を `frameId` /
`containerId` で辿るのと同じ扱いで、ADR 0047 自身がそれを中核思想 2 に反しない
読み方としている。

**矢印が何を意味するかは書かない。** 「呼び出し」「親子」「1 対多」と読むのは
LLM で、種別ごとに書き分けもしない（ADR 0047 の「種別から図の読み方を導く
実装を書かない」は変わらない）。

### 守れていることの印を言い直す

ADR 0047 の印は「`domain.Element` に図の構造を読む口が無いこと」だった。これを
次のように言い直す。

**`domain.Element` が読むのは、人が置いたり、つないだりした事実
（`frameId` / `containerId` / `startBinding` / `endBinding`）までで、座標と
大きさを読む口が無いこと。** 座標や大きさを読みたくなったら、そこが設計を
見直す合図である。

### 囲みの外の結び先は名前を出さない

囲みの外の要素につないだ端は「囲みの外」とだけ書く。解釈の入力は囲みの中身
だけで、外の材料は背景として別に渡す（ADR 0093）。

### つながっていない矢印は渡さない

どちらの端もつながっていない矢印には、結び先の事実が無い。ラベルはテキストの
一覧にすでに入っている。

### ジョブの鍵には入れ、ハッシュには入れない（いまは）

- **ジョブの鍵には入れる。** テキストを変えずに矢印をつなぎ直した保存でも、
  LLM に渡すものは変わる。入れないと、古いつながりで走っているジョブが返る
  （ADR 0085、0093 と同じ理由）。
- **`content_hash` にはまだ入れない。** ADR 0047 の追記（#301）が矢印を
  ハッシュに入れない理由にしていた「始点・終点を読む口が要る」は、この ADR で
  無くなった。ADR 0093 の基準（囲みの中に人が書いたもの）に照らせば入れる側
  にも見える。ただし入れると、矢印を持つ作成済みの注釈が一度だけ一斉に
  「変更あり」になる。図形の幅を変えると折り返しが変わってハッシュが動く件
  （#413 で見つけた）を直すときにも同じことが起きるので、**ハッシュの入力の
  見直しは 2 つをまとめて別に決める。**

## 検討したが採らなかった案

### 画像だけに任せる（ADR 0047 の線を守る）

モデルの画像を読む力が上がれば済む、という考え方。この端末で動かせる
モデル（`gemma3:4b`）は読めなかった。より大きいモデル（`qwen3-vl:8b`）は、
文脈の長さと etoki の待ち時間の上限（5 分）に収まらず比べられなかった。手元の
LLM に向ける使い方は支えている構成の 1 つで（ADR 0008）、そこで動かせるモデルで
絵解きが成り立たないのは重い。

### 矢印を上下の位置で並べて渡す

シーケンス図の順番をテキストでも渡せるが、座標から順序を決めることになる
（中核思想 2）。順番は画像に任せる。

### 種別ごとに矢印の読み方を添える

「シーケンス図なら矢印は呼び出し」とプロンプトに書けば小さいモデルでも当たる
かもしれないが、ADR 0047 がはっきり禁じている。

## 影響

- **小さいモデルでも、矢印で描いた流れが issue に載る。** シーケンス図・
  システム構成図・マインドマップで効いた。
- **位置で表した構造は変わらない。** ER 図の属性（箱の中に置いた文字）や境界の
  入れ子は、結び先を持たないので文字では渡らない。読めるかは画像を読む力
  しだいで、`gemma3:4b` では関連（1 対 多）も属性の持ち主も取り違えた。
- **矢印をつなぎ直しても状態は「作成済み」のまま。** 上のとおり、ハッシュの
  入力の見直しで決める。
