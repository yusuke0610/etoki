# PR の見回り

複数の PR について、**full review の枠を使う順番を決め、依頼し、結果を読む。**
出すのは「この PR の full review の指摘は決着した」まで。決着の条件と、
full review が要る PR（変更の重さ）の正本は `CONTRIBUTING.md`「マージ」。

| 頼まれたこと                         | スキル       |
| ------------------------------------ | ------------ |
| 枠と順番を回し、決着したかを判定する | `/pr-watch`  |
| 1 本の PR に付いた指摘に答える       | `/pr-review` |
| マージしてよいかを確かめ、マージする | `/land`      |
| main が進んだあと、PR を追従させる   | `/sync-prs`  |

**指摘への対応の手順はここに写さない。** 指摘が付いたら `/pr-review` を呼ぶ。
指摘への対応だけを頼まれたときに、見回りの手順まで読み込まずに済むように
分けてある（#398）。

## レビューは自動では付かない

**このリポジトリでは、PR を作っても CodeRabbit のレビューは付かない。** スター数
が少ないリポジトリは自動レビューの対象外で、要約のコメントは「This repository
does not receive automatic reviews」と「Trigger review」の欄を出したまま
止まる。Dependabot の PR は「Bot user detected」で止まる。

**レビューは `@coderabbitai full review` で依頼して初めて付く。** 増分の
`@coderabbitai review` はマージの条件にならない（`CONTRIBUTING.md`「マージ」）
ので、依頼するのは常に full review。

**軽い PR（文書・規約とスキル・テストだけ）と Dependabot の PR には依頼しない。**
軽い PR は条件が CI だけで、枠を使っても条件は変わらない。Dependabot の PR は
CodeRabbit が飛ばし、依頼しても「Review skipped」で終わる（#424）。軽いのは
Dependabot の PR のうち依存の更新と生成物の作り直しだけのもの。人がほかの変更を
足したものは、足した変更の重さで決める。ふつうか重いに当たれば、full review を
通せないまま `/land` がユーザーに渡す（`CONTRIBUTING.md`「マージ」）。

## 状態を見る

```sh
.claude/skills/pr-watch/status.sh          # 開いている PR すべて
.claude/skills/pr-watch/status.sh 394 375  # 番号で絞る
```

1 PR 1 行で出る。

| 列          | 中身                                                                         |
| ----------- | ---------------------------------------------------------------------------- |
| `head`      | いまの head                                                                  |
| `fr`        | 最後の full review の状態（下の「full review の読み方」）                    |
| `threads`   | CodeRabbit の未解決スレッドの数。取れなければ `?`（0 件とは読まない）        |
| `mergeable` | `mergeable` と `mergeable_state`（`clean` / `dirty` / `blocked` など）       |
| `ci`        | Actions の check-run と run。`未起動` は衝突を疑う（下の「CI が走らない」）  |
| `base`      | base のブランチ。`main` 以外は積んだ PR                                      |
| `=>`        | **`full review 決着` が出たものだけが、マージの条件の full review を満たす** |

`ci` は GitHub Actions の check-run とワークフローの run だけを見る。CodeRabbit
などほかの App の check-run は数えない（CodeRabbit は `skipped` を付けるので、
数えると CI が起動していないのに `緑` と出る）。run が 1 本でも終わっていなければ
`走行中`。

最後の行に、直近に終わった full review の時刻が出る。枠の目安に使う。

クラウドのセッションでは GraphQL が塞がれている。`status.sh` は REST だけで
引き、スレッドはプロキシの経路（`ccr/review_threads`）に切り替える。こちらは
書き手で絞れないので、**人が立てたスレッドも数える。**

## full review の読み方

**いちばん間違えやすいところ。** `status.sh` が判定まで出すが、読み方を知らない
と出力を疑えないので、ここに書く。

**決着は 2 通り**（`CONTRIBUTING.md`「マージ」）。

- **`済(head を読んで 0 件)`。** いまの head を読んだ full review が、指摘を 1 件も
  出さなかった。下の 1〜4 を全部通ったときだけ出る。
- **`決着済み(…)`。** 最後の full review が終わったあとに、PR の作者がまとめ
  （印 `<!-- etoki:findings-settled head=<sha> -->` を持つコメント。`/pr-review`
  の「まとめを書く」）を書いた。full review のあとに head が進んでいても、指摘が
  付いていてもよい。**ただし、印の head がいまの head と違えば決着と読まない**
  （`まとめは … まで`）。まとめが言えるのは印の head までのコミットのことで、
  そのあとのコミットが直しかどうかを `status.sh` は見分けられない。時刻では
  比べない（前に push した commit へ戻すと、その commit の時刻は古いまま）。
  **まとめのあとに指摘が付いたときも決着と読まない**（`…件付いた`）。本文に
  だけ載る指摘はスレッドに出ないので、ここでしか見えない。
  **まとめを書くのは、指摘を全部決着させ、そのあとのコミットが直しか main の
  取り込みだけのとき。** 直し以外を積んだなら、まとめで済ませずに依頼し直す。
  印は誰でも書けるので、PR の作者が書いたものだけを数える。

どちらも、未解決のスレッドが 0 でなければ `=> full review 決着` は出ない。
まとめのあとに依頼し直したら、そのまとめは前の full review のものになり、次の
full review が終わってから書き直す。

1. **依頼より後に head が進んでいたら、その full review はいまの head を読んで
   いない**（`依頼のあとに head が進んだ`）。docs だけのコミットでも同じ。0 件でも
   `済` にはならず、まとめが要る。head の時刻は
   committer の日付と、GitHub がこの PR の枝でその commit を最初に受けた時刻
   （その枝の最も古い check-suite）の遅いほう。committer の日付は古いまま push
   できる。PR の枝の check-suite が無い（別の枝へ先に push した commit など）とき
   は `head の時刻を取れなかった` と出し、`済` と読まない。依頼と同じ秒の push と、
   依頼のあとの force push（前にこの枝にあった commit へ戻すと check-suite の
   時刻は古いまま）も、head が進んだと読む。
2. **依頼への返信を見る。** 返信は 1 つのコメントで、中身が書き換わる。
   - `triggered` のうちは**走っている**（`走行中`）。**ここで決着と読まない。**
     #256 は走行中を 0 件と読んでマージし、指摘がマージの後に付いた。
   - `Full review finished` になったら走り終えた。
   - `Action not completed` / `Review rate limited` は枠切れ（`枠切れ`）。
     その依頼では走らないので、`available in N minutes` の後に**依頼し直す。**
3. **走り終えたら、要約が読んだ commit を見る**（`読んだのは …`）。
   要約の「between A and B」の B が、full review が読んだ head。**B がいまの
   head と一致しなければ、そのレビューは古い。** 要約がこの行を持たず、読んだ
   commit が HTML コメントの `"coveredCommitId":"<sha>","kind":"reviewed"` に
   だけあることもある。`status.sh` はどちらも読み、どちらも無ければ `?` を出す。
4. **review が増えたかどうかでは判定しない。** 指摘 0 件の full review は、
   review を付けないことも、pre-merge check の案内だけを載せた review を付ける
   こともある（#414 の 5821456498）。`.claude/skills/pr-review/findings.sh` の
   1 行目（review の件数）では判定しない。判定は
   「head を読んだ」「その依頼のあとに指摘が 1 件も付いていない」「未解決
   スレッド 0」の 3 つで行う。**返信して解決しただけでは `済` にならない。**
   直さないと返して解決したものも同じで、まとめを書いて `決着済み` にする。
   スレッドの数だけで見ると、指摘を出した full review を 0 件と読む。
   **review 本文は件数行（`Actionable comments posted: N`）を持たないことがある。**
   `status.sh` は本文の節の見出しの数を足し、それも無いのに文字が残る本文は
   件数を `?` と出す（数えた分に足りないかもしれないときは `N+`）。0 件とは読まず、
   本文を開いて読む。

**要約の `updated_at` だけでは判定しない。** 要約は full review のあとに push
しただけでも書き換わる（「Trigger review」の欄が新しい head を指す）。
`updated_at` が依頼より後でも、読んだ commit が古いことがある（#394）。
**逆に、full review が終わってから 5 分より後に書き換わった要約も信じない**
（`要約が full review のあとに書き換わった`）。増分のレビューが別の
head を読んで書き換えたのかもしれない。古い committer の日付のコミットを依頼の
あとに push し、増分のレビューが要約を書き換えると、この形になる。**依頼の
あとに `@coderabbitai review`（増分）を頼んでいたら、5 分以内でもいまの head を
読んだとは言わない。** 要約の commit が、どちらのレビューが読んだものか言えない。自動のレビューは
止めてあるので、増分が走るのはこの依頼か、要約の「Trigger review」の欄を押した
ときだけ。欄を押したことはコメントに残らないので、5 分の比べでしか見えない
（だから欄は押さない。「やらないこと」）。

## 枠の使い方

**full review の枠は org 全体で 1 時間に 1 本。** 走り終えるまで 6〜10 分
かかる。PR が複数あるときは、1 本ずつ順番に回す。

### 枠を使う PR を選ぶ

**マージ順の表（`/land`）の先頭から使う。** 決着しても、先に入れるものが
入らないとマージできない PR に枠を使っても、その枠は先送りされるだけ。積んだ
PR は表で下の段が先に来るので、この順で回せば下の段から埋まる。

表がまだ無いときは `/land` の「表を出す」で作る。番号の小さい順は採らない。
番号は作った順で、入れる順ではない。

### 依頼する前に揃えるもの

**枠は 1 時間に 1 本なので、依頼してから直すことになる状態では依頼しない。**

- CI が緑（走行中なら待つ）
- `mergeable` が `clean`。衝突しているなら `/sync-prs` で先に取り込む。
  依頼のあとに取り込むと、0 件でもまとめが要るようになる
- 未解決のスレッドが 0（前回の指摘を全部決着させた）
- 直すものはまとめて push し終えた

揃っている PR が無いなら、その回は依頼しない。

### 依頼と待ち

```sh
gh api -X POST "repos/{owner}/{repo}/issues/<番号>/comments" -f body='@coderabbitai full review'
```

1. **依頼したら、返信が `Full review finished` か `rate limited` になるまで待つ。**
   `status.sh <番号>` の `fr` が `走行中` から変わるのを見る。
2. **`Full review finished` が出たら、`status.sh` の `=>` と `fr` で判定する。**
   `=>` に出るのは決着したときの `full review 決着` だけで、決着していなければ
   空になる。そのときは `fr` と `threads` で次を選ぶ。
   - `=>` が `full review 決着` → 「決着したら」へ。
   - `fr` が `決着待ち(…)` → `/pr-review` で全部決着させ、まとめを書く。**直して
     push しても依頼し直さない。** 依頼し直すのは、直し以外を積んだときだけ
     （上の「full review の読み方」）。`fr` の括弧の中に、まとめを書き直すか依頼し
     直すかの手がかりが出る。
   - `fr` が `済(…)` か `決着済み(…)` で、`threads` が 1 以上 → 未解決の
     スレッドが残っている。`/pr-review` で決着させて解決する。
   - `threads` が `?` → スレッドの数を取れなかった。残っているとも 0 件とも
     読まず、`status.sh` を取り直す。
3. **`rate limited` なら、`available in N minutes` の後に依頼し直す。** 枠の
   読みが外れたということなので、そのあいだに他の PR に依頼しない。

## 決着したら

マージに進むかを `/land` に渡す。**このスキルはマージしない。** 変更の重さ
（Claude がマージしてよいか）を決めるのも `/land`。

指摘の件数（`docs/review-findings.md`）は 2026-11-25 に記録を止めたので、書かない。

## 見回りの間隔

`/loop` で回すときの間隔は、**待っているものから決める。**

| 待っているもの                        | 次に見るまで                                       |
| ------------------------------------- | -------------------------------------------------- |
| full review の結果                    | 返信の時刻から 10 分。まだ走っていれば 5 分刻み    |
| 枠（`rate limited` や直近の終了時刻） | `available in N minutes` か、直近の終了の 1 時間後 |
| CI                                    | 走り出してから 10 分                               |
| 何も待っていない（全部ユーザー待ち）  | 30 分。何度続いても縮めない                        |

**待つものが無いのに短い間隔で回さない。** 見るたびに API を叩くだけで、
状態は変わらない。

## 見回りは 1 つのセッションで

**PR を作ったセッションは見回らない。見回りは 1 つのセッションにまとめる。**
枠は org で 1 本なので、セッションごとに見回ると、互いの依頼を知らずに枠を
取り合い、`rate limited` で依頼が走らずに終わる。

### 受け取り口

PR を作ったセッションは、見回りのセッションに次を渡す。

- **PR の番号と base。** base が `main` 以外なら、積んでいる下の段の番号
- **衝突しうる相手。** 同じファイルを触っている開いた PR（`CLAUDE.md` の表、
  ADR の番号と `docs/adr/README.md` の末尾など）
- **`bun install` が要るか。** `web/bun.lock` が動いた PR
- **まだ直していない指摘や、ユーザー待ちの判断があるか**
- **full review の扱い。** `/sync-prs` で取り込んだ PR は、`/sync-prs` の表の
  「full review」の列（まとめを書く・依頼し直す・要らない）

受け取った側は `status.sh` で状態を取り直し、マージ順の表に載せる。**full review の
扱いを受け取ったら、`status.sh` の `fr` より優先する。** `status.sh` は、衝突を
解くときに変更を書き換えたかを見分けられない。「依頼し直す」と渡された PR は、
まとめがあって `決着済み` と出ても依頼し直す。

## CI が走らない

**push しても CI が走らないなら、衝突を疑う。** `mergeable` が `false`
（`dirty`）だと、`pull_request` のワークフローは起動しない。#259 ではこれで
1 時間空回りした。`status.sh` の `ci=未起動` と `mergeable=false/dirty` が
並んでいたら `/sync-prs` に回す。

## やらないこと

- **マージ。** `/land` の担当。
- **増分の `@coderabbitai review` を依頼すること、要約の「Trigger review」の
  欄を押すこと。** マージの条件にならないうえ、要約を増分が読んだ head で
  書き換える。欄を押したことはコメントに残らないので、full review の終わりから
  5 分以内に押されると、`status.sh` は要約の commit をどちらが読んだか見分け
  られない（「full review の読み方」）。
- **走行中や枠切れを決着と読むこと。** 判定は `status.sh` の `=>` だけを見る。
- **直し以外を積んだのに、依頼し直さずにまとめで済ませること。** `status.sh` は
  まとめの中身を確かめられない。まとめが言っていることを本当にするのは書いた側。
