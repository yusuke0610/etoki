# 壊して確かめる

`.claude/rules/test-effectiveness.md` の「検知能力を確かめる」を回す手順。
**何を確かめるべきかはそちらが正本で、ここには写さない。**

## 1. 壊すものを並べる

差分が足した守りを 1 つずつ挙げる。条件、早期の `return`、世代の照合、依存の
配列、上限の境界など。

**壊すのは振る舞いで、構文ではない。** 構文や型が壊れて落ちても、テストが守りを
見ている証拠にならない。

## 2. 宣言を書く

置き場所は `tmp/mutate/<名前>.json`（`tmp/` は gitignore 済み）。

```json
{
  "file": "web/src/app/useBoardNavigation.ts",
  "cwd": "web",
  "cmd": ["bunx", "vitest", "run", "src/app/useBoardNavigation.test.ts"],
  "mutations": [
    {
      "name": "ログアウトで未保存の確認を通さない",
      "edits": [
        {
          "from": "消えるものは同じ。\n    if (!confirmDiscard()) return;",
          "to": "消えるものは同じ。"
        }
      ]
    }
  ]
}
```

- **`cmd` は対象のテストだけを回す。** `cwd` はリポジトリのルートからの相対。
- **`from` は、ファイルにちょうど 1 回現れる文字列にする。** 足りなければ前後を
  含めて長くする。
- **1 つの壊し方に、書き換えを複数書ける**（`edits`）。フックの比べ方を変えるなら、
  依存の配列も同じ壊し方の中で変える。変えないと古い値を閉じ込めたままになり、
  挙動が変わらない。別のファイルを書き換えるときは、書き換えごとに `file` を書く。

## 3. 走らせる

```sh
make mutate SPEC=tmp/mutate/<名前>.json
```

- **止まる場面は 2 つある。** 壊す前から落ちているときと、書き換えが 1 つでも
  当たらないとき。どちらも、壊し方を 1 つも走らせずに止まる。
- **壊したファイルは、壊し方ごとに戻す。** Ctrl-C で止めても戻してから抜ける。
  終わったら `git status` で、触ったファイルが壊す前のままかを見る。
- **出力は `tmp/mutate/<番号>.log` に落ちる。** 落ちたものも、狙ったテストで
  落ちたかをログで確かめる。Go はビルドに失敗しても落ちる。

## 4. 落ちなかったものを決着させる

| 落ちなかった理由                         | やること                         |
| ---------------------------------------- | -------------------------------- |
| テストが守りを見ていない                 | テストを足して、もう一度回す     |
| 二重の守りの片方（もう片方が先に止める） | 残すなら、理由を PR 本文に書く   |
| その行に届く経路が無い                   | 同上。届かない理由を名指しで書く |

## 5. PR 本文に書く

「テスト」の節に次を書く。

- 壊したものを名前で並べる。
- すべて落ちたかを書く。落ちなかったものがあれば、その理由も書く。

宣言の JSON はコミットしない。
