# RV（セルフレビュー）

作業中の差分を etoki の規約に照らして点検し、直し、また点検する。

## 何を見るか

対象は**このブランチで加えた変更のみ**。既存コードの粗探しはしない。

```sh
git status --short
git diff main...HEAD        # コミット済みの差分
git diff                    # 未コミットの差分
git diff --cached
```

差分の周辺は必要なだけ読む。変更行だけ見て判断しない。

## 1 周の手順

1. 上のコマンドで差分を集める。**初回は `main...HEAD` の全体。2 周目以降は
   前の周で直した箇所を起点にする**。差分全体を取り直すのは、直した内容が
   構造に及んだときだけ。周ごとに全部を読み直すと、見る範囲は変わらないまま
   量だけ 3 倍になる（#125）。
2. 下の観点で点検する。
3. 見つけたものを分類する（後述）。
4. 「直す」に分類したものを直す。
5. `make lint` と `make test` を通す。UI かハンドラを触っているなら
   `make test-e2e` も通す（`make` は devShell の外からでも自分を包み直す）。
   **出力はログに落とし、終了コードだけ見る。**

   ```sh
   mkdir -p tmp
   make lint >tmp/lint.log 2>&1; echo "lint=$?"
   make test >tmp/test.log 2>&1; echo "test=$?"
   ```

   0 ならログを開かない。0 でなければ `tmp/*.log` の落ちた箇所だけ読む。
   **通った検査の出力は判断に使わないのに、落ちたときと同じ量を持ち込む。**
   3 周ぶん効く（#125）。`tmp/` は `.gitignore` 済み。

6. 直したものがあれば次の周へ。なければ終了。

## 観点

CLAUDE.md に書いてある規約が守られているかを見る。以下は落としやすい順。

**規約は 1 ファイルではない。** ルートの `CLAUDE.md` に全体の規約があり、
領域ごとの約束は触ったディレクトリの `CLAUDE.md`（`internal/` / `web/` / `api/`）
にある。差分がそのディレクトリに及んでいるなら、そちらも読んで照らす。

**`.claude/rules/` のテーマ別の落とし穴集にも照らす。** 過去の CodeRabbit
レビューで実際に踏んだ形を集めてあり、各ファイルの `paths` が差分に
かかるものを読む。対象ファイルを読めば自動でも読み込まれるが、点検の周では
明示的に開いて 1 項目ずつ照らす。「やらないこと」の節は逆向きの検査で、
そこに載っている「修正」を善意で入れていないかを見る。

**`.claude/rules/` 自体を変更したなら、そのファイルを別に点検する。** どの
rule の `paths` も `.claude/rules/**` を対象にしていないので、上の手順では
自分自身が読み込まれない。本文が要求している変更対象（例:「実装とテストを
同時に足す」なら実装側のパス）が `paths` に入っているか、参照先
（`CLAUDE.md` / ADR）が実在して内容とずれていないかを見る。**読み込まれない
規約は無いのと同じ。**

### 中核思想（最優先）

- ブレストフェーズに issue / epic の概念を持ち込んでいないか。
- 付箋の座標や近接から構造をルールベースで推測していないか。構造の解釈は
  Vision LLM の仕事。
- 自動同期・自動更新・自動作成を足していないか。トリガーは常に開発者。

### 壊れやすい約束

- `Element.isAnnotation`（Go）と `isAnnotation`（TS）は同じ規則か。片方だけ
  変わっていないか。
- `content_hash` の入力はテキストのみ。図形・座標を混ぜていないか。
  `TestComputeContentHash_IgnoresNonTextChanges` を通すために仕様を変えて
  いないか。**これは仕様であって不具合ではない。善意で直さない。**
- `sync_runs` は履歴。既存 run を上書き・削除していないか。
- 最新 run の決定に `created_at` を使っていないか（`id` で決める）。
- GitHub に作るのは epic と issue の 2 階層のみ。`summary` を作っていないか。
- 境界の DTO を手書きしていないか。`api/openapi.yaml` を直したなら
  `make codegen` の結果が同じコミットに入っているか（ADR 0011）。
- エラー本文に `gin.H` を直書きしていないか。`ErrorResponse` に揃っているか。
- E2E のモック応答が生成型から外れていないか。`tsconfig.json` の `include` から
  `e2e` を外していないか（ADR 0012）。

### 構造

- ユースケース層がクラウド / GitHub SDK の型を直接参照していないか。
  `go.mod` にクラウド SDK が増えていないか。
- `port/` が `internal/` に依存していないか。境界 DTO を自前で持っているか。
- SQLite の配線を知っているのが `cmd/etoki` だけのままか。

### 進め方

- テストが先にあるか。状態判定と冪等性に対応するケースがあるか。
- 外部サービスに触れる箇所はインターフェース越しで、テストはフェイクか。
- 設計判断をしたなら `docs/adr/` にあるか。`docs/adr/README.md` の索引も
  更新したか。実装を読めば分かることを ADR に書いていないか。
- スコープ外（IaC、特定クラウド前提、Postgres 実装、逆方向同期など）を
  入れていないか。
- 慣用的でない書き方に理由のコメントがあるか。逆に、差分を読めば分かること
  をコメントで繰り返していないか。
- コミットが Conventional Commits 形式か。本文が「何をしたか」ではなく
  「なぜそうしたか」になっているか。赤いコミットを挟んでいないか。

## 指摘の分類

見つけたものは必ずどれかに割り振る。曖昧なまま直さない。

| 分類     | 扱い                                                       |
| -------- | ---------------------------------------------------------- |
| 直す     | 規約違反、バグ、テスト漏れ。その周のうちに直す。           |
| 直さない | 仕様として固定されているもの。**理由を添えて報告に残す。** |
| 聞く     | 設計判断が要るもの。手を動かさずユーザーに投げる。         |

好みの問題は指摘しない。周辺コードと違う書き方をしている場合だけ挙げる。

## 打ち切り条件

**最大 3 周。** 周回はこのスキルの中で回す（`/loop` は要らない）。

- 指摘ゼロなら、その時点で終わる。周回数を消化しない。
- 3 周して残った指摘は、直さずに一覧で報告して判断を仰ぐ。同じ箇所を
  3 周直しても収まらないなら、それは設計の問題であって手直しの問題ではない。
- 直した結果が別の指摘を生む堂々巡りに入ったら、そこで止めて報告する。

## 報告

各周について、見た範囲・指摘・対応を簡潔に。最後に:

- 直したもの
- 直さなかったもの（理由つき）
- ユーザーの判断を待つもの
- `make lint` / `make test` の結果
- UI を触ったなら `make test-e2e` の結果と、`web/e2e-output/screenshots/` の
  スクリーンショット（`web/CLAUDE.md`「報告にブラウザの実行結果を添える」）
