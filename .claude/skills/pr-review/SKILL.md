# PR レビュー対応

付いた CodeRabbit の指摘を、**1 件ずつ決着させ、まとめを書く。** レビューは
自動では付かず、`@coderabbitai full review` で依頼して初めて付く。依頼と待ち、
決着したかの判定は `/pr-watch` の担当で、ここには写さない。

レビューの言語・頻度・対象は `.coderabbit.yaml`（リポジトリ直下）で決まる。
挙動が想定と違うときはまずそこを見る。

## 指摘を取る

指摘は依頼の数分後に付く。**直後に見て無ければ待つ。** レビューが来ないことと
指摘が無いことは、待たないと区別できない。走り終えたかは `/pr-watch` の
`status.sh` で見る。

```sh
.claude/skills/pr-review/findings.sh <番号>
```

まだ決着していないスレッドの先頭コメントだけが出る。1 行目に review の件数と
時刻が出るので、**「まだ来ていない」と「指摘が無い」はそこで区別する。**

**返信・`<details>`・walkthrough は落としてある。** 全文を取ると 1 PR で 6 万
文字に達し、その大半は確認応答と Analysis chain で、決着の判断には使わない
（#125）。落ちたものが要るときだけ、絞り込む前の全文を直に見る。行単位の
コメントとレビュー本体（walkthrough を含む）は別のエンドポイントなので、
両方取る（#127）。

```sh
gh api repos/yusuke0610/etoki/pulls/<番号>/comments -q '.[] | "\(.path):\(.line)\n\(.body)"'
gh api repos/yusuke0610/etoki/pulls/<番号>/reviews -q '.[] | "\(.user.login):\n\(.body)"'
```

CodeRabbit は増分レビューなので、2 回目以降は**前回から変わった範囲しか
見ない**。指摘が返ってこないのは「今回の差分には無い」という意味であって、
過去の指摘が消えたわけではない。

## 1 件ずつ決着をつける

放置しない。どちらかに割り振る。

| 判断     | やること                                  |
| -------- | ----------------------------------------- |
| 直す     | 修正して push する                        |
| 直さない | **理由をコメントで返す。** 黙って閉じない |

決着させるのは、全部そのとおりに直すという意味ではない。

**リポジトリの規約や仕様と衝突する指摘は直さない。** レビュアーは事情を
知らない。よくあるもの:

- `content_hash` がテキストのみなのを「バグ」と言われる → 仕様。
  `TestComputeContentHash_IgnoresNonTextChanges` で固定してある（`internal/CLAUDE.md`）。
- `Origin` の無いリクエストを通すのを「穴」と言われる → ADR 0013 の判断。
- `sync_runs` を上書きしないのを「無駄」と言われる → ADR 0007 の判断。

どれも直さず、理由を返す。

スレッドは自分で解決する。返信しただけでは open のまま残る。`findings.sh` が
出す `thread=` の id をそのまま渡す。

```sh
gh api graphql -f query='mutation($id:ID!){resolveReviewThread(input:{threadId:$id}){thread{isResolved}}}' -F id=<thread の id>
```

**解決したスレッドは次から `findings.sh` に出ない。** 決着したものを毎回
読み直さずに済むのはこのため。裏返すと、**解決し忘れたスレッドは決着済みでも
出続ける。**

**返信したら、CodeRabbit の応答を読んでから解決する。** 応答は返信の数十秒後に
付き、「残っている」と返ることがある。先に解決すると `findings.sh` に
出なくなり、その反論は読まれないまま残る（#160）。

## 直したら

**直して push しても、full review は依頼し直さない**（`CONTRIBUTING.md`「マージ」）。
依頼し直すのは、full review のあとに直し以外を積んだときだけ。直した範囲が指摘より
広がった（指摘の箇所を直すついでに別の箇所も書き換えた、など）もこれに当たる。
**直す範囲は指摘の箇所に収める。** 広げたくなったら、別の PR にするか、依頼し直す
前提で積む。

## まとめを書く

全件の決着が付き、スレッドを全部解決したら、**PR にまとめのコメントを 1 つ書く。**
ユーザーは指摘を全部は読まないので、Claude が何を直さなかったかをあとから辿れる
のはここになる。`status.sh` はこのコメントの印で決着を判定する（`/pr-watch` の
「full review の読み方」）。

```sh
gh api -X POST repos/yusuke0610/etoki/issues/<番号>/comments -F body=@- <<'EOF'
<!-- etoki:findings-settled -->
full review（<終わった時刻>）の指摘を決着させました。

- 直した（N 件）: <指摘の要約> → <直したコミット>
- 直さなかった（M 件）: <指摘の要約> — <理由>（スレッドへのリンク）

full review のあとのコミットは、指摘への直し<と main の取り込み>だけです。
EOF
```

- **印（1 行目）を消さない。** 無いと決着に数えられない。
- **最後の 1 文が本当であるときだけ書く。** 直し以外を積んだなら、まとめで
  済ませずに `/pr-watch` に依頼し直してもらう。`status.sh` は中身を確かめられない。
- **本文にだけ載った指摘（nitpick、diff の外）も数える。** スレッドが無いので、
  解決し忘れても `status.sh` では見えない。
- **依頼し直したら、次の full review が終わってから書き直す。** 前のまとめは数えない。

## 決着した指摘を規約に還す

全件の決着が付いたら、**一般化できる指摘を `.claude/rules/` の該当テーマに
追記する。** テーマは `ls .claude/rules` で見る。**ここに列挙しない。** 写すと
rules を足した日にここだけが古くなり、足したテーマに指摘が還らない（#154）。
**その PR を離れる前に書き切る。** 後回しにすると、ADR 0033 でやった棚卸しを
もう一度やることになる。

入れる基準は 3 つ。全部満たすものだけ入れる。

- 再発しうる一般則である。単発の実装バグは入れない。
- lint / 型 / CI で塞げない。機械で塞げるならそちらに寄せる。
- 既存の規約（CLAUDE.md / ADR / rules）に無い。あるならリンクで済ます。

**「直さない」と返した指摘も、上の 3 条件を満たすものだけ入れる。** 該当テーマの
「やらないこと」に理由と PR 番号を添えて入れる。書いておかないと、将来の実装や
セルフレビューが同じ「修正」を善意で入れ、レビューでも同じ議論をやり直す。
却下の側で効くのは 1 つめで、**その PR 限りの却下は入れない**。別の PR でも
同じ形で来るものだけが対象。

該当が無ければ何も足さない。1 件 1〜3 行に収め、出典の PR 番号を添える。

**そこで新しい設計判断が確定したなら、行き先は `docs/adr/`。** 返事を書くために
「なぜこの形なのか」を言語化した結果が、rules の 1〜3 行に収まらない判断だった
場合（既存の判断を覆したなら、その ADR の更新）。索引
（`docs/adr/README.md`）にも足す。**番号は進行中の PR と衝突しうる**ので、
先に確かめる（`CONTRIBUTING.md`）。

ADR に書いたら rules 側はそこへのリンクで済ます。**同じ内容を 2 箇所に置かない。**
設計判断が無いなら、ADR は触らない。

## 止める条件

- 指摘が収束しない
- 同じ箇所を何度も往復している

このどちらかになったら、そこで止めてユーザーに報告する。往復が続くのは
指摘の問題ではなく設計の問題であることが多い。

決着が付いた PR をマージしてよいかは `CONTRIBUTING.md` の「マージ」。
