# PR レビュー対応

PR を作ったら CodeRabbit のレビューが付く。**作りっぱなしにせず、指摘が
なくなるまで対応する。**

レビューの言語・頻度・対象は `.coderabbit.yaml`（リポジトリ直下）で決まる。
挙動が想定と違うときはまずそこを見る。

## 指摘を取る

指摘は数分遅れて付く。**直後に見て無ければ待つ。** レビューが来ないことと
指摘が無いことは、待たないと区別できない。

```sh
gh pr view <番号> --json reviews -q '.reviews[].body'
gh api repos/yusuke0610/etoki/pulls/<番号>/comments -q '.[] | "\(.path):\(.line)\n\(.body)"'
```

CodeRabbit は増分レビューなので、2 回目以降は**前回から変わった範囲しか
見ない**。指摘が返ってこないのは「今回の差分には無い」という意味であって、
過去の指摘が消えたわけではない。

## 1 件ずつ決着をつける

放置しない。どちらかに割り振る。

| 判断     | やること                                  |
| -------- | ----------------------------------------- |
| 直す     | 修正して push する                        |
| 直さない | **理由をコメントで返す。** 黙って閉じない |

「指摘がなくなるまで」は、全部そのとおりに直すという意味ではない。

**リポジトリの規約や仕様と衝突する指摘は直さない。** レビュアーは事情を
知らない。よくあるもの:

- `content_hash` がテキストのみなのを「バグ」と言われる → 仕様。
  `TestComputeContentHash_IgnoresNonTextChanges` で固定してある（`internal/CLAUDE.md`）。
- `Origin` の無いリクエストを通すのを「穴」と言われる → ADR 0013 の判断。
- `sync_runs` を上書きしないのを「無駄」と言われる → ADR 0007 の判断。

どれも直さず、理由を返す。

スレッドは自分で解決する。返信しただけでは open のまま残る。

## push したらもう一度見る

修正を push すると再レビューが走る。**対応した結果に新しい指摘が付くことが
ある。** もう一度取り直して、また 1 件ずつ決着させる。

## 決着した指摘を規約に還す

全件の決着が付いたら、**一般化できる指摘を `.claude/rules/` の該当テーマに
追記する**（e2e-mocks / test-effectiveness / validation-boundaries /
async-ui / github-adapter / docs-consistency）。**その PR を離れる前に
書き切る。** 後回しにすると、ADR 0033 でやった棚卸しをもう一度やることに
なる。

入れる基準は 3 つ。全部満たすものだけ入れる。

- 再発しうる一般則である。単発の実装バグは入れない。
- lint / 型 / CI で塞げない。機械で塞げるならそちらに寄せる。
- 既存の規約（CLAUDE.md / ADR / rules）に無い。あるならリンクで済ます。

**「直さない」と返した指摘も、上の 3 条件を満たすものだけ入れる。** 該当テーマの
「やらないこと」に理由と PR 番号を添えて入れる。書いておかないと、将来の実装や
セルフレビューが同じ「修正」を善意で入れ、レビューでも同じ議論をやり直す。
却下の側で効くのは 1 つめで、**その PR 限りの却下は入れない**。別の PR でも
同じ形で来るものだけが対象。

該当が無ければ何も足さない。1 件 1〜3 行に収め、出典の PR 番号を添える。

**そこで新しい設計判断が確定したなら、行き先は `docs/adr/`。** 返事を書くために
「なぜこの形なのか」を言語化した結果が、rules の 1〜3 行に収まらない判断だった
場合（既存の判断を覆したなら、その ADR の更新）。索引
（`docs/adr/README.md`）にも足す。**番号は進行中の PR と衝突しうる**ので、
先に確かめる（`CONTRIBUTING.md`）。

ADR に書いたら rules 側はそこへのリンクで済ます。**同じ内容を 2 箇所に置かない。**
設計判断が無いなら、ADR は触らない。

## 止める条件

- 指摘が収束しない
- 同じ箇所を何度も往復している

このどちらかになったら、そこで止めてユーザーに報告する。往復が続くのは
指摘の問題ではなく設計の問題であることが多い。
