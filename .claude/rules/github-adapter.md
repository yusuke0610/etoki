# GitHub アダプタの縁

GitHub API を叩く側で実際に踏んだ穴。いずれもテストが無い経路で
起きた。

## ページング

**終端の見方は REST と GraphQL で違う。** 片方の書き方をもう片方に持ち込むと
取りこぼす。

- **一覧は入れ子の内も外も回し切る。** 内側（リポジトリ）だけページング
  して外側（インストール一覧）が 1 ページ止まり、という非対称で取り
  こぼした（#26）。
- **REST は「短いページが返ったら終わり」。** `total_count` は権限で
  絞られた件数と食い違うので信じない（#26）。
- **GraphQL は `pageInfo` で決める。** `hasNextPage` が真なら
  `endCursor` で続ける。**ページの件数で打ち切らない**（`nextCursor`）。
  進まないカーソル（空、または前回と同じ）は無限ループなので、黙って
  終わらせずエラーにする。
- **件数上限とは別に、ページ数の上限も置く。** フィルタで捨てる行が
  多いと、件数が増えないまま全ページを辿り続ける。REST 側は
  `maxRestPages`（#26）。GraphQL 側はサーバーのクエリで絞るので
  （下の「クエリと応答」）、この歯止めは要らない。

## クエリと応答

- **絞り込みはサーバー側のクエリで行う。** `isArchived: false` や
  `minPermissionLevel: WRITE` をクエリに載せ、クライアント側の読み捨てに
  しない。ページングの数え方も正しくなる（#25）。
- **403 は `retry-after` を先に見る。** secondary rate limit は
  `x-ratelimit-remaining` が残っていても 403 + `retry-after` で来る。
  先に `port.ErrForbidden` に包むと、待てば直るものが権限エラーの導線に
  流れる（#28）。
- **応答の形の揺れ（`node: null` 等）は、扱いを決めてテストで固定する**
  （`test-effectiveness.md`、#28）。

## テスト

- **REST / GraphQL の経路を足したら `httptest` のテストを同時に足す。**
  送っているクエリ文字列（フィルタ引数を含む）と、ページングの終端条件を
  断言する。`ModeApp` にテストが無かったことが、ページング取りこぼしの
  残った理由だった（#26 / #25）。
