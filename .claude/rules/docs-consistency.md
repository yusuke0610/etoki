# 記述と実装の整合

ドキュメントへの指摘は「書いてあることが実装と違う」に集中している。
どれも書いた時点では合っていて、片方だけ変えたときにずれた。

## 実装と同じコミットで揃える

- **意味や挙動を変えたら、それを説明する記述も同じコミットで変える。**
  ADR の比較規則、画面のラベル、Makefile の `##` と `CLAUDE.md` の
  コマンド説明。追記した節と矛盾する結論を上に残す形でもずれる
  （#87 / #84 / #81 / #23）。
- **規則は関数名でなく内容で書く。** 「`normalizeText` を通す」ではなく
  「改行コード・行末の空白・NFC・前後の空白を畳む」。名前で書くと、
  実装を読まない限り記述とのずれに気づけない（#87）。
- **規約に現在値や件数を書き写さない。** 「いま `eslint-disable` は 1 件」の
  ような実装状態は実装の側に置く。写すと実装を足した日にここだけが古くなり、
  ずれても機械では気づけない（#106）。

## 保証の書き方

- **守れる範囲だけを書く。** 「外部サイトから叩けない」ではなく
  「未許可のオリジンから状態を変える API を叩けない」。広く書くと、
  後から GET に副作用を足した人が矛盾に気づけない。残る隙は「後述」で
  結んで、離れた記述の対応を示す（#23）。
- **条件は判断基準そのもので書く。** 「ループバック以外を拒否」ではなく
  「許可していない Host / Origin を拒否（ループバックは常に許可）」。
  実装の分岐と違う軸で要約すると、例外を足すたびに嘘になる（#23）。

## ADR

- **ADR には「なぜ」だけを書く。** 生成器の挙動のような実装詳細は
  実装側のコメントへ。両方に書くと二重になる（#21、`CLAUDE.md`）。
- **あえてしないことは理由ごと書く。** 「`Excalidraw` は包まない。
  包んでも助かるものが無いため」。書かないと、揃っていないのが漏れ
  なのか判断なのかを後から読む人が区別できない（#85）。
- **参照する API 名は実装と一致させる。** 案内先を間違えると外部
  実装者が誤った出入口を読む。どこからも読まれない公開 API は、名前を
  直すのではなく削除を検討する（#26）。
- **他の ADR を前提として引くときは、それが置き換え済みでないか
  確かめる。** 捨てた前提を新しい ADR の根拠にすると、読んだ人は
  生きている判断だと受け取る（#92）。
- **他所の仕様を根拠にするなら、書く前に今の記述を見る。** 「〜できない
  から採らない」は相手が直せば嘘になり、判断だけが残る。**採らない理由は
  仕様ではなくこちらの都合で書けるか**を確かめてから引く（#92）。

## 対になるファイルを名指しするとき

- **相手のファイル名は、実際にそれかを開いて確かめる。** 共有の
  `testdata` を読む対の相手を `annotation.test.ts` と書いていたが、
  読んでいるのは `annotationRule.test.ts` だった。**惜しい名前が実在
  すると、開いた人は「読んでいない」で終わり**、対の相手を教えるための
  コメントが対の相手を隠す。パスの実在では検知できない（#104）。

## やらないこと

- **80 桁の折り返しで入った改行を「余分な空白」として詰めない。** 日本語の本文は
  MD013 に合わせて 80 桁で折り返してある（`.markdownlint-cli2.yaml`）。校正の
  道具は行をつないでから読むので、改行をまたぐ助詞を「`決めた のと`」のような
  分かち書きとして拾うが、ソースに空白は無く、前後がどちらも CJK の soft line
  break は描画時に空白にならない。折り返す位置を変えても次の行境界で同じ形の
  指摘が出る（#120）。
