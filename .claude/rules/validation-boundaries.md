# 検証の置き場所と契約

入力検証と排他をどこに置くか。CodeRabbit は「ハンドラで検証しろ」
「フロントにも同じ判定を」と提案しがちだが、このリポジトリの答えは
決まっている。

## 単一ゲート

- **入力検証はユースケース層かドメインの 1 箇所に置く。** ハンドラ・
  openapi・フロントに重複させない。2 箇所に置くと片方だけ変わる。
  `ErrInvalidInput` を 400 に写すのは `h.fail` の仕事で、ハンドラに
  足すものはない（#75 / #81）。
- **同じ判定を提案されたら、既にどこが見ているかを先に確かめる。**
  重複 `previousItemId` は `domain.Validate` が、作成先の判定は
  `BoardService.SetTarget` が持っている。指摘への返事はその場所と
  テスト名で返す（#81）。
- **不正値は黙って空に落とさず、400 で弾く。** 渡した値が消えたことに
  呼び出し側が気づけない（#75、ADR 0018 と同じ思想）。

## 検証の範囲

- **知っていることだけを検証する。** projectUrl はスキームとホストは
  見るが、パスの形（`/orgs/` か `/users/` か）は見ない。etoki は owner が
  user か org かを知らないので、形の検証は「知らない」という判断を裏で
  覆すことになる（#75、ADR 0025）。
- **設定値はコンストラクタで検証し、実行時に持ち越さない。** `New` で
  検証する目的は綴り間違いの早期検出なので、スキームだけでなくホスト名の
  有無まで見る。`url.Parse` は `http://` も `https:host` も通す（#16）。
- **設定できないものを設定可能なふりで持たせない。** GHES のホストは
  `BaseURL` を設定する導線を作るときに一緒に開ける（#75）。
- **正規化して空になる入力は「空」として弾く。** 検査の順は「直す道が
  残るほう」で決める。改行だけの title に「1 行にまとめてください」と
  返しても直しようがない（#96、ADR 0029）。

## 構造の守り

- **排他はユースケース層に置く。** `BoardLocks` のように。`port/` は
  永続化の境界であり、予約や revision を持ち込まない（#25）。
- **`BoardService` に GitHub 依存を生やさない。** 作成先の実在確認の
  ような提案は、ボードの読み書きを GitHub の可用性に依存させる。
  問い合わせは `GitHubCatalogService` の担当（#25 で却下済み）。
- **取り消せない外部書き込みの列に工程を足すときは、途中失敗の後に
  「どこまで進んだか」が記録に残るかを確かめる。** 更新成功のあとの
  フィールド設定失敗で run ごと消える、という形になりやすい（#81）。
- **版の 1ns 繰り上げは、基準を照合する保存だけの約束**（ADR 0020）。
  `updated_at` を書く経路すべてに課さない。基準を取らない書き込み
  （作成先や表示名の更新）で版を前に出すと、シーンを編集中の別の
  利用者に理由のない 409 が出る（#96）。

## 大きさの上限と検証の順

- **読み込みの歯止め（`http.MaxBytesReader`）は、正本の上限をエスケープの
  最悪値で割り増して置く。** JSON の文字列は `\u00XX` で 1 バイトが 6 バイトに
  なるので、2 倍で取ると上限ちょうどの入力が歯止め側で落ち、減らす必要の
  ないものを減らせと言うことになる（#100）。
- **入力の検証はアクセス確認より先でよい。** 入力だけで決まる 400 / 413 は
  ボードの有無に依らないので、非メンバーに存在を教えることにならない。
  「404 / 403 が先」という指摘には、判定がボードを見ていないことで返す（#100）。

### やらないこと

- **永続化層の `WHERE` にロールの集合を書かない。** 「認可の確認と UPDATE の
  あいだに降格されうる」という指摘で提案されるが、ロールの上下を知るのは
  `port.BoardRole.AtLeast` だけ、という判断が先にある（ADR 0017、
  `internal/CLAUDE.md`）。書き込み経路すべてが同じ形なので、1 つだけ足すと
  判定が 2 箇所になる（#105）。

- **認可を先に、ロックを後にする順序へ入れ替えない。** 「不存在の ID で
  ロックのエントリが増える」という指摘で提案されるが、`locks.Acquire` は
  6 つの書き込み経路すべてで認可より前にある。入れ替えると認可と実行の
  あいだに作成が割り込み、指摘自身が求める「取得後の再確認」が要る。
  判定を直列化の内側に置くほうが状態として正しい（#109）。

- **押す前に見せた数を、実行時の前提条件にしない。** 「確認で返した件数に
  token を付けて、変わっていたら 409 で確認をやり直させろ」と提案されるが、
  あれは判断の材料であって可否の入力ではない（中核思想 3）。照合すると、
  数が増えただけで畳めないボードが残る（ADR 0042、#109）。

- **バインド成功後にボディの残りを読み切って上限に数える。** 歯止めは
  「メモリに載せる量」の上限であって、読まないバイトは守る対象ではない。
  数えるために捨て読みすると、守るためのはずの読み込みが増える（#100）。

- **サーバーや GitHub が返した本文を、伏せたり安定した `code` に差し替えたり
  しない。** 「生の例外を画面に出すな」という指摘で提案されるが、畳んだ本文
  しか手掛かりが無い経路がある、というのが ADR 0034 の判断。1 件ずつ理由が
  違いうるので 1 つの code にも落ちない。保存して履歴に出すときは**読める人が
  広がる**ので、そこだけは ADR に書いて確かめる（ADR 0043、#117）。

- **実行の上限を、試行ごと（`llm.Complete` ごと）に取り直さない。** 「1 回の枠で
  再送のぶんまで通る」という指摘で提案されるが、縛る対象は開発者が押した回数、
  という判断が先にある（ADR 0044）。取り直すと、再送の途中で断られて払ったぶんが
  結果にならず、同時実行の枠も試行の隙間に割り込まれる。総量を縛るなら
  `maxAttempts` を動かす（#120）。

- **契約の説明が保証する範囲を、永続化層が受け付けるかどうかで緩めない。**
  「`SaveRun` は空の `Items` を保存できるから、空配列がありうると書け」と
  提案されるが、その口に書ける経路はユースケース 1 つで、そこが弾いている
  （ADR 0009）。単一ゲートの裏返しで、**保証の出どころもゲートの側**にある。
  ただし「昔の版なら書けた」は別問題なので、経路がいつからあるかは確かめて
  から返す（#117）。
